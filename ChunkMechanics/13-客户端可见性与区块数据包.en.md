Chapter 1 explained that client chunk data **comes entirely from server synchronization**. This chapter pursues a more specific question: when does the server decide "this player should see this chunk," and which packet does it use to send the changes?

## Server Authoritative, Client Only a Snapshot

The terrain rendered by the client is not a locally authoritative world, but a snapshot of chunks sent by the server. The server's `WorldChunk` is the authoritative data source; after the client receives a `ChunkDataS2CPacket`, it only rebuilds a locally renderable and queryable copy in its `ClientWorld`.

This also explains why "can see" and "is simulating" are not the same thing. Client rendering is controlled by `watchDistance` (the chunk watch range related to player view distance); server block ticking and entity ticking are controlled by load levels and simulation distance covered in Chapter 3. Players may see distant terrain, but redstone, random ticks, or entity AI there are no longer running.

## Types of Chunk Packets

The server doesn't synchronize chunks with "one big packet for everything." The heaviest type is `ChunkDataS2CPacket`, the **chunk data packet (S2C)**. When a chunk newly enters a player's view, `ThreadedAnvilChunkStorage.sendWatchPackets()` sends it via `sendChunkDataPackets()`. This packet carries the chunk's main client-visible data: block states, biomes, block entity data, and lighting data filled in by `ServerLightingProvider`. The client can then build the corresponding renderable chunk locally.

After entering view, most changes don't require resending the entire chunk. Single block changes typically use `BlockUpdateS2CPacket`, the **block update packet (S2C)**; when multiple block changes accumulate within the same sub-chunk, `ChunkHolder.flushUpdates()` switches to `ChunkDeltaUpdateS2CPacket`, the **chunk delta update packet (S2C)**. Light changes are sent separately via `LightUpdateS2CPacket`, the **light update packet (S2C)**, to players at the edge of watch distance. The division of labor among these packets is essentially bandwidth optimization: the first time entering view requires a complete snapshot, subsequent local changes only send differences.

> [!NOTE]
> After sending `ChunkDataS2CPacket`, `sendChunkDataPackets()` also refreshes entity tracking status for entities in that chunk to that player, and resends packets for leashes, passengers, etc. But these belong to the entity sync system, not chunk data packets themselves.

## When to Send Chunk Data

When a player joins, leaves, or moves, TACS recalculates which chunks the player observes. Joins and leaves go through `handlePlayerAddedOrRemoved()`; moves go through `updatePosition()`. Both enumerate candidate chunks around the player's new and old `ChunkSectionPos` and use `isWithinDistance()` to determine whether a chunk is within the current `watchDistance`.

When a chunk changes from "not in view" to "in view," `sendWatchPackets()` retrieves the corresponding `ChunkHolder`, then its `WorldChunk`, and sends `ChunkDataS2CPacket`. When a chunk changes from "in view" to "not in view," the same method only calls `player.sendUnloadChunkPacket(pos)`, telling the client to discard the local copy of that chunk.

Block changes take a different path. `ChunkHolder.markForBlockUpdate()` doesn't send packets immediately, but packs the local coordinate into a `short` and puts it into `blockUpdatesBySection`. After each tick's subsequent refresh, `flushUpdates()` batch-sends these changes to players watching that chunk. This way, many adjacent block changes within the same tick can be merged into one chunk delta update, rather than creating many scattered small packets.

View distance changes also trigger recalculation. `setViewDistance()` first clamps the new value to 2-32, then updates the `ticketManager`'s watch distance, then iterates all current `ChunkHolder`. For each player watching that chunk, it calculates `isWithinDistance()` results under old and new distances; only boundary changes like "old in, new out" or "old out, new in" call `sendWatchPackets()`.

## Geometric Determination of `watchDistance`

The `watchDistance` determination is not a simple Chebyshev distance. Load ticket propagation commonly uses "maximum horizontal or vertical offset" to form a square range, while `ThreadedAnvilChunkStorage.isWithinDistance()` uses a different geometry: it first shrinks the X/Z direction differences by 1, then uses an approximate Euclidean distance expression for comparison.

The core logic can be rewritten as:

```java
int dx = Math.max(0, Math.abs(chunkX - playerChunkX) - 1);
int dz = Math.max(0, Math.abs(chunkZ - playerChunkZ) - 1);
long longSide = Math.max(0, Math.max(dx, dz) - 1);
long shortSide = Math.min(dx, dz);
return shortSide * shortSide + longSide * longSide < distance * distance;
```

The initial 1-block subtraction gives a more lenient core area around the player's chunk; then `shortSide² + longSide² < distance²` cuts off corners. Therefore, the client watch range is more like a **rounded rectangle**, not the pure square of ticket propagation. This difference matters: both are called "distance," but `watchDistance` determines whether the client should keep a chunk snapshot, while ticket propagation determines what load level the server should push a chunk to.

## Player Chunk Watching Manager

TACS holds a `PlayerChunkWatchingManager`, the **player chunk watching manager**. It records which players are currently watching each chunk and handles player watch center moves, watch disables, watch re-enables, and other states.

This manager doesn't directly generate chunk data packets, but it determines "who should receive them." `ChunkHolder.flushUpdates()` queries the observer list via `PlayersWatchingChunkProvider`: light updates query players at the edge of watch distance, block updates query all players watching that chunk. In other words, `PlayerChunkWatchingManager` is the index table for the final delivery targets of full packets, incremental packets, and light packets.

## Summary

- Client chunks are snapshots synchronized from the server; client rendering and server simulation are controlled by different distance systems.
- `ChunkDataS2CPacket` is for full chunk sync when newly entering view, `BlockUpdateS2CPacket` and `ChunkDeltaUpdateS2CPacket` for block state changes, `LightUpdateS2CPacket` for light changes.
- Player joins, leaves, moves, and view distance changes all trigger watch range recalculation; only boundary changes entering or leaving watch range send full packets or unload packets.
- `watchDistance` uses a rounded-rectangle geometric determination, not equivalent to the Chebyshev distance in load ticket propagation.
- `PlayerChunkWatchingManager` tracks observers for each chunk and is the key index for deciding which players receive data packets.

## [!ADVANCED] Code Walkthrough

### sendWatchPackets: Four Enter/Leave Cases

In `sendWatchPackets()` parameters, `oldWithinViewDistance` indicates whether the chunk was in the player's watch range before the call, `newWithinViewDistance` indicates whether it's in range after:

```java
protected void sendWatchPackets(
    ServerPlayerEntity player,
    ChunkPos pos,
    MutableObject<ChunkDataS2CPacket> packet,
    boolean oldWithinViewDistance,
    boolean newWithinViewDistance
) {
    if (player.getWorld() == this.world) {
        if (newWithinViewDistance && !oldWithinViewDistance) {
            // Case 1: Just entered watch range
            ChunkHolder chunkHolder = this.getChunkHolder(pos.toLong());
            if (chunkHolder != null) {
                WorldChunk worldChunk = chunkHolder.getWorldChunk();
                if (worldChunk != null) {
                    this.sendChunkDataPackets(player, packet, worldChunk);
                }
            }
        }
        if (!newWithinViewDistance && oldWithinViewDistance) {
            // Case 2: Just left watch range
            player.sendUnloadChunkPacket(pos);
        }
    }
}
```

Only case 1 sends the chunk data packet; case 2 sends an unload packet. The other two combinations (`newWithinViewDistance == oldWithinViewDistance`) represent "still in" or "still out," neither requiring watch status change.

### sendChunkDataPackets: Lazy Packet Construction and Reuse

`sendChunkDataPackets()` doesn't immediately serialize the chunk into a packet. It uses a `MutableObject<ChunkDataS2CPacket>` to reuse the same packet across multiple players:

```java
private void sendChunkDataPackets(ServerPlayerEntity player, MutableObject<ChunkDataS2CPacket> cachedDataPacket, WorldChunk chunk) {
    if (cachedDataPacket.getValue() == null) {
        cachedDataPacket.setValue(new ChunkDataS2CPacket(chunk, this.lightingProvider, null, null));
    }
    player.sendPacket(cachedDataPacket.getValue());
    // ...
    this.updateEntityTrackers(player, chunk.getPos());
}
```

When the first player needs this chunk, `ChunkDataS2CPacket` is constructed and cached in `cachedDataPacket`; subsequent players directly read the cached value. This avoids multiple serializations of the same chunk data within a single tick.

### markForBlockUpdate: Local Coordinate Packing

`markForBlockUpdate()` uses `short` to pack block positions within a chunk:

```java
public void markForBlockUpdate(BlockPos pos) {
    if (this.pendingBlockUpdates != null) {
        int i = this.levelHeightAccessor.getSectionIndex(pos.getY());
        if (this.blockUpdatesBySection[i] == null) {
            this.blockUpdatesBySection[i] = new ShortOpenHashSet();
        }
        this.blockUpdatesBySection[i].add(ChunkSectionPos.packLocal(pos));
        this.pendingBlockUpdates = true;
    }
}
```

`packLocal(pos)` packs the chunk-local x, y, z coordinates (each 0-15) into a `short`: `(x & 15) << 8 | (y & 15) << 4 | (z & 15)`. This saves memory: each position only occupies 2 bytes, and accumulating thousands of changes within a tick doesn't create memory pressure.

### flushUpdates: Batch Send Selection

`flushUpdates()` determines whether to send `BlockUpdateS2CPacket` or `ChunkDeltaUpdateS2CPacket` by section change count:

```java
public void flushUpdates(WorldChunk chunk) {
    if (this.pendingBlockUpdates) {
        ServerWorld world = (ServerWorld) chunk.getWorld();
        List<ServerPlayerEntity> list2 = this.getPlayersWatchingChunk(this.pos, false);
        for (int i = this.levelHeightAccessor.getBottomSectionCoord(); i < this.levelHeightAccessor.getTopSectionCoord(); ++i) {
            ShortSet shortSet = this.blockUpdatesBySection[i];
            if (shortSet != null) {
                this.blockUpdatesBySection[i] = null;
                if (!list2.isEmpty()) {
                    int j = this.levelHeightAccessor.sectionCoordToIndex(i);
                    ChunkSectionPos chunkSectionPos = ChunkSectionPos.from(this.pos, j);
                    if (shortSet.size() == 1) {
                        BlockPos blockPos = chunkSectionPos.unpackBlockPos(shortSet.iterator().nextShort());
                        BlockState blockState = world.getBlockState(blockPos);
                        this.sendPacketToPlayers(list2, new BlockUpdateS2CPacket(blockPos, blockState));
                        this.tryUpdateBlockEntityAt(list2, world, blockPos, blockState);
                    } else {
                        ChunkSection chunkSection = chunk.getSection(i);
                        ChunkDeltaUpdateS2CPacket chunkDeltaUpdateS2CPacket = new ChunkDeltaUpdateS2CPacket(chunkSectionPos, shortSet, chunkSection);
                        this.sendPacketToPlayers(list2, chunkDeltaUpdateS2CPacket);
                        chunkDeltaUpdateS2CPacket.visitUpdates((pos, state) -> this.tryUpdateBlockEntityAt(list2, world, pos, state));
                    }
                }
            }
        }
    }

    this.pendingBlockUpdates = false;
}
```

`list2` uses `getPlayersWatchingChunk(this.pos, false)`, all players watching this chunk. Each non-empty sub-chunk is judged separately: if `shortSet.size() == 1`, send `BlockUpdateS2CPacket`; if multiple positions changed in the same sub-chunk, send `ChunkDeltaUpdateS2CPacket`. Both paths check block entities: the single-block path directly calls `tryUpdateBlockEntityAt()`, the delta path iterates each changed position via `visitUpdates()`.

This design separates "change recording" and "network sending": block changes only do lightweight recording when they occur, and when actually sending packets, choose the most appropriate packet based on observers, sub-chunks, and change count.
