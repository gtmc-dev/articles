按下 `F3 + G` 后，地面上会出现彩色网格。这些网格每条线间隔 16 格，展示的就是**区块边界**。

但要理解区块管理系统，仅仅知道"16×16 的格子"远远不够。让我们从底层开始。

## 区块与子区块的定义

### 区块的数学定义

区块是 Minecraft 中一个数据存储与加载单元。严格来说，一个区块对应区域：

$$\{(x, y, z) \mid 16m \le x < 16(m+1),\; 16n \le z < 16(n+1),\; m, n \in \mathbb{Z}\}$$

这意味着：

- 区块在**水平方向**固定为 16×16，边界坐标为 16 的整倍数；
- 区块在**竖直方向**没有上限——它覆盖所在维度的**完整可用高度**。主世界从 Y=`-64` 到 Y=`319` 的同一列 384 个方块，全都属于同一个区块；
- 区块只有 X、Z 坐标，没有单独的 Y 坐标。

### 区块坐标换算

换算规则严格由三个位运算定义：

```text
区块 X  = 方块 X >> 4    （算术右移 4 位 = 向下取整除以 16）
区块 Z  = 方块 Z >> 4
区块内 X = 方块 X & 15   （取低 4 位 = 除以 16 的余数）
区块内 Z = 方块 Z & 15
```

反算同样严格：

```text
区块起始方块 X = 区块 X << 4
区块最东侧方块 X = 区块起始方块 X + 15
```

> [!IMPORTANT]
> 负坐标的区块归属容易算错。`>>` 是算术右移（向下取整），所以 `-1 >> 4 = -1`、`-16 >> 4 = -1`、`-17 >> 4 = -2`。方块 X=`-1` 不在区块 0，而在区块 **-1** 的最东侧（区块内 X=15）。记忆方法：**负坐标向 -∞ 方向取整**。

### 子区块

区块本身很高，但游戏不需要每次都遍历整根竖直柱体。它继续沿 Y 方向把区块切成 **16×16×16** 的**子区块**（Chunk Section）。每个子区块恰好包含 `16³ = 4096` 个坐标。

换算规则与区块坐标**完全同构**：

```text
子区块 Y  = 方块 Y >> 4
子区块内 Y = 方块 Y & 15
```

`Chunk` 根据维度高度创建一个 `ChunkSection[]` 数组。主世界高度 384 格，所以一个完整的主世界区块拥有 `384 / 16 = 24` 个子区块。

**子区块坐标 ≠ 数组下标**。以主世界为例：

- 最底部子区块坐标：`-64 >> 4 = -4`
- 数组下标 0 对应子区块坐标 -4
- `sectionArray[23]` 对应子区块坐标 `-4 + 23 = 19`（覆盖 Y=`304` 至 Y=`319`）

转换公式：`数组下标 = 子区块坐标 - 最底部子区块坐标`

### 局部坐标的打包压缩

游戏频繁需要在一个 16³ 的子区块中表示"第几行第几列第几层"的局部坐标。`ChunkSectionPos` 提供了将三个 0~15 的整数打包为一个 `short` 的方法：

```java
// 打包：x(4bit) | z(4bit) | y(4bit) → 总共 12 bit 有效
short packed = (short)(x << 8 | z << 4 | y);
```

打包成 16 位的 `short` 而非 32 位的 `int`，是为了在大量存储时节省内存——`ChunkHolder` 中使用 `ShortSet[]` 按子区块存储发生变更的方块位置。

### 子区块计数器

每个 `ChunkSection` 维护三项计数器：

| 计数器 | 含义 |
|---|---|
| `nonEmptyBlockCount` | 非空气方块数量 |
| `randomTickableBlockCount` | 需要随机刻的方块数量 |
| `nonEmptyFluidCount` | 非空流体方块数量 |

这些计数器在 `setBlockState()` 中同步更新。它们有两个作用：

1. **快速跳空**：`isEmpty()` 返回 `nonEmptyBlockCount == 0`，完全为空的子区块可以直接跳过后续处理（如区块刻、保存）。
2. **随机刻筛选**：`hasRandomBlockTicks()` 返回 `randomTickableBlockCount > 0`，服务端的随机刻循环只处理此计数器为正的子区块。

## `Chunk`：区块的公共底座

`Chunk` 是所有区块对象的抽象基类。它定义了每个区块共有的数据结构和访问方式：

| 数据类别 | 存储字段 | 类型 |
|---|---|---|
| 子区块 | `sectionArray` | `ChunkSection[]` |
| 高度图 | `heightmaps` | `Map<Heightmap.Type, Heightmap>`（四种：MOTION_BLOCKING、MOTION_BLOCKING_NO_LEAVES、OCEAN_FLOOR、WORLD_SURFACE） |
| 方块实体（已加载） | `blockEntities` | `Map<BlockPos, BlockEntity>` |
| 方块实体（待加载） | `blockEntityNbts` | `Map<BlockPos, NbtCompound>` |
| 结构起点 | `structureStarts` | `Map<Structure, StructureStart>` |
| 结构引用 | `structureReferences` | `Map<Structure, LongSet>` |
| 生物群系 | 每个 `ChunkSection` 内部 | `PalettedContainer<RegistryEntry<Biome>>`（4³ 分辨率） |
| 已居住时间 | `inhabitedTime` | `long` |
| 升级数据 | `upgradeData` | `UpgradeData` |
| 是否需要保存 | `needsSaving` | `volatile boolean` |

> [!IMPORTANT]
> 方块状态使用 `PalettedContainer<BlockState>` 存储，采用**调色板 + 紧凑数据**方案。它不会为 4096 个坐标各存一份完整方块名称和属性，而是用一个调色板记录"这个子区块里出现了哪些状态"，再用紧凑的位宽编码每个位置引用调色板中的第几项。空气为主或方块单一的区块因此可以大大节省空间。

## ProtoChunk 与 WorldChunk

区块在代码中有两种主要实现，对应生命周期中的两个阶段：

| | `ProtoChunk` | `WorldChunk` |
|---|---|---|
| **用途** | 世界生成 | 正常运行 |
| **数据来源** | 生成管线逐步填充 | 从 `ProtoChunk` 转换 或 从磁盘加载 |
| **能否参与 tick** | ❌ | ✅ |
| **能否正常查询** | ❌（生成完成后才转为 `WorldChunk`） | ✅ |
| **有无 levelTypeProvider** | ❌ | ✅（标记当前运行级别） |
| **实体管理** | 不参与 | `ServerEntityManager` 管理 |

**为什么需要 ProtoChunk？** 世界生成是在独立于主线程的生成线程上进行的。如果生成线程直接操作 `WorldChunk`，就可能在主线程同时读写这个区块时造成竞争条件。`ProtoChunk` 提供了一个隔离的"生成沙盒"——只有生成完成的区块才能通过 `convertToFullChunk()` 转换为 `WorldChunk`，正式进入服务端的运行逻辑。

`WorldChunk` 在构造时挂载了一个 **`levelTypeProvider`**（一个 `Supplier<ChunkLevelType>`），它直接从 `ChunkHolder` 查询当前区块的运行级别。这样，任何需要检查"这个区块是否应该执行 XX 运算"的代码，都可以通过 `WorldChunk.getLevelType()` 直接获取。

## 客户端区块管线

客户端和服务端对区块的管理是两个完全独立的体系。理解这一点是区分"看得见"和"在运算"的关键。

### 客户端视角

客户端的区块数据**完全来自服务端同步**。流程为：

1. **服务端决定发送**：当区块进入玩家视距（由 `NearbyChunkTicketUpdater` 控制）时，服务端通过 `ThreadedAnvilChunkStorage.sendWatchPackets()` 判断是否需要向该玩家发送区块数据。
2. **`ChunkDataS2CPacket`**：包含该区块内所有非空子区块的方块状态、生物群系、方块实体和光照数据。
3. **客户端接收与重建**：客户端解析数据包，在自己的 `ClientWorld` 中构建对应的 `WorldChunk`（客户端自己的版本），用于渲染和本地预测。

### 服务端视角

服务端的 `WorldChunk` 是**权威数据**。它的加载由加载票系统驱动——即使客户端已经收到了 `ChunkDataS2CPacket` 并完成了渲染，服务端的 `ChunkHolder` 可能仍在通过 `CompletableFuture` 异步地推进区块的生成状态。

### "看得见 ≠ 在运算"的本质

客户端渲染依赖的是服务端发送的区块数据快照，而服务端的方块运算依赖的是 `ChunkLevelType` 达到 `BLOCK_TICKING`。两者的决定机制不同：

- **客户端渲染**：由 `DistanceFromNearestPlayerTracker` 控制，基于视距（view distance）；
- **方块运算**：由 `SimulationDistanceLevelPropagator` 控制，基于模拟距离（simulation distance）。

当模拟距离小于视距时，玩家**看得见**远方的地形，但那里的红石装置已经**不再运算**。

## 小结

- 区块的数学定义为水平 16×16、覆盖维度完整高度的竖直区域，边界为 16 的整倍数。
- 区块坐标由 `>> 4`（向下取整）计算，负坐标向 -∞ 取整；区块内坐标由 `& 15` 取低 4 位。
- 子区块是 `16³` 的立方体，子区块坐标与 `ChunkSection[]` 下标差值为 `-bottomSectionCoord`。
- 局部坐标被打包为 `short` 节省内存；子区块计数器用于快速跳空和随机刻筛选。
- `Chunk` 是抽象基类，包含子区块数组、高度图、方块实体、结构信息和元数据。
- `ProtoChunk` 是生成隔离沙盒，`WorldChunk` 是正常运行的区块实现，后者挂载了 `levelTypeProvider` 来查询运行级别。
- 客户端区块数据来自服务端的 `ChunkDataS2CPacket` 同步；客户端渲染和服务端运算是两套独立的决定机制。

## [!ADVANCED] 源码验证

### 局部坐标打包

`ChunkSectionPos.packLocal()` 将三个 0~15 的坐标打包为 `short`：

```java
// ChunkSectionPos.java
public static short packLocal(BlockPos pos) {
    int i = getLocalCoord(pos.getX());  // 0~15
    int j = getLocalCoord(pos.getY());
    int k = getLocalCoord(pos.getZ());
    return (short)(i << 8 | k << 4 | j << 0);  // x 在高 4 bit, z 在中 4 bit, y 在低 4 bit
}

public static int unpackLocalX(short packedLocalPos) {
    return packedLocalPos >>> 8 & 15;
}

public static int unpackLocalY(short packedLocalPos) {
    return packedLocalPos >>> 0 & 15;
}

public static int unpackLocalZ(short packedLocalPos) {
    return packedLocalPos >>> 4 & 15;
}
```

注意位布局：`x(bit 8-11) | z(bit 4-7) | y(bit 0-3)`。总计 12 bit 有效，但为了内存对齐用 `short`（16 bit）。`ChunkHolder` 使用 `ShortSet[]` 按子区块存储变更的方块位置，每项就是一个 `packLocal` 后的 `short`。

### ProtoChunk 继承链

```java
// ProtoChunk.java
public class ProtoChunk extends Chunk {
    // 生成用的临时区块，不参与 tick
    // 在 FULL 阶段通过 convertToFullChunk() 转换为 WorldChunk
}

// WorldChunk.java
public class WorldChunk extends Chunk {
    private Supplier<ChunkLevelType> levelTypeProvider;

    public ChunkLevelType getLevelType() {
        return this.levelTypeProvider == null
            ? ChunkLevelType.FULL : this.levelTypeProvider.get();
    }

    public void setLevelTypeProvider(Supplier<ChunkLevelType> levelTypeProvider) {
        this.levelTypeProvider = levelTypeProvider;
    }
}
```

`ProtoChunk` 和 `WorldChunk` 都继承 `Chunk`，共享 `sectionArray`、`heightmaps`、`blockEntities` 等字段。区别在于 `WorldChunk` 额外挂载了 `levelTypeProvider`——它从 `ChunkHolder` 获取当前运行级别（在 `ThreadedAnvilChunkStorage` 的 744 行附近设置）。

### 子区块计数器

`ChunkSection` 的 `setBlockState` 中同步更新三项计数：

```java
// ChunkSection.java
private short nonEmptyBlockCount;
private short randomTickableBlockCount;
private short nonEmptyFluidCount;

public BlockState setBlockState(int x, int y, int z, BlockState state, boolean lock) {
    BlockState blockState = lock
        ? this.blockStateContainer.swap(x, y, z, state)
        : this.blockStateContainer.swapUnsafe(x, y, z, state);

    FluidState fluidState = blockState.getFluidState();
    FluidState fluidState2 = state.getFluidState();
    if (!blockState.isAir()) { this.nonEmptyBlockCount--;
        if (blockState.hasRandomTicks()) { this.randomTickableBlockCount--; } }
    if (!fluidState.isEmpty()) { this.nonEmptyFluidCount--; }
    if (!state.isAir()) { this.nonEmptyBlockCount++;
        if (state.hasRandomTicks()) { this.randomTickableBlockCount++; } }
    if (!fluidState2.isEmpty()) { this.nonEmptyFluidCount++; }
    return blockState;
}
```

### TACS 核心表结构

以下字段直接位于 `ThreadedAnvilChunkStorage` 中：

```java
// ThreadedAnvilChunkStorage.java
private final Long2ObjectLinkedOpenHashMap<ChunkHolder> currentChunkHolders
    = new Long2ObjectLinkedOpenHashMap<>();                              // 所有持有 ChunkHolder 的区块
private volatile Long2ObjectLinkedOpenHashMap<ChunkHolder> chunkHolders
    = this.currentChunkHolders.clone();                                 // currentChunkHolders 的快照
private final Long2ObjectLinkedOpenHashMap<ChunkHolder> chunksToUnload
    = new Long2ObjectLinkedOpenHashMap<>();                             // 待卸载的区块
private final LongSet loadedChunks = new LongOpenHashSet();             // 已完全加载的区块
final LongSet unloadedChunks = new LongOpenHashSet();                   // 从可访问退出后标记为可卸载
```

注意 `chunkHolders` 是 `currentChunkHolders` 的 volatile 克隆快照，用于在迭代时避免并发修改。lovexyn0827 原文提到的"chunkHolders"在较早版本中可能指代不同字段，1.20.1 中已明确为上述结构。
