上一章我们了解了 `ChunkStatus`——它回答的是"这个区块生成了多少"。

但 Minecraft 中还有另一个维度的问题："这个区块现在**在做什么**？"——它是否允许被普通代码访问？是否在运行方块刻？实体是否在移动？

这两个问题由两套不同的系统回答。

## ChunkStatus ≠ 区块热度

这是一个必须首先澄清的常见混淆：

| | ChunkStatus | ChunkLevel / ChunkLevelType |
|---|---|---|
| **回答的问题** | "这个区块的生成进度如何？" | "这个区块现在允许做哪些运算？" |
| **决定因素** | 生成管线各阶段是否完成 | 加载票系统计算出的加载等级 |
| **变化时机** | 生成推进（通常不可逆） | 加载票增减（动态升降） |
| **典型值** | `EMPTY`, `BIOMES`, ..., `FULL` | `ENTITY_TICKING`, `BLOCK_TICKING`, `FULL`, `INACCESSIBLE` |

一句话总结：**ChunkStatus 管"生成了多少"，ChunkLevelType 管"现在能干什么"。**

一个区块完全可以在 `ChunkStatus = FULL`（生成完毕）的状态下，同时处于 `ChunkLevelType = INACCESSIBLE`（不可访问）——这就是"远处地形已生成，但没有在运算"的精确源码解释。

## 加载等级（ChunkLevel）

加载等级是一个**整数**，决定区块的加载或生成状态。关键规则：

- 取值范围为 44 及以下（通常不低于 11）；
- **数值越低，区块被加载得越"彻底"**；
- 加载等级与加载距离的关系为：`加载等级 = 33 - 加载距离`。

例如，一张 `radius = 2` 的票，其中心区块的加载等级为 `33 - 2 = 31`（强加载），向外每走一格切比雪夫距离，加载等级 +1。

> [!IMPORTANT]
> 加载等级的上限为 **44**。`INACCESSIBLE = 33 + ChunkStatus.getMaxDistanceFromFull()`。在 1.20.1 中 `getMaxDistanceFromFull()` 返回 11，所以 `INACCESSIBLE = 33 + 11 = 44`。即不可访问区块的最高加载等级为 44。

## ChunkLevelType：四种运行资格

`ChunkLevels.getType(level)` 将加载等级映射为四种 **`ChunkLevelType`**：

```java
// 判定规则
public static ChunkLevelType getType(int level) {
    if (level <= 31) return ChunkLevelType.ENTITY_TICKING;    // 强加载
    else if (level <= 32) return ChunkLevelType.BLOCK_TICKING; // 弱加载
    else return level <= 33 ? ChunkLevelType.FULL : ChunkLevelType.INACCESSIBLE;
}
```

四种类型的精确含义：

| ChunkLevelType | 对应加载等级 | 方块状态可访问 | 方块刻/红石运算 | 实体运算 | 刷怪 | 客户端渲染 |
|---|---|---|---|---|---|---|
| `ENTITY_TICKING` | ≤ 31 | ✅ | ✅ | ✅ | ✅ | ✅ |
| `BLOCK_TICKING` | 32 | ✅ | ✅ | ❌ | ❌ | ✅ |
| `FULL` | 33 | ✅ | ❌ | ❌ | ❌ | ❌ |
| `INACCESSIBLE` | ≥ 34 | ❌ | ❌ | ❌ | ❌ | ❌ |

逐一说明：

### ENTITY_TICKING（强加载，≤31）

**最完整的运行态**。区块内几乎所有运算逻辑都正常进行——方块刻（包括红石运算和随机刻）、实体 AI 与移动、刷怪判定、方块实体更新。通常所说的"玩家周围的区块"就处于此状态。

### BLOCK_TICKING（弱加载，32）

与强加载的**唯一区别是实体的运算被暂停**。红石装置、流体、计划刻等仍正常运行。`World#setBlockState` 中可以看到，只有当前区块达到 `BLOCK_TICKING` 级别，服务端才会触发客户端同步。弱加载区块在客户端仍然会被渲染。

### FULL（边界加载，33）

区块数据**在内存中可供读写**，但几乎不执行任何主动运算。方块状态可以查询、实体可以记录（计入刷怪上限），但不会有方块刻、红石运算或实体移动。客户端不会渲染此级别的区块。

### INACCESSIBLE（不可访问，≥34）

区块**在正常的运算逻辑中不可见**。这意味着：
- 调用 `World.getBlockState()` 查询此区块会失败（可能返回空气或默认状态）；
- `World.setBlockState()` 不会对不可访问区块生效；
- 实体运算和方块刻都不会在此运行。

但它**可能在进行世界生成**——这正是 `ChunkStatus` 与 `ChunkLevelType` 分离的体现：一个 `INACCESSIBLE` 的区块可能正在后台生成，只是还没有资格参与游戏逻辑。

> [!NOTE] "方块刻"与"计划刻"的区别
> **方块刻**（Block Tick）是一个宏观概念，指 `BLOCK_TICKING` 级别下所有的方块运算，它包括：
> - **计划刻**（Scheduled Tick）——由 `WorldTickScheduler` 管理的具体预约机制，方块通过 `world.scheduleTick()` 预约在未来某一时刻执行运算；
> - **随机刻**（Random Tick）——每随机刻对选中方块执行的周期性运算；
> - **方块实体刻**（Block Entity Tick）——对 `BlockEntity` 实例执行的 tick 运算。
>
> 换言之，计划刻是方块刻的子集，是一种具体的、预约式的执行机制。有关计划刻的详细运作方式，请参见 [MicroTiming：计划刻与计划刻元件](../../MicroTiming/计划刻与计划刻元件.zh.md)。

## 何时可访问、何时方块刻、何时实体刻

三种资格的判定在源码中有各自的明确入口：

- **可访问性**：`ChunkLevels.isAccessible(level)` → 检查 `level <= INACCESSIBLE`
- **方块刻权限**：`ChunkLevels.shouldTickBlocks(level)` → 检查 `level <= 32`
- **实体刻权限**：`ChunkLevels.shouldTickEntities(level)` → 检查 `level <= 31`

服务端在 `ServerWorld.tick()` 中遍历区块时，大量使用这些检查来决定"这个区块当前刻要不要处理"。

## "生成完成但不再运算"是怎么发生的

这是实际游戏中最常见的现象。完整流程：

1. 玩家站在区块 A，区块 A 的加载票使其达到 `ENTITY_TICKING`（level ≤ 31），一切正常。
2. 玩家走远，`NearbyChunkTicketUpdater` 检测到区块 A 到玩家的距离超出视距，移除 A 上的 PLAYER 加载票。
3. `TicketDistanceLevelPropagator` 重新计算 A 的加载等级。若有其他票撑着，level 可能回升到 32 或 33；若没有，level 最终变为 `INACCESSIBLE + 1`（≥ 34）。
4. `ChunkHolder.tick()` 检测到 `ChunkLevelType` 降级，将 `entityTickingFuture` 或 `tickingFuture` complete 为 `UNLOADED`，相应的运算停止。
5. 如果 level 退出了 `FULL`（≥ 34），`ThreadedAnvilChunkStorage` 会将 `ChunkHolder` 标记为可卸载，`needsSaving` 为 `true` 的区块在卸载前被保存到磁盘。

关键洞察：**"生成完成"由 ChunkStatus=FULL 标记，但"是否在运算"由 ChunkLevelType 标记。两者独立变化。**

## 常见误区

| 误区 | 事实 |
|---|---|
| "客户端看得见 = 服务端正在 tick" | 客户端渲染由视距（view distance）控制，服务端 tick 由模拟距离（simulation distance）控制。两者是独立的参数。 |
| "FULL = 会随机刻" | `FULL` 只保证数据可访问，随机刻需要 `BLOCK_TICKING`（level ≤ 32）。 |
| "被加载 = 会刷怪" | 刷怪需要 `ENTITY_TICKING`（level ≤ 31）。 |
| "玩家附近 = 一定刷怪" | 刷怪还需要满足光照、空间、刷怪上限等额外条件。`ENTITY_TICKING` 是必要条件，非充分条件。 |
| "强制加载 = 万物都会运作" | `/forceload` 通过 `FORCED` 票实现 `ENTITY_TICKING`，但具体运算仍受 gamerule、区块状态等约束。 |

## 小结

- `ChunkStatus` 管"生成进度"，`ChunkLevelType` 管"运行资格"——两者回答不同的问题。
- 四种运行资格按 level 逐层递进：`INACCESSIBLE` → `FULL` → `BLOCK_TICKING` → `ENTITY_TICKING`。
- 强加载（≤31）一切运算正常，弱加载（32）暂停实体，边界加载（33）仅供查询，不可访问（≥34）对外不可见。
- 生成完成但不再运算的本质：`ChunkStatus = FULL` 而 `ChunkLevelType != ENTITY_TICKING`。

## [!ADVANCED] 代码走读

### ChunkLevels 阈值设计：为什么是 31/32/33？

```java
// ChunkLevels.java
private static final int ENTITY_TICKING = 31;
private static final int BLOCK_TICKING = 32;
private static final int FULL = 33;
public static final int INACCESSIBLE = 33 + ChunkStatus.getMaxDistanceFromFull(); // = 44

public static ChunkLevelType getType(int level) {
    if (level <= 31)      return ChunkLevelType.ENTITY_TICKING;
    else if (level <= 32) return ChunkLevelType.BLOCK_TICKING;
    else                  return level <= 33
        ? ChunkLevelType.FULL : ChunkLevelType.INACCESSIBLE;
}
```

这三个阈值不是随意选的。它们的设计基于加载票的传播模型：加载票的 `level = 33 - radius`，向外每走一区块 level+1。因此：

- `radius ≥ 2` → level ≤ 31：玩家脚下 2 格切比雪夫距离以内的区块，**实体和方块全部运行**。这是最核心的游戏体验区域——玩家能直接看到的生物、红石装置、水流都在此范围内。
- `radius = 1` → level = 32：向外一圈。**方块还在运行**（红石、流体、计划刻），但实体暂停。这一圈的设计意图是保留"视觉上的连续性"——远处的水还在流、红石灯还在亮——但节省实体运算的 CPU 开销。
- `radius = 0` → level = 33：最外一圈的"边界层"。数据在内存中，但**不做任何主动运算**。这一层的存在是为了保证当玩家移动时，新进入强加载范围的区块不需要重新生成——它们已经以 FULL 状态在内存中准备好了。

**为什么 `BLOCK_TICKING` 是 32 而不是别的值？** 注意 32 = 33 - 1。它恰好对应 `radius=1`——即玩家周围切比雪夫距离为 1 的区块。如果设为 31，则 `radius=1` 的区块也必须达到强加载，这意味着玩家脚下 5×5 区域内的所有实体都在运动——成本太高。如果设为 33，则 `radius=1` 的区块和 `radius=0` 没有区别——远处的水不会流动，视觉效果断裂。

### isAfter()：为什么用 ordinal 而不是直接比较 level？

```java
// ChunkLevelType.java
public enum ChunkLevelType {
    INACCESSIBLE,    // ordinal = 0
    FULL,            // ordinal = 1
    BLOCK_TICKING,   // ordinal = 2
    ENTITY_TICKING;  // ordinal = 3

    public boolean isAfter(ChunkLevelType other) {
        return this.ordinal() >= other.ordinal();
    }
}
```

`isAfter` 的语义是"当前级别**至少达到了**参数级别的要求"。因为声明顺序是递进的（INACCESSIBLE → FULL → BLOCK_TICKING → ENTITY_TICKING），`ordinal()` 直接反映了"运算能力的强弱"。

这里有一个容易混淆的点：`isAfter` **不是**比较 "level 数值的大小"（那个在 `ChunkLevels` 里已经做了），而是比较 "运算资格的包含关系"。`ENTITY_TICKING.isAfter(BLOCK_TICKING)` 为 true，因为强加载区块自动满足弱加载的所有条件。`FULL.isAfter(BLOCK_TICKING)` 为 false，因为"只能读取"不满足"必须运行方块刻"的要求。

### 降级时为何用 UNLOADED 填充而非 null

ChunkHolder 降级时，需要清空不再需要的生成状态 Future：

```java
// ChunkHolder.tick()
if (bl) {  // 旧等级可访问
    Either<Chunk, Unloaded> either = Either.right(new Unloaded() { ... });
    for (int i = bl2 ? chunkStatus2.getIndex() + 1 : 0;
         i <= chunkStatus.getIndex(); i++) {
        if (this.futuresByStatus.get(i) == null) {
            this.futuresByStatus.set(i,
                CompletableFuture.completedFuture(either));
        }
    }
}
```

循环从 `0` 到 `旧ChunkStatus.index`：如果降级后仍可访问（`bl2=true`），则保留新等级对应状态及以上的 Future（从 `新ChunkStatus.index + 1` 开始清）；如果降级后不可访问（`bl2=false`），则从 `0` 开始全部清空。

**为什么用 `CompletableFuture.completedFuture(either)` 而不是 `set(i, null)`？** 因为外部代码可能已经通过 `getFutureFor(someStatus)` 获取了这个 Future 并注册了回调（`.thenAccept()`）。如果直接设为 `null`，那些回调会永远等不到结果，导致内存泄漏。设为一个已完成（值为 `Unloaded`）的 Future，让所有等待者立即收到"不可用"的通知并清理回调——这是 `CompletableFuture` 的**优雅终止模式**。

注意 `futuresByStatus` 用的是 `AtomicReferenceArray` 而非普通数组——因为生成线程和主线程可能同时访问它。`AtomicReferenceArray` 提供了无锁的并发安全保证，代价是每个元素多一个 CAS 操作的开销。
