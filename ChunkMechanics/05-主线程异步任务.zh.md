> 源自 lovexyn0827《1.14+区块管理系统及其动态分析》第四章（CC0 协议），有改编。

如果你读到本章时已经对前几章的架构有了理解，你可能会问："`ChunkTicketManager.tick()` 更新了加载等级，通知了 `ChunkHolder`，那区块到底什么时候被真正加载？"

答案是：**不是"立刻"，而是"在未来的某个异步任务中被执行"**。

## CompletableFuture 的核心作用

在区块管理系统中，`CompletableFuture` 是贯穿始终的异步协调工具。它的两个角色：

### 角色一：任务的计划与执行

一个 `CompletableFuture` 对应一个基本任务——更新玩家加载票、加载一个区块、完成一个区块的一个生成阶段。任务不是直接被运行的，而是作为一个 `CompletableFuture` 被**计划**（scheduled），然后在之后的某处运算中才被**执行**。

这种"计划-执行"的分离意味着：你可能在一个 gt 的开始添加了一个任务，但它要到好几个 gt 之后的异步任务执行阶段才真正运行。

### 角色二：区块可用性的标识

在 `ChunkHolder` 中，三个 `CompletableFuture` 充当了区块不同"视图"的可用性标识：

- `accessibleFuture`：区块数据可访问时 complete
- `tickingFuture`：区块可以参与方块刻时 complete
- `entityTickingFuture`：区块可以参与实体运算时 complete

当一个区块不再满足某个级别要求时，对应的 Future 被 `complete(UNLOADED_WORLD_CHUNK)`，任何依赖该视图的操作都会收到一个"不可用"的结果。

## 任务队列：MainThreadExecutor

异步任务由 `ServerChunkManager.MainThreadExecutor` 管理。它的本质是一个**先入先出（FIFO）**的任务队列，保证所有任务均在服务端主线程上执行。

每件进入队列的任务最终会在主线程上被取出并执行，但取出的时机是不固定的——参见下一节。

## 执行时机

可能引起异步任务执行的位置分散在代码的各个角落。主要分为三大类：

### 第一类：区块保存时的阻塞性执行

由暂停、退出、自动保存或 `/save-all` 指令触发的区块保存中，保存单个区块时需要确保该区块的数据已经就绪。此时，相关的异步任务会被**阻塞性地立即执行**——不执行完就无法继续保存。

### 第二类：getChunk() 触发的需求性执行

这是最常见也最隐蔽的一类。当外部代码通过 `ServerChunkManager.getChunk()` 获取一个区块时：

1. 一个"获取此区块"的任务 T 被添加到异步任务队列；
2. 队列中的任务按 FIFO 顺序被执行，**直到 T 执行完成**；
3. T 完成后，任务执行**立即停止**——队列中排在 T 后面的任务**不会被在此处执行**。

这意味着：如果在你调用 `getChunk()` 之前，队列中已经排了 50 个其他任务，这 50 个任务会在你的 T 之前被执行完毕。反之，排在 T 之后的任务就只能等待下一个执行时机。

可能触发 `getChunk()` 的位置至少有**数百个**——包括（但不限于）：

- 使用 `World.getBlockState()` / `setBlockState()` 时
- 使用 `World.getBlockEntity()` / `setBlockEntity()` 时
- 使用 `World.getFluid()` 时
- 玩家重生、进入维度、加入维度时
- 获取区域难度时
- 折跃门传送实体时

> 获取一个区域内的实体的操作一般不会引起相关区块的加载——实体查询和方块查询在源码中是两套独立的机制。

### 第三类：游戏刻末尾的兜底执行

服务端每个游戏刻末尾有一个异步任务运算阶段。在这个阶段：

- 如果不掉刻（当前 gt 运行 ≤ 50ms），任务执行可以一直进行到**所有维度**的任务队列被清空；
- 如果掉刻，任务执行会立刻终止，剩余任务留到下一 gt 处理；
- 执行过程中产生的新任务也会在这个阶段内被继续执行。

执行的顺序固定为：

1. 服务端本身的异步任务（如处理来自客户端的操作）
2. 主世界的 `ServerChunkManager` 异步任务
3. 其他维度的 `ServerChunkManager` 异步任务（下界先于末地）

## 动态理解

三类执行时机的设计意图可以这样理解：

- **第一类**是为了完成一个必须立刻完成的阻塞性任务（"如果不保存这个区块，服务端就不能安全关闭"）；
- **第二类**是为了完成一个调用者必须立刻得到的任务（"`getBlockState()` 如果不返回真实状态，后续逻辑就没法进行"）；
- **第三类**是兜底机制——保证正常情况下本 gt 产生的所有异步任务都能在本 gt 内被处理。

但正因为执行时机分散在数百个调用点中，**同一维度的异步任务队列可以在任意位置被部分执行**——这导致了区块加载的时机在动态上高度不可预测。这也是 lovexyn0827 原文中提到的"这一部分真的写的非常奥利给"的原因。

## TaskExecutor —— Mailbox 架构

前面提到的"异步任务队列"，在更底层并不是一个裸露的 `Queue<Runnable>`。Minecraft 把它包装成了 `net.minecraft.util.thread.TaskExecutor<T>`：一个实现了 `MessageListener<T>`、`Runnable`、`AutoCloseable` 的执行器。

它的结构可以拆成三个核心组件：

- **消息队列**：`TaskQueue` 负责抽象队列行为，默认工厂会落到 `ConcurrentLinkedQueue`；
- **线程池 Executor**：真正运行任务的底层线程池，由服务器传入；
- **状态标志**：`AtomicInteger stateFlags` 记录 mailbox 是否正在运行、是否已经关闭。

```java
// TaskExecutor.java line 16
public class TaskExecutor<T> implements SampleableExecutor, MessageListener<T>, AutoCloseable, Runnable {
    private final AtomicInteger stateFlags = new AtomicInteger(0);  // line 20
    private final TaskQueue<? super T, ? extends Runnable> queue;   // line 21
    private final Executor executor;                                // line 22
}
```

`TaskExecutor` 的状态机很小，但很关键：`unpause()` 通过 CAS 设置 bit1=1，让 mailbox 进入 running 状态；`pause()` 清除 bit1=1，让它退出 running 状态；`close()` 设置 bit0=1，表示永久关闭。也就是说，running 是临时状态，closed 是不可逆状态。

一次 `send(message)` 的完整路径是：

1. `queue.add(message)` 把消息放进队列；
2. `execute()` 尝试触发执行；
3. 如果 `hasMessages() && unpause()` 成功，就调用 `executor.execute(this)`；
4. 线程池随后调用这个 `TaskExecutor` 自己的 `run()`；
5. `run()` 内部通过 `runWhile()` 循环消费队列中的消息。

```java
// TaskExecutor.java lines 105-122
public void send(T message) {
    this.queue.add(message);
    this.execute();
}

private void execute() {
    if (this.hasMessages() && this.unpause()) {
        this.executor.execute(this);
    }
}
```

`runWhile(condition)` 每次只从队列里取一条消息并执行，执行完就递增计数；当条件返回 `false`，或者队列已经为空，循环就停止。`TaskExecutor.create(executor, name)` 则是常用工厂方法：它用 `ConcurrentLinkedQueue` 创建新的 mailbox，再绑定到传入的线程池。

> [!IMPORTANT]
> `TaskExecutor` 的本质是**单线程 mailbox 模式**：每个 mailbox 绑定到一个线程池，但同一时间只有一条线程能运行它的 `run()`。底层线程池可以有很多工作线程，mailbox 自己仍然保持串行消费。

## 三线程模型

`ThreadedAnvilChunkStorage` 的构造函数里，区块系统一次性创建了三个 actor，并全部注册到 `ChunkTaskPrioritySystem`。这三个 actor 不是三个固定的 Java `Thread` 对象，而是三个独立的消息接收端：worldgen、main、light。

```java
// ThreadedAnvilChunkStorage.java lines 185-196
this.mainThreadExecutor = mainThreadExecutor;
TaskExecutor<Runnable> taskExecutor = TaskExecutor.create(executor, "worldgen");
MessageListener<Runnable> messageListener = MessageListener.create("main", mainThreadExecutor::send);
TaskExecutor<Runnable> taskExecutor2 = TaskExecutor.create(executor, "light");
this.chunkTaskPrioritySystem = new ChunkTaskPrioritySystem(
    ImmutableList.of(taskExecutor, messageListener, taskExecutor2), executor, Integer.MAX_VALUE);
this.worldGenExecutor = this.chunkTaskPrioritySystem.createExecutor(taskExecutor, false);
this.mainExecutor = this.chunkTaskPrioritySystem.createExecutor(messageListener, false);
this.lightingProvider = new ServerLightingProvider(
    chunkProvider, this, this.world.getDimension().hasSkyLight(),
    taskExecutor2, this.chunkTaskPrioritySystem.createExecutor(taskExecutor2, false)
);
```

这段代码建立了三条任务通道：

| Actor | 创建方式 | 类型 | 职责 |
|---|---|---|---|
| worldgen | `TaskExecutor.create(executor, "worldgen")` | TaskExecutor | 世界生成任务（噪声、地物、洞穴、结构） |
| main | `MessageListener.create("main", mainThreadExecutor::send)` | MessageListener | 主线程任务（tick、区块状态变更通知） |
| light | `TaskExecutor.create(executor, "light")` | TaskExecutor | 光照计算与传播 |

worldgen 和 light 之所以用独立的 `TaskExecutor`，是因为它们面对的是 CPU 密集型工作。世界生成要做噪声采样、地物放置、结构生成、洞穴雕刻；光照传播则要在较大范围内遍历光照图，近似一次局部的 BFS/DFS 传播。把这些工作放到主线程里，最直接的结果就是掉刻。

main actor 的职责不同。它不负责重计算，而是执行协调任务：更新 `ChunkHolder` 状态、通知区块变化、安排后续任务、调度需要发给客户端的数据包。这些动作必须回到服务端主线程，因为它们会触碰世界状态和玩家连接状态。

> [!IMPORTANT]
> 这里传入的 `executor` 参数是同一个底层线程池，通常由 `MinecraftServer` 传入。worldgen、light 这两个 `TaskExecutor` 共享同一个 `ForkJoinPool` 或服务器自定义线程池；三线程模型强调的是三个 actor 的职责分离，不是必然创建三条永久专属线程。

## ChunkTaskPrioritySystem —— Actor 模型调度器

有了三个 actor，还需要一个调度中心决定"哪个 actor 的哪个区块任务先执行"。这就是 `net.minecraft.server.world.ChunkTaskPrioritySystem` 的位置：它位于 worldgen、main、light 之上，负责路由、排序和触发执行。

它的核心数据结构是：`Map<MessageListener<?>, LevelPrioritizedQueue<...>> queues`。每个 actor 都对应一个 `LevelPrioritizedQueue`，也就是说，worldgen 有自己的优先级队列，main 有自己的优先级队列，light 也有自己的优先级队列。

```java
// ChunkTaskPrioritySystem.java lines 32-37
public ChunkTaskPrioritySystem(List<MessageListener<?>> actors, Executor executor, int maxQueues) {
    this.queues = actors.stream().collect(Collectors.toMap(
        Function.identity(), actor -> new LevelPrioritizedQueue<>(...)));
    this.idleActors = Sets.newHashSet(actors);
    this.controlActor = new TaskExecutor<>(new TaskQueue.Prioritized(4), executor, "sorter");
}
```

这里还有一个额外 actor：`controlActor`。它是一个名为 `"sorter"` 的 `TaskExecutor<TaskQueue.PrioritizedTask>`，专门用来序列化对 `queues` 的访问。换句话说，真正的三条业务通道是 worldgen、main、light；`sorter` 则是调度器内部的控制通道。

`createExecutor(executor, addBlocker)` 的流程可以这样读：

1. 向 `controlActor` 发送一个 `ask()` 请求；
2. `controlActor` 确保目标 actor 在 `queues` 中有对应的 queue；
3. 返回一个 `MessageListener` 包装器；
4. 外部向这个包装器 `send()` 任务时，包装器调用 `enqueueChunk()`，把任务加入对应 actor 的优先级队列；
5. 随后调用 `enqueueExecution()`，尝试从队列中取出任务并投递给真正的 actor。

```java
// ChunkTaskPrioritySystem.java lines 68-85
public MessageListener<ChunkTaskPrioritySystem.Task<Runnable>> createExecutor(
    MessageListener<Runnable> executor, boolean addBlocker) {

}

// ChunkTaskPrioritySystem.java lines 124-152
private void enqueueChunk(...) {

private void enqueueExecution(MessageListener<?> actor) {

```

`shouldDelayShutdown()` 会检查所有队列是否已经清空，避免服务器在仍有区块任务时过早关闭；`updateLevel()` 则在加载等级变化时重排任务优先级，让靠近玩家、需求更强的任务更早被处理。

> [!IMPORTANT]
> 这就是区块系统里的 actor 模型：每个 actor 独立接收消息，彼此不直接阻塞；`ChunkTaskPrioritySystem` 不替它们做具体工作，只负责把任务按区块优先级路由到正确的 actor。

## MessageListener —— Actor 消息传递

`net.minecraft.util.thread.MessageListener<T>` 是 actor 之间的消息契约。它并不规定消息如何排队、在哪条线程上执行，只规定一件事：一个 actor 必须有名字，并且必须能接收消息。

```java
// MessageListener.java lines 8-11
public interface MessageListener<Msg> extends AutoCloseable {
    String getName();
    void send(Msg message);
}
```

`send(T message)` 是最基础的投递动作。对于 `TaskExecutor` 来说，`send()` 表示"把消息放进 mailbox 队列，然后尝试触发执行"；对于 main actor 来说，`send()` 表示"把消息转交给已有的主线程执行器"。

`MessageListener` 还提供了请求-响应模式：

```java
// MessageListener.java lines 24-29
default <Source> CompletableFuture<Source> ask(
    Function<? super MessageListener<Source>, ? extends Msg> messageProvider) {
    CompletableFuture<Source> future = new CompletableFuture<>();
    Msg object = (Msg)messageProvider.apply(create("ask future procesor handle", future::complete));
    this.send(object);
    return future;
}
```

`ask(Function)` 会先创建一个 `CompletableFuture`，再临时创建一个用于完成 future 的 reply listener，并通过 `send()` 把请求消息投递出去。接收方处理完请求后，只要向这个 reply listener 发送响应，future 就会 complete。`askFallible(Function)` 与它类似，只是响应值可以是 `Either<Source, Exception>`，因此能把异常也作为响应的一部分传回来。

`MessageListener.create(name, action)` 是最轻量的工厂方法：它创建一个匿名 listener，`send()` 时直接调用 `action.accept(message)`。`ThreadedAnvilChunkStorage` 中的 main actor 正是这样来的。

> [!IMPORTANT]
> `TaskExecutor` 实现了 `MessageListener<T>`，所以任何一个 `TaskExecutor` 实例都可以被当作 actor 使用。向它发送消息时，消息不会立刻在调用者线程上执行，而是进入它自己的 mailbox，再由绑定的线程池调度运行。

## light 线程的双阶段执行

前面提到 `ThreadedAnvilChunkStorage` 创建了三个 actor，其中 `TaskExecutor.create(executor, "light")` 负责处理光照计算。但光照任务的实际调度不是简单的"把任务扔进 mailbox"那么直接，而是由 `ServerLightingProvider` 在主线程和 light 线程之间设计了一套**双阶段执行机制**。

### 双线程架构

`ServerLightingProvider` 持有两个关键字段：

```java
// ServerLightingProvider.java lines 29, 32
private final TaskExecutor<Runnable> processor;           // light 线程
private final MessageListener<ChunkTaskPrioritySystem.Task<Runnable>> executor;  // 主线程封装器
```

**processor** 是 TACS 传入的 `TaskExecutor.create(executor, "light")`，代表真正的 light 线程执行器。**executor** 是通过 `ChunkTaskPrioritySystem.createExecutor(processor, false)` 创建的封装器，它会把任务先经过优先级队列再投递到 `processor`。

此外，`ServerLightingProvider` 还维护一个主线程上的任务列表：

```java
// ServerLightingProvider.java line 30
private final ObjectList<Pair<Stage, Runnable>> pendingTasks = new ObjectArrayList<>();
```

这个 `pendingTasks` 不在 light 线程上，也不在优先级队列里，而是在主线程上积累任务。光照任务先进入 `pendingTasks`，当积压达到阈值或每个 tick 到来时，才**成批转移到 light 线程**。

### enqueue() 的完整路径

当代码调用 `ServerLightingProvider.checkBlock(pos)` 时（如方块更新、区块生成触发光照重算），任务不会直接进入 light 线程，而是走这条路径：

```java
// ServerLightingProvider.java lines 127-138
private void enqueue(int x, int z, IntSupplier completedLevelSupplier, Stage stage, Runnable task) {
    this.executor.send(ChunkTaskPrioritySystem.createMessage(() -> {
        this.pendingTasks.add(Pair.of(stage, task));
        if (this.pendingTasks.size() >= 1000) {
            this.runTasks();
        }
    }, ChunkPos.toLong(x, z), completedLevelSupplier));
}
```

完整链路：

1. 调用者在主线程上调用 `checkBlock(pos)` 或其他光照入口
2. `enqueue(x, z, stage, task)` 被调用，包装成 `ChunkTaskPrioritySystem.Task`
3. `executor.send(task)` 通过 `ChunkTaskPrioritySystem` 路由（根据区块的 `completedLevel` 进入优先级队列）
4. 任务最终由 `processor.send()` 投递到 light 线程
5. light 线程执行 `() -> { pendingTasks.add(...); if (size >= 1000) runTasks(); }`

关键设计：`enqueue()` 不直接调用 `processor.send(task)`，而是通过 **executor 封装器**。这样 `ChunkTaskPrioritySystem` 才能基于区块的加载等级调度优先级，避免低优先级区块的光照计算抢占高优先级区块。

### tick() 的原子锁机制

每个游戏刻，`ThreadedAnvilChunkStorage.tick()` 会调用 `lightingProvider.tick()`：

```java
// ServerLightingProvider.java lines 186-193
public void tick() {
    if (this.ticking.compareAndSet(false, true)) {
        this.processor.send(() -> {
            this.runTasks();
            this.ticking.set(false);
        });
    }
}
```

这里的 **ticking** 是 `AtomicBoolean` 原子锁：

```java
// ServerLightingProvider.java line 34
private final AtomicBoolean ticking = new AtomicBoolean();
```

为什么需要这个锁？因为 `tick()` 每个 gt 被调用一次，但上一次的 `runTasks()` 可能还在 light 线程上运行。如果不加锁，多个 `runTasks()` 会同时访问 `pendingTasks`，而 `ObjectArrayList` **不是线程安全容器**，并发访问会导致数据竞争。

`compareAndSet(false, true)` 保证：如果上一次的 `runTasks()` 还没执行完（`ticking` 仍为 `true`），本次 tick 不会投递新任务。只有当上一轮执行完毕，`ticking.set(false)` 释放锁后，下一个 tick 才能投递新的 `runTasks()`。

### runTasks() 的三阶段执行

当 `runTasks()` 在 light 线程上运行时，它不是简单地"依次执行所有任务"，而是分为三个阶段：

```java
// ServerLightingProvider.java lines 195-218 (simplified)
private void runTasks() {
    int i = Math.min(this.pendingTasks.size(), 1000);
    ObjectListIterator<Pair<Stage, Runnable>> objectListIterator = this.pendingTasks.iterator();

    // 阶段 1：PRE_UPDATE
    int j;
    for (j = 0; objectListIterator.hasNext() && j < i; j++) {
        Pair<Stage, Runnable> pair = objectListIterator.next();
        if (pair.getFirst() == Stage.PRE_UPDATE) {
            pair.getSecond().run();
        }
    }

    // 阶段 2：实际光照传播
    objectListIterator.back(j);
    super.doLightUpdates();

    // 阶段 3：POST_UPDATE
    for (int var5 = 0; objectListIterator.hasNext() && var5 < i; var5++) {
        Pair<Stage, Runnable> pair2 = objectListIterator.next();
        if (pair2.getFirst() == Stage.POST_UPDATE) {
            pair2.getSecond().run();
        }
        objectListIterator.remove();
    }
}
```

三个阶段的职责：

- **PRE_UPDATE**：准备工作。典型任务包括 `setRetainData()`, `setColumnEnabled()`, `enqueueSectionData()`，它们标记哪些区块列需要光照重算，哪些区段的光照数据需要加载。
- **super.doLightUpdates()**：调用父类 `LightingProvider.doLightUpdates()` → `ChunkLightProvider.doLightUpdates()`，执行实际的光照传播（BFS/DFS 遍历光源图，计算每个方块的光照值）。
- **POST_UPDATE**：收尾工作。典型任务包括通知 `ChunkHolder` 光照完成、更新客户端数据包、清理临时状态。

为什么要分三阶段？因为光照传播依赖准备阶段设置的状态（哪些区块列启用了光照、哪些区段需要重算），而收尾阶段需要在光照计算完成后才能执行（否则通知客户端时光照数据还没准备好）。

> [!IMPORTANT]
> `Stage` 枚举只有两个值：`PRE_UPDATE` 和 `POST_UPDATE`。没有第三个 stage，因为 `doLightUpdates()` 不是任务，而是中间的同步执行点。

### 批处理触发时机

`runTasks()` 有两种触发方式：

**被动触发（每个 tick）**：`tick()` 每个 gt 调用一次，如果 `ticking` 锁可用，就向 light 线程投递 `runTasks()`。

**主动触发（队列满）**：`enqueue()` 中，当 `pendingTasks.size() >= 1000` 时，立即调用 `runTasks()`，不等下一个 tick。

```java
// ServerLightingProvider.java line 33
private final int taskBatchSize = 1000;
```

批处理上限是 1000，这个阈值平衡了两个目标：

- 如果阈值太小（如 10），每次只处理少量任务，light 线程频繁切换上下文，效率下降。
- 如果阈值太大（如 10000），光照任务积压严重时，客户端可能长时间看不到光照更新。

1000 的设计意味着：当光照任务积压严重时，不等 tick 就能立刻处理，减少延迟；当积压不严重时，由 tick 机制定期清空队列，保证稳定性。

### doLightUpdates() 的覆盖设计

父类 `LightingProvider.doLightUpdates()` 是公开方法，但 `ServerLightingProvider` 覆盖它并抛出异常：

```java
// ServerLightingProvider.java lines 54-56
@Override
public int doLightUpdates() {
    throw new UnsupportedOperationException("Ran automatically on a different thread!");
}
```

为什么要这样设计？因为服务端的光照更新**必须通过 `enqueue()` → light 线程**的路径，不能直接在任意线程上调用 `doLightUpdates()`。这个覆盖强制所有光照任务走异步路径，防止外部代码在主线程上直接调用 `doLightUpdates()` 导致阻塞。

但 `runTasks()` 内部调用的是 `super.doLightUpdates()`——这是调用父类 `LightingProvider` 的原始实现，绕过了子类的异常覆盖。这保证了 light 线程上的实际执行路径仍然可用。

设计意图很明确：外部调用者必须通过异步接口（`checkBlock()`, `tick()`）安排光照任务，不能直接调用 `doLightUpdates()`；但内部 `runTasks()` 作为控制流的合法执行点，可以绕过这个限制。

## 小结

- `CompletableFuture` 在区块管理中扮演双重角色：任务的载体和区块可用性的标识。
- 异步任务由 `MainThreadExecutor` 管理，FIFO 队列，保证在主线程执行。
- 执行时机分为三类：保存时的阻塞执行、`getChunk()` 的需求性执行、gt 末尾的兜底执行。
- 第二类执行时机会先执行完队列中排在目标任务之前的所有任务，但不执行后续任务。
- 正因为执行时机分散，"哪些操作会导致区块加载"是一个需要结合具体调用链分析的问题。
- `TaskExecutor` 用 mailbox 模式把消息队列、线程池和原子状态机组合起来，保证同一 actor 串行消费任务。
- `ThreadedAnvilChunkStorage` 建立了 worldgen、main、light 三个 actor，把世界生成、主线程协调、光照计算分开处理。
- `ChunkTaskPrioritySystem` 是三者之上的调度器，为每个 actor 维护按加载等级排序的队列。
- `MessageListener` 是 actor 之间的统一消息接口，`send()` 负责投递，`ask()` 则把投递扩展成请求-响应模式。
- `ServerLightingProvider` 通过 `processor` (light 线程) 和 `executor` (主线程封装器) 实现双阶段执行，用 `pendingTasks` 在主线程上积累任务，`ticking` 原子锁防止重入。
- 光照任务通过 `enqueue()` 经过优先级队列路由到 light 线程，`runTasks()` 分三阶段执行：PRE_UPDATE 准备、doLightUpdates() 传播、POST_UPDATE 收尾。
- 批处理上限 1000，被动触发（每 tick）和主动触发（队列满）结合，平衡延迟和效率。

### 为什么需要异步任务机制

假设没有异步任务机制——每次调用 `World.getBlockState()` 时，如果目标区块不在内存中，就**同步地**等待它生成完毕。这意味着整个服务端主线程会被阻塞，20 TPS 无法维持。

Minecraft 使用 `CompletableFuture` 解决了这个问题。区块的生成和加载不直接执行，而是被封装成一个 `CompletableFuture`，提交到 `ChunkTaskPrioritySystem` 的队列中：

```java
// ChunkTaskPrioritySystem.java
public static Task<Runnable> createMessage(ChunkHolder holder, Runnable task) {
    // 任务的优先级由 holder.getCompletedLevel() 决定
    // completedLevel 越低（越"强"的加载），任务越优先
    return createMessage(task, holder.getPos().toLong(), holder::getCompletedLevel);
}
```

`ChunkTaskPrioritySystem` 内部维护一个 `LevelPrioritizedQueue`——不是一个简单的 FIFO 队列，而是按 **level 优先级**排序。

**设计决策——为什么优先级由 `completedLevel` 决定而不是 `level`？** `level` 是"目标"（我们想让这个区块达到什么级别），`completedLevel` 是"现状"（实际达到了什么级别）。用 `completedLevel` 排序意味着：**已经很大程度完成、离目标最近的任务，优先级最高**。这避免了"一个 level=22 但生成进度为 EMPTY 的区块"抢在"一个 level=33 但只需要读盘的区块"之前——后者可能在 1 个 tick 内就完成了。

### 三种执行时机的设计逻辑

```java
// ServerChunkManager.getChunk() 简化流程
public Chunk getChunk(int x, int z, ChunkStatus leastStatus, boolean create) {
    // 1. 如果缓存命中（最近 4 个请求的区块），直接返回
    // 2. 未命中 → 创建 UNKNOWN 加载票 + 安排异步任务
    // 3. 调用 tick() 执行队列中的异步任务，直到目标区块的任务完成
    // 4. 返回结果
}
```

**三种时机的设计意图：**

**第一类（保存时阻塞执行）**："如果不保存这个区块就关服，数据会丢失"。这是唯一可以阻塞主线程的场景，因为用户已经发起了关服操作，安全性优先于性能。

**第二类（getChunk 触发）**："如果不加载这个区块，调用者会得到空气方块，后续逻辑全乱"。调用者依赖返回值为正确的 `BlockState`，所以这里必须**半阻塞**——执行队列直到目标完成，但执行完就停。停的原因是不想"顺便"帮其他区块完成任务，延长本次调用的延迟。

**第三类（gt 末尾兜底）**："这些任务本来应该在第二类中被顺便执行，但没排到。现在 gt 快结束了，还有时间就处理掉。"这是兜底机制——保证正常不掉刻时所有任务都在当 gt 内完成。如果掉刻了（当前 gt 超过 50ms），未完成的任务留到下个 gt——硬实时约束优先于完整性。

### "部分执行"的问题

第二类执行时机的"执行到目标完成即停"导致了一个反直觉的现象：**如果你调用 getChunk() 获取区块 A，恰好之前有人调用 getChunk() 获取了区块 B 且 B 的任务还在队列中，那 B 的任务会先被执行（因为排在 A 前面），然后才轮到 A**。但 B 后面的任务（如果还有）就不会被执行——因为 A 完成后执行就停了。

这就是 lovexyn0827 原文说的"非常奥利给"：异步任务的执行顺序依赖于调用顺序，而调用顺序又依赖于数百个 `getBlockState()`、`setBlockState()`、`getBlockEntity()` 的调用点——这些调用点分散在生物 AI、红石运算、方块更新、实体碰撞检测等各个角落。**两个完全相同的玩家行为，可能因为服务端的微小时间偏差而导致完全不同的任务执行顺序**。

### TaskExecutor 状态机的位操作设计

`TaskExecutor` 的 `stateFlags` 是一个 `AtomicInteger`，但它不是普通计数器，而是用**位掩码**同时表达两个布尔状态：

- bit0（值为 1）：`closed` 标志。一旦设置，就不再清除；
- bit1（值为 2）：`running` 标志。`unpause()` 设置，`pause()` 清除。

```java
// TaskExecutor.java lines 36-53
private boolean unpause() {
    int i;
    do {
        i = this.stateFlags.get();
        if ((i & 3) != 0) {
            return false;
        }
    } while (!this.stateFlags.compareAndSet(i, i | 2));

    return true;
}

private void pause() {
    int i;
    do {
        i = this.stateFlags.get();
    } while (!this.stateFlags.compareAndSet(i, i & -3));
}
```

`unpause()` 的判断 `(i & 3) != 0` 同时检查了 bit0 和 bit1：只要已经关闭，或者已经有线程在运行，就不能再次进入 running 状态。成功时，它用 `compareAndSet(i, i | 2)` 原子地设置 bit1。

`pause()` 则用 `i & -3` 清除 bit1。这里的 `-3` 等价于 `~2`，也就是"除了 bit1 之外全为 1"的掩码。`close()` 使用同样的 CAS 思路设置 bit0：`compareAndSet(i, i | 1)`。

为什么不用两个 `AtomicBoolean`？因为这里需要保证的是**组合状态**的原子性。`unpause()` 必须同时检查"未关闭"和"未运行"两个条件，并在检查结果仍然成立时设置 running。两个独立的 `AtomicBoolean` 无法把这个复合判断和更新合成一次原子操作；单个 `AtomicInteger` 的 CAS 可以。

### 三线程模型的完整创建链路

把 `ThreadedAnvilChunkStorage` 构造函数里的几行代码展开，就能看到三线程模型的完整装配过程：

```text
ThreadedAnvilChunkStorage 构造
  -> TaskExecutor.create(executor, "worldgen")
  -> MessageListener.create("main", mainThreadExecutor::send)
  -> TaskExecutor.create(executor, "light")
  -> new ChunkTaskPrioritySystem(List.of(worldgen, main, light), executor, MAX)
      内部：为每个 actor 创建 LevelPrioritizedQueue
  -> this.chunkTaskPrioritySystem.createExecutor(worldgen, false)
      -> controlActor.ask(yield -> ...)
         内部：为 worldgen 在 queues 中注册 queue
         返回 MessageListener wrapper
      -> 赋值给 this.worldGenExecutor
  -> 同样的流程用于 mainExecutor 和 lightingProvider
```

`createExecutor()` 之所以必须通过 `controlActor.ask()` 间接完成，是因为 `queues` 是普通的 `HashMap`，不是线程安全容器。为 actor 创建或取得对应队列，本质上是对这个 map 的访问；如果多个线程同时创建包装器或更新队列，就需要一个串行化入口。

`controlActor` 正是这个入口。它是单个 `TaskExecutor`，同一时间只会有一条执行流消费它的 mailbox，因此所有对 `queues` 的创建、查询、入队、出队动作都被压到同一个控制 actor 中顺序执行。

### 跨线程任务流转的全链路示例

以一次完整的区块加载请求为例，可以把任务怎样跨越 main、worldgen、light 三个 actor 串起来看。

**步骤 1：主线程发起请求。** 某个 `getBlockState()` 调用发现目标区块不在内存中，于是间接进入 `ServerChunkManager.getChunk()`。`getChunk()` 创建一个 `UNKNOWN` 加载票，区块系统再通过 `ChunkTaskPrioritySystem.createMessage(holder, generationTask)` 把生成动作包装成 `Task<Runnable>`，并通过 `this.mainExecutor.send(task)` 发送给 main actor。

**步骤 2：main actor 处理。** main actor 来自 `MessageListener.create("main", mainThreadExecutor::send)`，所以它不会新建线程，而是把任务交给主线程执行器。主线程在执行队列时取出任务，检查目标区块是否需要继续生成；如果需要，就通过 `worldGenExecutor.send(generationTask)` 把真正的生成任务转发给 worldgen actor。

**步骤 3：worldgen actor 处理。** `TaskExecutor("worldgen")` 在底层线程池的工作线程上运行。它的 `runWhile()` 循环取出生成任务，执行地形生成、地物放置、洞穴雕刻、结构处理等 CPU 密集型运算。完成后，对应的 `CompletableFuture.complete()` 被触发，生成出的区块数据进入后续阶段可见的状态。

**步骤 4：light actor 处理。** 生成完成后，`ServerLightingProvider.initializeLight()` 等光照入口会安排光照任务。任务通过 lighting provider 内部持有的 executor 被发送到 light actor，`TaskExecutor("light")` 再在底层线程池上执行光照计算与传播。完成后，类似 `super.setColumnEnabled()` 的状态更新会标记该列光照已经就绪。

**步骤 5：回到 main actor。** 当生成和光照的 `CompletableFuture` 链全部完成，回调会通过 `mainExecutor.send(updateTask)` 通知主线程更新 `ChunkHolder` 状态。主线程完成状态更新后，区块才正式进入调用者需要的可访问状态。

关键洞察是：整个流程里，主线程没有阻塞在噪声采样或光照传播上。CPU 密集型工作交给 worldgen 和 light，主线程只负责任务调度、状态更新和必须在主线程完成的世界交互。这就是 `CompletableFuture`、`TaskExecutor`、`ChunkTaskPrioritySystem` 三者协作的核心价值。

### 为什么 main actor 是 MessageListener 而不是 TaskExecutor？

`ThreadedAnvilChunkStorage` 中的 `mainExecutor` 最终类型是 `MessageListener<ChunkTaskPrioritySystem.Task<Runnable>>`，而 worldgen 和 light 的底层 actor 都是 `TaskExecutor<Runnable>`。这个差异不是偶然的。

`TaskExecutor` 有自己的消息队列和线程池执行循环，适合承载独立线程上的工作；`MessageListener.create("main", mainThreadExecutor::send)` 则只是一个轻量包装，`send()` 会直接调用 `mainThreadExecutor.send()`。它不创建新队列，也不创建新线程，只把消息路由到已经存在的主线程执行器。

设计原因很直接：服务端主线程本来就有一个 `ThreadExecutor`，也就是 `MinecraftServer` 自身的主循环。主线程任务必须回到这条既有执行流里运行，否则世界状态、玩家连接、实体列表等主线程约束都会被破坏。

所以 TACS 构造函数中才会出现这种不对称：worldgen 和 light 需要 `TaskExecutor` 来承载独立计算；main 只需要一个 `MessageListener` 包装已有的 `mainThreadExecutor`。`mainExecutor` 的职责是**路由到主线程**，不是创造另一条"主线程"。
