In [MicroTiming: Scheduled Ticks and Scheduled Tick Components](../MicroTiming/计划刻与计划刻元件.zh.md), we discussed scheduled ticks from a micro-timing perspective, covering information structure, ordering, and scheduled tick suppressors. This chapter supplements one question: **What happens to a scheduled tick when its chunk hasn't entered `BLOCK_TICKING` (weak loading)?**

One-sentence answer: Scheduled ticks can continue to exist in the chunk-level scheduler, but the world-level scheduler won't retrieve and execute scheduled ticks from that chunk. It's not "execute unconditionally when time arrives," but also requires permission from the chunk runtime level.

## Basics

### Scheduled Ticks Are Just Reservation Slips

A scheduled tick can be understood as "at a certain world time, have a certain position's block or fluid execute a scheduled logic once." As for `TickPriority`, `subTickOrder`, `triggerTick`, and specific component behavior, those were covered in the MicroTiming chapter and won't be repeated here.

What we need to grasp here is another layer of relationship: scheduled ticks aren't isolated objects hanging directly on the entire world, but are first grouped by chunk ownership and placed into the corresponding chunk's `ChunkTickScheduler` (chunk-level scheduler); then `WorldTickScheduler` (world-level scheduler) picks out scheduled ticks from tickable chunks each tick and executes them.

### How Scheduled Ticks Bind to Chunks

Each `WorldChunk` holds its own block and fluid `ChunkTickScheduler`. When a chunk is truly loaded into the world as a `WorldChunk`, its chunk-level scheduler is attached to the world-level scheduler:

```java
// WorldChunk.java
public void addChunkTickSchedulers(ServerWorld world) {
    world.getBlockTickScheduler().addChunkTickScheduler(this.pos, this.blockTickScheduler);
    world.getFluidTickScheduler().addChunkTickScheduler(this.pos, this.fluidTickScheduler);
}
```

When unloading entities and cleaning up chunks, the attachment relationship is removed:

```java
// WorldChunk.java
public void removeChunkTickSchedulers(ServerWorld world) {
    world.getBlockTickScheduler().removeChunkTickScheduler(this.pos);
    world.getFluidTickScheduler().removeChunkTickScheduler(this.pos);
}
```

This shows that "having a chunk-level scheduler recognized by the world-level scheduler" and "this chunk can currently execute scheduled ticks" are not the same thing. The former indicates chunk data has already been involved in world management as a `WorldChunk`; the latter still depends on whether the chunk has reached the runtime level required for block ticking.

In Chapter 3 [Level and Runtime State Layering](./03-级别与运行态分层.en.md), we already defined `BLOCK_TICKING` as weak loading: it allows block ticks, redstone computation, random ticks, and scheduled ticks to run, but doesn't run entities. `FULL` below this qualification only guarantees block data is accessible, not active computation.

### How the World-Level Scheduler Determines "This Chunk Can Execute"

`WorldTickScheduler` doesn't just check "are there due scheduled ticks in the queue?" It also holds a `tickingFutureReadyPredicate` (ticking readiness predicate). When a chunk's earliest scheduled tick is already due, the world-level scheduler first asks this predicate: is this chunk now in a ticking state?

If the answer is true, that chunk's `ChunkTickScheduler` is placed in the current tick's executable queue; if the answer is false, it stays in `nextTriggerTickByChunkPos`, waiting to be rechecked in a later tick.

Therefore, chunks not at `BLOCK_TICKING` won't "compensate by executing immediately." They just keep already-due scheduled ticks in the queue. When the chunk re-enters weak loading or entity ticking, the world-level scheduler will retrieve these scheduled ticks again and execute them according to the sorting rules described in the MicroTiming chapter.

> [!IMPORTANT]
> `triggerTick` only indicates "earliest world time when execution is possible," not "must execute at this tick regardless of chunk load state." When chunks aren't ticking, scheduled ticks are delayed, not executed through the runtime level.

### How Scheduled Ticks Cross Chunk Boundaries

A scheduled tick's position determines which chunk it belongs to. `WorldTickScheduler.scheduleTick()` uses `OrderedTick.pos()` to calculate chunk coordinates, then delivers this `OrderedTick` (scheduled tick object) to the corresponding chunk's `ChunkTickScheduler`:

```java
// WorldTickScheduler.java
public void scheduleTick(OrderedTick<T> orderedTick) {
    long l = ChunkPos.toLong(orderedTick.pos());
    ChunkTickScheduler<T> chunkTickScheduler = this.chunkTickSchedulers.get(l);
    if (chunkTickScheduler == null) {
        Util.throwOrPause(new IllegalStateException("Trying to schedule tick in not loaded position " + orderedTick.pos()));
    } else {
        chunkTickScheduler.scheduleTick(orderedTick);
    }
}
```

So when a piston pushes a block across a chunk boundary, subsequent scheduled tick ownership depends on "where the new scheduled tick is arranged." If the move process clears scheduled ticks within the original position's range and reschedules scheduled ticks at the new position, then the new scheduled tick enters the target chunk's chunk-level scheduler; if there's just an unexecuted scheduled tick from the original chunk, it still records the original `pos` and won't automatically rebind to the new coordinates just because the block later moved.

This is why cross-chunk contraptions need extra care: scheduled ticks themselves are "reservations on coordinates," not "tags following block entities as they move." Once coordinates cross a chunk boundary, whether it can execute in the current gt depends on whether the chunk at the new coordinates has reached `BLOCK_TICKING`.

## Common Misconceptions

| Misconception                                                            | Reality                                                                                                                                                                      |
| ------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| "Scheduled ticks must execute when time arrives"                         | They require both `triggerTick` arrival AND the chunk being in a tickable state.                                                                                             |
| "Chunks can execute scheduled ticks as long as they're loaded"           | "Loaded" needs to distinguish FULL (accessible) from BLOCK_TICKING (tickable). Only the latter allows scheduled tick execution.                                              |
| "Scheduled ticks in unloaded chunks execute earlier"                     | They don't execute at all — they wait in the chunk-level scheduler until the chunk re-enters ticking state.                                                                  |
| "Pistons automatically transfer scheduled ticks across chunk boundaries" | Scheduled ticks belong to coordinates. New scheduled ticks from block moves need to be rescheduled at the new position; the old scheduled tick doesn't automatically follow. |

## Summary

- Scheduled ticks are grouped by coordinate ownership into chunk-level schedulers; the world-level scheduler only handles cross-chunk collection and execution.
- `WorldChunk` attaches `ChunkTickScheduler` when loaded into the world, removes attachment when unloading and cleaning.
- `BLOCK_TICKING` (weak loading) is the minimum runtime level for scheduled tick execution; `FULL` only guarantees data accessibility, not scheduled tick execution.
- `tickingFutureReadyPredicate` is the chunk ticking threshold before scheduled tick execution, checking whether `ChunkHolder.getTickingFuture()` currently provides a usable `WorldChunk`.
- When crossing chunk boundaries, scheduled ticks follow coordinates and rescheduled positions, not automatically following moved blocks.
- Scheduled tick suppressors must also be in tickable chunks; non-ticking chunks cannot participate in the world-level scheduler's current tick competition.

## [!ADVANCED] Code Walkthrough

### WorldTickScheduler: tickingFutureReadyPredicate

`WorldTickScheduler` is responsible for collecting and executing scheduled ticks from all chunks. During initialization, it receives a `tickingFutureReadyPredicate`:

```java
// ServerChunkManager.java
this.tickScheduler = new ServerTickScheduler<>(
    (pos) -> this.threadedAnvilChunkStorage.getTickingFuture(pos)
);
```

This lambda passes `ChunkHolder.getTickingFuture()` to the predicate. When `WorldTickScheduler` needs to determine whether a chunk can currently execute scheduled ticks, it calls:

```java
// WorldTickScheduler.java
private boolean shouldTick(ChunkPos pos, long currentTick) {
    CompletableFuture<Either<WorldChunk, ChunkHolder.Unloaded>> future =
        this.tickingFutureReadyPredicate.apply(pos);
    return future != null && future.getNow(ChunkHolder.UNLOADED_WORLD_CHUNK).left().isPresent();
}
```

Interpretation:

1. Get the `tickingFuture` for that chunk position.
2. If the future is null (chunk holder doesn't exist), can't tick.
3. If the future is completed and the result is `Either.left(WorldChunk)`, can tick.
4. If the future is not yet completed or the result is `Either.right(Unloaded)`, can't tick.

This check doesn't happen every tick for every chunk — only chunks whose `nextTriggerTickByChunkPos` records indicate "time has arrived" are checked.

### Chunk-Level Scheduler Collection Logic

When `WorldTickScheduler.tick()` executes, it first traverses `nextTriggerTickByChunkPos` to find chunks whose earliest scheduled tick has arrived:

```java
// WorldTickScheduler.java
public void tick(long time, int maxTicks, Consumer<OrderedTick<T>> tickConsumer) {
    profiler.push("collect");
    this.collectTickableChunkTickSchedulers(time);
    profiler.pop();
    ...
}

private void collectTickableChunkTickSchedulers(long time) {
    ObjectIterator<Long2LongMap.Entry> objectIterator =
        this.nextTriggerTickByChunkPos.long2LongEntrySet().iterator();

    while (objectIterator.hasNext()) {
        Long2LongMap.Entry entry = objectIterator.next();
        long l = entry.getLongKey();
        long m = entry.getLongValue();
        if (m <= time) {
            ChunkTickScheduler<T> chunkTickScheduler = this.chunkTickSchedulers.get(l);
            if (chunkTickScheduler == null) {
                objectIterator.remove();
            } else {
                OrderedTick<T> orderedTick = chunkTickScheduler.peekNextTick();
                if (orderedTick == null) {
                    objectIterator.remove();
                } else if (orderedTick.triggerTick() > time) {
                    entry.setValue(orderedTick.triggerTick());
                } else if (this.tickingFutureReadyPredicate.test(l)) {
                    objectIterator.remove();
                    this.tickableChunkTickSchedulers.add(chunkTickScheduler);
                }
            }
        }
    }
}
```

This code has four filtering layers:

1. `m <= time`: This chunk's recorded next scheduled tick time has reached current world time.
2. `chunkTickScheduler == null`: If the chunk-level scheduler no longer exists, remove this index.
3. `orderedTick == null` or `orderedTick.triggerTick() > time`: If the head scheduled tick doesn't exist, or the head scheduled tick hasn't actually arrived yet, correct or clean up the index.
4. `this.tickingFutureReadyPredicate.test(l)`: After time has arrived and queue exists, finally check whether the chunk can actually tick.

The key is the last layer. Only by passing the ticking readiness check does the chunk-level scheduler enter `tickableChunkTickSchedulers`. If it doesn't pass, the code neither `remove()`s nor `add()`s; it stays in `nextTriggerTickByChunkPos`, to be tried again next time the world-level scheduler collects.

### tickingFutureReadyPredicate Implementation

When `ServerWorld` creates block and fluid world-level schedulers, it passes the same method reference to the constructor:

```java
// ServerWorld.java
private final WorldTickScheduler<Block> blockTickScheduler = new WorldTickScheduler<>(this::isTickingFutureReady, this.getProfilerSupplier());
private final WorldTickScheduler<Fluid> fluidTickScheduler = new WorldTickScheduler<>(this::isTickingFutureReady, this.getProfilerSupplier());
```

This method in `ServerWorld` first confirms the chunk entity management side still considers it loaded, then hands off to `ServerChunkManager`:

```java
// ServerWorld.java
private boolean isTickingFutureReady(long chunkPos) {
    return this.isChunkLoaded(chunkPos) && this.chunkManager.isTickingFutureReady(chunkPos);
}
```

The actual chunk runtime level check is in `ServerChunkManager.isTickingFutureReady()`:

```java
// ServerChunkManager.java
public boolean isTickingFutureReady(long pos) {
    ChunkHolder chunkHolder = this.getChunkHolder(pos);
    if (chunkHolder == null) {
        return false;
    }

    if (!this.world.shouldTickBlocksInChunk(pos)) {
        return false;
    }

    Either<WorldChunk, ChunkHolder.Unloaded> either = chunkHolder.getTickingFuture().getNow(null);
    return either != null && either.left().isPresent();
}
```

Two thresholds here:

- `world.shouldTickBlocksInChunk(pos)` goes to the ticket system's `shouldTickBlocks(chunkPos)`, which is the block computation qualification discussed in Chapter 3;
- `chunkHolder.getTickingFuture().getNow(null)` must have obtained `Either.left(WorldChunk)`, indicating `ChunkHolder`'s `tickingFuture` is completed and the completion result is a usable `WorldChunk`, not `Unloaded`.

So `tickingFutureReadyPredicate` is essentially asking: **Does this chunk already have a usable ticking Future?** In plainer terms, it's checking whether a condition like `ChunkHolder.getTickingFuture().isDone()` is met, and the completion result must be `WorldChunk`. In Yarn 1.20.1+build.10's actual implementation, it doesn't directly call `isDone()`, but uses `getNow(null)` to get the current result, then checks whether the result is `Either.left(WorldChunk)`.

Note this doesn't block waiting for Future completion. `getNow(null)` means "is it completed now? If not, give me null." Therefore the scheduled tick system won't wait for a certain chunk to finish loading; it just checks in passing during each tick's collection, and skips if not ready.

### Execution Location in ServerWorld.tick

Block scheduled ticks actually execute in `ServerWorld.tick()`'s `tickPending` phase:

```java
// ServerWorld.java
profiler.swap("tickPending");
if (!this.isDebugWorld()) {
    long m = this.getTime();
    profiler.push("blockTicks");
    this.blockTickScheduler.tick(m, 65536, this::tickBlock);
    profiler.swap("fluidTicks");
    this.fluidTickScheduler.tick(m, 65536, this::tickFluid);
    profiler.pop();
}
```

The `65536` here is the maximum number of scheduled ticks retrieved in this call. `this::tickBlock` is the entry point where scheduled tick objects finally trigger block `scheduledTick` behavior; but before reaching it, scheduled ticks have already gone through world-level scheduler collection, chunk-level scheduler filtering, and `tickingFutureReadyPredicate`'s chunk runtime level check.

This explains a common phenomenon: if a scheduled tick is already due when the chunk leaves weak loading, it won't continuously execute while offline, nor will it force execution when world time reaches `triggerTick`. Only when the chunk re-enters `BLOCK_TICKING` will it be re-collected in subsequent `ServerWorld.tick()` and executed as an already-due scheduled tick.
