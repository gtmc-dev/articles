If you've understood the architecture from previous chapters by the time you reach this one, you might ask: "`ChunkTicketManager.tick()` updated the loading level and notified `ChunkHolder`, so when is the chunk actually loaded?"

The answer is: **not "immediately", but "executed in some future async task"**.

## CompletableFuture's Core Role

In the chunk management system, `CompletableFuture` is the pervasive async coordination tool. It has two roles:

### Role One: Task Planning and Execution

A `CompletableFuture` corresponds to a basic task — updating player loading tickets, loading a chunk, completing one generation stage of a chunk. Tasks aren't run directly, but are **scheduled** as a `CompletableFuture`, then **executed** somewhere later in the operation.

This "planning-execution" separation means: you might add a task at the start of a game tick (gt), but it won't actually run until the async task execution phase several game ticks later.

### Role Two: Chunk Availability Marker

In `ChunkHolder`, three `CompletableFuture`s serve as availability markers for different "views" of chunks:

- `accessibleFuture`: Completes when chunk data is accessible
- `tickingFuture`: Completes when chunk can participate in block ticking
- `entityTickingFuture`: Completes when chunk can participate in entity operations

When a chunk no longer meets a certain level requirement, the corresponding Future is `complete(UNLOADED_WORLD_CHUNK)`, and any operations depending on that view receive a "not available" result.

## Task Queue: MainThreadExecutor

Async tasks are managed by `ServerChunkManager.MainThreadExecutor`. It's essentially a **first-in-first-out (FIFO)** task queue, ensuring all tasks execute on the server main thread.

Each task entering the queue will eventually be taken out and executed on the main thread, but the timing is not fixed — see the next section.

## Execution Timing

Locations that may trigger async task execution are scattered throughout the code. Three main categories:

### Category One: Blocking Execution During Chunk Save

During chunk saves triggered by pause, exit, autosave, or `/save-all` command, saving a single chunk requires ensuring that chunk's data is ready. At this point, related async tasks are **executed blockingly and immediately** — can't continue saving without finishing execution.

### Category Two: Need-Based Execution Triggered by getChunk()

This is the most common and most hidden category. When external code obtains a chunk through `ServerChunkManager.getChunk()`:

1. A task T for "get this chunk" is added to the async task queue;
2. Tasks in the queue are executed in FIFO order **until T completes**;
3. After T completes, task execution **immediately stops** — tasks queued after T **won't be executed here**.

This means: if 50 other tasks were already queued before you called `getChunk()`, those 50 tasks will be executed before your T. Conversely, tasks after T can only wait for the next execution opportunity.

Locations that may trigger `getChunk()` number at least in the **hundreds** — including (but not limited to):

- When using `World.getBlockState()` / `setBlockState()`
- When using `World.getBlockEntity()` / `setBlockEntity()`
- When using `World.getFluid()`
- Player respawn, entering dimension, joining dimension
- Getting region difficulty
- Nether portal teleporting entities

> Getting entities in a region generally doesn't cause related chunks to load — entity queries and block queries are two independent mechanisms in the source code.

### Category Three: Fallback Execution at Game Tick End

At the end of each server game tick is an async task operation phase. In this phase:

- If not lagging (current gt runtime ≤ 50ms), task execution can continue until task queues for **all dimensions** are emptied;
- If lagging, task execution terminates immediately, remaining tasks left for next gt;
- New tasks produced during execution will also continue to be executed in this phase.

Execution order is fixed:

1. Server's own async tasks (like processing operations from client)
2. Main world's `ServerChunkManager` async tasks
3. Other dimensions' `ServerChunkManager` async tasks (Nether before End)

## Dynamic Understanding

Design intent behind the three execution timing categories can be understood this way:

- **Category One** is to complete a task that must be completed blockingly immediately ("if we don't save this chunk, the server can't safely shut down");
- **Category Two** is to complete a task the caller must immediately receive ("`getBlockState()` can't return a real state, subsequent logic can't proceed");
- **Category Three** is a fallback mechanism — ensures all async tasks produced in the current gt are processed within the current gt under normal circumstances.

But precisely because execution timing is scattered across hundreds of call points, **async task queues for the same dimension can be partially executed anywhere** — this makes chunk loading timing highly unpredictable dynamically. This is also why lovexyn0827's original text mentioned "this part is really written very 'awesome'".

## Summary

- `CompletableFuture` plays a dual role in chunk management: task carrier and chunk availability marker.
- Async tasks are managed by `MainThreadExecutor`, FIFO queue, guaranteed main thread execution.
- Execution timing falls into three categories: blocking execution during save, need-based execution from `getChunk()`, fallback execution at gt end.
- Category Two execution timing first executes all tasks queued before the target task, but doesn't execute subsequent tasks.
- Precisely because execution timing is scattered, "which operations cause chunk loading" is a question requiring analysis combined with specific call chains.

## :advanced Code Walkthrough

### Why Async Task Mechanism Is Needed

Assume there's no async task mechanism — every time `World.getBlockState()` is called, if the target chunk isn't in memory, **synchronously** wait for it to finish generating. This means the entire server main thread would block, unable to maintain 20 TPS.

Minecraft uses `CompletableFuture` to solve this problem. Chunk generation and loading don't execute directly, but are wrapped as a `CompletableFuture` and submitted to `ChunkTaskPrioritySystem`'s queue:

```java
// ChunkTaskPrioritySystem.java
public static Task<Runnable> createMessage(ChunkHolder holder, Runnable task) {
    // Task priority determined by holder.getCompletedLevel()
    // Lower (more "strong" loading) completedLevel = higher task priority
    return createMessage(task, holder.getPos().toLong(), holder::getCompletedLevel);
}
```

`ChunkTaskPrioritySystem` internally maintains a `LevelPrioritizedQueue` — not a simple FIFO queue, but sorted by **level priority**.

**Design Decision — Why is priority determined by `completedLevel` rather than `level`?** `level` is the "target" (what level we want this chunk to reach), `completedLevel` is "current state" (what level actually reached). Sorting by `completedLevel` means: **tasks already largely complete and closest to target have highest priority**. This avoids "a chunk with level=22 but generation progress EMPTY" jumping ahead of "a chunk with level=33 but only needs disk read" — the latter might complete in 1 tick.

### Design Logic of Three Execution Timings

```java
// ServerChunkManager.getChunk() simplified flow
public Chunk getChunk(int x, int z, ChunkStatus leastStatus, boolean create) {
    // 1. If cache hit (last 4 requested chunks), return directly
    // 2. Cache miss → create UNKNOWN loading ticket + schedule async task
    // 3. Call tick() to execute queue's async tasks until target chunk task completes
    // 4. Return result
}
```

**Design intent for three timings:**

**Category One (blocking execution during save)**: "If we don't save this chunk before closing server, data will be lost". This is the only scenario that can block the main thread, because user has already initiated server shutdown, safety priority over performance.

**Category Two (getChunk triggered)**: "If we don't load this chunk, caller will get air blocks, all subsequent logic breaks". Caller depends on return value being correct `BlockState`, so must **semi-block** here — execute queue until target completes, but stop after completion. Stopping reason is not wanting to "incidentally" help other chunks complete tasks, extending this call's latency.

**Category Three (gt end fallback)**: "These tasks should have been incidentally executed in Category Two, but didn't get their turn. Now gt is almost over, if there's time handle them." This is fallback mechanism — ensures all tasks complete within current gt under normal non-lag. If lagging (current gt exceeds 50ms), incomplete tasks left for next gt — hard real-time constraints priority over completeness.

### The "Partial Execution" Problem

Category Two execution timing's "execute until target completes then stop" causes a counter-intuitive phenomenon: **If you call getChunk() to get chunk A, and someone happened to call getChunk() for chunk B earlier with B's task still in queue, B's task will execute first (because it's ahead of A in queue), then comes A**. But tasks after B (if any) won't execute — because execution stops after A completes.

This is what lovexyn0827's original text calls "very awesome": async task execution order depends on call order, and call order depends on hundreds of `getBlockState()`, `setBlockState()`, `getBlockEntity()` call sites — these sites are scattered across mob AI, redstone operations, block updates, entity collision detection, and various corners. **Two completely identical player actions may lead to completely different task execution orders due to tiny server timing differences**.
