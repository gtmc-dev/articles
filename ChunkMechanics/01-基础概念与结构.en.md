Press `F3 + G`, and colored grids appear on the ground. These grids, spaced 16 blocks apart, show **chunk boundaries**.

Understanding the chunk management system requires more than knowing "16×16 grid squares". Let's start from the bottom.

## Chunk and Chunk Section Definition

### Mathematical Definition of a Chunk

A chunk is a data storage and loading unit in Minecraft. Strictly speaking, a chunk corresponds to the region:

$$\{(x, y, z) \mid 16m \le x < 16(m+1),\; 16n \le z < 16(n+1),\; m, n \in \mathbb{Z}\}$$

This means:

- Chunks are fixed at 16×16 in the **horizontal direction**, with boundaries at multiples of 16;
- Chunks have no upper limit in the **vertical direction** — they span the **full buildable height** of the dimension. In the Overworld, all 384 blocks in a column from Y=`-64` to Y=`319` belong to the same chunk;
- Chunks have only X and Z coordinates, no independent Y coordinate.

### Chunk Coordinate Conversion

Conversion rules are strictly defined by three bitwise operations:

```text
Chunk X  = Block X >> 4    (arithmetic right shift 4 bits = floor division by 16)
Chunk Z  = Block Z >> 4
In-chunk X = Block X & 15  (take low 4 bits = remainder after division by 16)
In-chunk Z = Block Z & 15
```

Reverse calculation follows the same strict rules:

```text
Chunk start block X = Chunk X << 4
Chunk eastmost block X = Chunk start block X + 15
```

> [!IMPORTANT]
> Chunk ownership for negative coordinates is easy to miscalculate. `>>` is arithmetic right shift (floor division), so `-1 >> 4 = -1`, `-16 >> 4 = -1`, `-17 >> 4 = -2`. Block X=`-1` is not in chunk 0, but in chunk **-1** at the eastmost position (in-chunk X=15). Memory aid: **negative coordinates round toward -∞**.

### Chunk Sections

Chunks themselves are tall, but the game doesn't need to traverse entire vertical columns every time. The chunk continues to be sliced along the Y axis into **16×16×16** **chunk sections**. Each chunk section contains exactly `16³ = 4096` coordinates.

Conversion rules are **completely isomorphic** to chunk coordinates:

```text
Section Y  = Block Y >> 4
In-section Y = Block Y & 15
```

`Chunk` creates a `ChunkSection[]` array based on dimension height. The Overworld has 384 blocks of height, so a complete Overworld chunk contains `384 / 16 = 24` chunk sections.

**Section coordinate ≠ array index**. In the Overworld:

- Bottommost section coordinate: `-64 >> 4 = -4`
- Array index 0 corresponds to section coordinate -4
- `sectionArray[23]` corresponds to section coordinate `-4 + 23 = 19` (covering Y=`304` to Y=`319`)

Conversion formula: `Array index = Section coordinate - Bottommost section coordinate`

### Local Coordinate Packing

The game frequently needs to represent "which row, column, layer" as local coordinates within a 16³ chunk section. `ChunkSectionPos` provides a method to pack three 0-15 integers into a single `short`:

```java
// Pack: x(4bit) | z(4bit) | y(4bit) → total 12 valid bits
short packed = (short)(x << 8 | z << 4 | y);
```

Unpacking is the reverse:

```java
int x = (packed >> 8) & 15;
int z = (packed >> 4) & 15;
int y = packed & 15;
```

This packing **isn't just a space-saving trick** — it's used throughout the codebase:

- Chunk section skylight and blocklight storage use 16-bit arrays indexed by packed coordinates;
- Random tick candidate list uses 16-bit arrays to store which coordinates need ticking;
- Block entity position references often use packed coordinates rather than `BlockPos`.

The cost of packing is negligible: two shift operations plus two bitwise ANDs. The gain is halving the storage space and improving CPU cache locality.

## Why ProtoChunk and WorldChunk Exist

Minecraft doesn't use a single "Chunk" class for all scenarios. It distinguishes between two fundamentally different situations:

|                             | ProtoChunk                                      | WorldChunk                                   |
| --------------------------- | ----------------------------------------------- | -------------------------------------------- |
| **Purpose**                 | Temporary carrier during generation             | Data structure in the running world          |
| **Existence phase**         | Only during `EMPTY` → `FULL` generation process | From `FULL` to unload                        |
| **Modifiability**           | Writable (builder mode)                         | Read-write (runtime state)                   |
| **Block entity operations** | No complex ticker scheduling                    | Full block entity ticking system             |
| **Entity handling**         | Only stores entity list                         | Full entity simulation (when ENTITY_TICKING) |
| **Client visibility**       | Non-existent                                    | Sent to clients (when in view)               |

### ProtoChunk: Generation Carrier

`ProtoChunk` is the mutable data structure used during chunk generation. Each generation step (from `EMPTY` to `FEATURES`) gradually fills its internal data:

- `sections[]` progressively fills with block states
- `heightmaps` records terrain height during `NOISE`
- `carvingMask` marks cave/ravine boundaries during `CARVING`
- `lights` accumulates light propagation ranges
- `entities` simply stores entity NBT for later transfer

After finishing generation, `ProtoChunk` is directly converted to `WorldChunk`:

```java
public WorldChunk convertToWorldChunk(ServerLightingProvider lighting, Chunk chunk) {
    // Batch transfer entities
    chunk.getEntitySectionStorage().addAll(this.entities);

    // Transfer block ticks
    this.transferTicksToSections(this.blockTickScheduler, Chunk::createBlockTickScheduler);
    this.transferTicksToSections(this.fluidTickScheduler, Chunk::createFluidTickScheduler);

    // ...other transfer logic

    return worldChunk;
}
```

Note that the conversion **doesn't copy data from `ProtoChunk` to `WorldChunk`** — instead, it **transfers ownership** of sections, heightmaps, block tick schedulers, etc. Memory addresses remain unchanged; only the wrapper changes. This is why generation and post-generation use different classes: generation needs build pattern design, runtime needs minimal state machine overhead.

### WorldChunk: Runtime Carrier

Once generation is complete, the chunk becomes `WorldChunk`. This class adds runtime-specific functionality:

- **Block entity ticker registration**: WorldChunk maintains `blockEntityTickers` for efficient tick iteration
- **Entity section management**: Entity storage switches to section-sliced indexing for spatial queries
- **Client synchronization**: Tracks dirty sections (`chunkNeedsLight`, `lightUpdateTime`) to determine sync packets
- **Game event listeners**: Manages per-section `GameEventDispatcher` (Sculk Sensor, Warden)

Reading a block state from `WorldChunk` is simpler than from `ProtoChunk`, because the `PalettedContainer` in sections is already initialized and doesn't need fallback logic. This is also why `setBlockState()` in WorldChunk directly triggers neighbor updates and block entity state sync — because WorldChunk **is the world**.

## Palette: The Data Structure Behind Block Storage

Most players know chunks are 16×16×384 (Overworld), but how does the game store 98,304 block states? Not as a 16³ three-dimensional array — that would make chunk files gigabytes large. The real structure is `PalettedContainer<BlockState>`.

### Basic Structure

```java
public class PalettedContainer<T> {
    private Palette<T> palette;              // Dictionary: index → actual value
    private PackedIntegerArray data;         // Bit-packed array: coordinate → palette index
    private int bits;                        // Bits per entry
}
```

The core idea: instead of storing each block state's full ID (16 bits), store an **index** into a local palette (typically 4-8 bits).

### Read/Write Process

**Write**:

```java
public T swap(int index, T value) {
    int paletteIndex = palette.index(value);
    if (paletteIndex < 0) {                  // Not in palette
        paletteIndex = palette.add(value);   // Add to palette
        if (paletteIndex >= (1 << bits)) {   // Palette full
            resize();                        // Expand bit width or switch to global palette
        }
    }
    return data.swap(index, paletteIndex);
}
```

**Read**:

```java
public T get(int index) {
    int paletteIndex = data.get(index);
    return palette.get(paletteIndex);
}
```

### Palette Types

Minecraft uses three kinds of palettes based on diversity:

| Palette Type         | Condition                 | Index Bits | Characteristics                                       |
| -------------------- | ------------------------- | ---------- | ----------------------------------------------------- |
| `SingleValuePalette` | Only 1 unique block state | 0          | No data array needed, directly returns the same value |
| `ArrayPalette`       | 2-16 unique block states  | 4-8        | Most space-efficient, common case                     |
| `GlobalPalette`      | >16 unique block states   | 16         | Directly stores global registry IDs, no compression   |

When placing new blocks in a section, the palette may expand from `ArrayPalette` to `GlobalPalette`. This process triggers `resize()`, which reallocates the `data` array and remaps all entries. This is why chunk generation performance degrades with more diverse block states — more reallocation overhead.

**Design decision — why separate palette and data arrays?** The `palette` stores unique block states that appear in the section, while `data` stores indices into that palette. If a section contains only stone and air:

- Without palette: 4096 entries × 16 bits (block state ID) = 8192 bytes
- With palette: `palette=[stone, air]` + 4096 entries × 1 bit (index 0 or 1) = ~512 bytes

The palette is **dictionary compression** — the more homogeneous the chunk, the higher the compression ratio. A section filled with air stores only `palette=[air]` and doesn't even need a `data` array.

### Block State ID Packing

Block state IDs are composed of:

```text
Block ID (registry order) + State properties (metadata)
```

For example, `minecraft:oak_stairs` has properties `facing`, `half`, `shape`, `waterlogged`, with combinations `4 × 2 × 5 × 2 = 80` states. The registry assigns 80 consecutive IDs to this block. When storing, the game packs:

```java
int stateId = Block.STATE_IDS.getRawId(blockState);
```

This ID is what gets stored in `PalettedContainer`. When reading:

```java
BlockState blockState = Block.STATE_IDS.get(stateId);
```

**Why not store `(block ID, properties)` separately?** Packing into a single integer allows bitwise operations and table lookups — both faster than map queries. The cost is larger ID space, but since the palette compresses it, actual storage doesn't increase significantly.

## Client Chunk Pipeline

This chapter focuses on server-side chunk management, but it's worth briefly understanding the client side to clarify where responsibilities are divided.

### Client-Server Division

| Responsibility       | Server                    | Client                                                   |
| -------------------- | ------------------------- | -------------------------------------------------------- |
| Chunk generation     | ✅                        | ❌                                                       |
| Block entity ticking | ✅                        | ❌ (client-side block entities are only for rendering)   |
| Entity simulation    | ✅                        | ❌ (client entities interpolate based on server updates) |
| Chunk rendering      | ❌                        | ✅                                                       |
| Lighting computation | ✅ (authoritative source) | ✅ (receives and applies server light data)              |

The client **doesn't generate chunks** — it only receives chunk data from the server and renders it. Even in singleplayer mode, the integrated server generates chunks and sends them to the client running in the same process.

### ProtoChunk and WorldChunk: The Design Philosophy of Two Chunk Types

```java
// ProtoChunk.java
public class ProtoChunk extends Chunk {
    // No levelTypeProvider
    // No ServerEntityManager integration
    // No BlockTickScheduler integration
    // -- Its job is to "be generated," not to "be run"
}

// WorldChunk.java
public class WorldChunk extends Chunk {
    private Supplier<ChunkLevelType> levelTypeProvider;

    public ChunkLevelType getLevelType() {
        return this.levelTypeProvider == null
            ? ChunkLevelType.FULL : this.levelTypeProvider.get();
    }
    public void setLevelTypeProvider(Supplier<ChunkLevelType> levelTypeProvider) {
        this.levelTypeProvider = levelTypeProvider;
    }
    // Holds BlockTickScheduler and FluidTickScheduler
    // Holds GameEventDispatcher
    // Manages entities through ServerEntityManager
    // -- Its job is to "be run"
}
```

The design idea behind this is **separation of concerns**. `ProtoChunk` does not need to know what a "tick" is or what "mob spawning" is. It only needs to be gradually filled by the world-generation pipeline on the generation thread. `WorldChunk` does not need to know what "noise terrain" is or what "cave carving" is. It only needs to participate in per-gt game logic on the main thread.

But both share the `Chunk` base class. This means they have the same data structures such as `sectionArray`, `heightmaps`, and `blockEntities`. The elegance of this design is that at the `FULL` stage, `ProtoChunk` does not need to be "copied." Its `ChunkSection[]` is passed directly to the converted `WorldChunk`. The other parts of the `ProtoChunk` object are discarded (and later reclaimed by GC), but the block data itself enters the runtime state intact.

**Why is `levelTypeProvider` a `Supplier`?** Because a chunk's runtime level can **change dynamically**. The same `WorldChunk` may switch back and forth among 31 (`ENTITY_TICKING`), 32 (`BLOCK_TICKING`), and 33 (`FULL`). If `levelType` were stored directly as a field, it would need to be updated every time the level changed. But the trigger for that update lives in `ChunkHolder`, not in `WorldChunk` itself. Using a `Supplier` lets `WorldChunk` **query `ChunkHolder` directly for the current level**, avoiding the synchronization cost of having to notify `WorldChunk` on every level change.

`setLevelTypeProvider` is called by `ThreadedAnvilChunkStorage` when the chunk first enters runtime state (around line 744):

```java
// ThreadedAnvilChunkStorage.java (simplified)
worldChunk.setLevelTypeProvider(() -> ChunkLevels.getType(chunkHolder.getLevel()));
```

### TACS Table Structure Design

```java
// ThreadedAnvilChunkStorage.java
private final Long2ObjectLinkedOpenHashMap<ChunkHolder> currentChunkHolders;
private volatile Long2ObjectLinkedOpenHashMap<ChunkHolder> chunkHolders
    = this.currentChunkHolders.clone();
private final Long2ObjectLinkedOpenHashMap<ChunkHolder> chunksToUnload;
private final LongSet loadedChunks;
final LongSet unloadedChunks;
```

**Why is `chunkHolders` (the snapshot) necessary?** `currentChunkHolders` changes frequently. Each tick may create or remove dozens of chunks. But operations such as `tick()` and `save()` need to traverse all holders stably. If they iterated `currentChunkHolders` directly, additions or removals during traversal could trigger `ConcurrentModificationException`. `chunkHolders` is a `volatile` clone that provides an **immutable snapshot of the current moment**. Iterators can safely traverse it without being affected by later modifications. The performance cost is one full clone, usually tens to hundreds of entries, which is far lower than the cost of locking during traversal.

**What is the difference between `unloadedChunks` and `chunksToUnload`?** `unloadedChunks` is the `LongSet` that `setLevel()` immediately adds to when a chunk leaves accessible range. It is only a "marker set" and does not carry the `ChunkHolder` itself. `chunksToUnload`, by contrast, stores the complete `ChunkHolder` object. In `setLevel()`, if a `ChunkHolder` is found to already exist in `chunksToUnload` (meaning this chunk left accessible range before and then came back), it is reused directly rather than recreated. This avoids frequent object creation in a repeated "leave-return-leave" cycle.
