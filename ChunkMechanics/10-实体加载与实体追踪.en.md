Previous chapters discussed chunks themselves: `ChunkStatus` determines generation progress, `ChunkLevelType` determines runtime qualification. But entities aren't simply stuffed into `WorldChunk` to compute alongside blocks. Minecraft uses a separate specialized management system for entities: block data answers "what block is at this coordinate," the entity system answers "what movable, syncable, savable objects exist in this space."

## Why Entities and Blocks Are Managed Separately

Block storage is in a chunk's `ChunkSection[]`, where each `ChunkSection` is a 16×16×16 block state array; entities are stored in `ServerEntityManager`, and the entity manager builds indexes by chunk / section. In other words, blocks and entities are two independent data structures, two independent loading/unloading mechanisms: `World.getBlockState()` can only retrieve `BlockState` from a chunk's block array, can't "incidentally" get entities; similarly, entity queries go through `EntityLookup`, won't trigger new chunk loading just to find entities.

## ServerEntityManager's Responsibilities

`ServerEntityManager` is the server entity manager. It doesn't manage "where a specific entity currently is," but rather entity storage and indexing grouped by chunk / section: `SectionedEntityCache` is responsible for placing entities into corresponding `EntityTrackingSection`, `EntityIndex` handles quick lookups by UUID / id, `trackingStatuses` records each chunk's current corresponding `EntityTrackingStatus`. When an entity moves to another section, the entity's own `EntityChangeListener` calls back to the manager, moving it from the old section to the new section, and decides whether to start or stop tracking, start or stop ticking based on new/old tracking status.

Loading and unloading are also coordinated here. `WorldChunk.loadEntities()` executes the `EntityLoader` saved during chunk construction, ultimately delivering the entity stream read from NBT to `ServerWorld.addEntities()` / `ServerEntityManager.loadEntities()`, mounting them into the entity manager. During unloading, `ServerEntityManager.unload(ChunkPos)` first calls `trySave()` to write this chunk's savable entities to the `entities` region file, then marks these entities as `UNLOADED_TO_CHUNK` and removes them from memory management state. Whether entities are visible to clients, whether they participate in ticking, is represented by `EntityTrackingStatus`: `HIDDEN` doesn't track or tick, `TRACKED` syncs but doesn't tick, `TICKING` both syncs and ticks.

## EntityTracker and Player Sync

An entity "existing on the server" and "being visible to a certain player's client" are not the same thing. TACS (`ThreadedAnvilChunkStorage`) internally maintains `entityTrackers`: an `Int2ObjectMap<EntityTracker>`, where keys are entity network ids and values are corresponding entity trackers. When an entity enters a trackable state, `ServerEntityManager` calls `EntityHandler.startTracking()`, then `ServerWorld.ServerEntityHandler` delivers the entity to TACS's `loadEntity()`, creating an `EntityTracker`.

Each `EntityTracker` holds an `EntityTrackerEntry`, recording the entity's last synced state to clients. `EntityTracker.updateTrackedStatus(player)` compares horizontal distance between player and entity: when distance doesn't exceed `min(entity type tracking distance, view distance * 16)`, and the entity allows observation by that player, it adds the player's network connection to the listener set and sends a spawn packet; otherwise removes the listener and sends a remove packet. The tracking range here is jointly limited by "entity type's own maximum tracking distance" and "server view distance," and whether the entity actually computes still depends on simulation distance and `ENTITY_TICKING` — they're related but not the same switch.

## ENTITY_TICKING Prerequisites

Chapter 7 already showed that `makeChunkEntitiesTickable()` doesn't just wait for the center chunk itself to reach `FULL`, but calls `getRegion(holder, 2, distance -> ChunkStatus.FULL)`, requiring a 5×5 range centered on the center chunk to all reach `FULL`. This is stricter than `makeChunkTickable()`'s 3×3: block ticking only needs a closer neighborhood, while entity movement, collision, pathfinding, and spawn determination more easily cross chunk boundaries. The final level threshold still comes from `ChunkLevels.shouldTickEntities(level)`: only chunks with `level <= 31` have entity computation qualification.

## Entity Queries Don't Trigger Chunk Loading

The underlying implementation of `World.getEntitiesByClass()` / `World.getEntitiesByType()` is `getEntityLookup().forEachIntersects(...)`: it only searches for intersecting entities in the entity index currently held by the entity manager, won't request `ChunkStatus.FULL` like chunk reading, and won't add loading tickets. This echoes Chapter 5's conclusion: entity queries and block queries are two separate mechanisms. Block queries ask "is a certain chunk's block array accessible," entity queries ask "are there objects in the currently loaded, mounted entity index."

## Summary

- Block data is in `ChunkSection[]`, entity data is in `ServerEntityManager`; they're independently stored, loaded, and unloaded.
- `ServerEntityManager` handles entity chunk / section grouping, loading/saving, tracking state switching, and start/stop tracking and start/stop ticking lifecycle callbacks.
- `EntityTracker` handles network sync: maintains nearby player sets for each entity, sends spawn / update / remove packets based on distance.
- `ENTITY_TICKING` requires level ≤ 31, and `makeChunkEntitiesTickable()` requires a 5×5 `FULL` chunk context.
- Entity queries only search entities already loaded into the entity manager, won't trigger new chunk loading.

## :advanced Code Walkthrough

### ServerEntityManager.trySave() and unload()

`ServerEntityManager`'s save logic starts from `trySave(long chunkPos, Consumer<T> action)`:

```java
private boolean trySave(long chunkPos, Consumer<T> action) {
    ServerEntityManager.Status status = this.managedStatuses.get(chunkPos);
    if (status == ServerEntityManager.Status.PENDING) {
        return false;
    }

    List<T> list = this.cache
        .getTrackingSections(chunkPos)
        .flatMap(section -> section.stream().filter(EntityLike::shouldSave))
        .collect(Collectors.toList());
    if (list.isEmpty()) {
        if (status == ServerEntityManager.Status.LOADED) {
            this.dataAccess.writeChunkData(new ChunkDataList<>(new ChunkPos(chunkPos), ImmutableList.of()));
        }

        return true;
    } else if (status == ServerEntityManager.Status.FRESH) {
        this.scheduleRead(chunkPos);
        return false;
    } else {
        this.dataAccess.writeChunkData(new ChunkDataList<>(new ChunkPos(chunkPos), list));
        list.forEach(action);
        return true;
    }
}
```

Three states need clarification: `PENDING` means the chunk's entity data is still being read asynchronously, can't save now; `FRESH` means the manager hasn't read this chunk's entity data yet, saving rashly would overwrite old entities on disk, so it first calls `scheduleRead()` and returns failure; `LOADED` means entity data has been read or confirmed empty, can safely write back. The save target comes from `cache.getTrackingSections(chunkPos)`, meaning all entities in all sections under this chunk that `shouldSave()`, not from `WorldChunk`'s block data.

`unload(ChunkPos chunkPos)` first calls `trySave` to write data, then marks entities as unloaded:

```java
public void unload(ChunkPos chunkPos) {
    long l = chunkPos.toLong();
    this.trySave(l, entity -> entity.setRemovalReason(Entity.RemovalReason.UNLOADED_TO_CHUNK));

    this.managedStatuses.remove(l);
    this.cache.getTrackingSections(l).forEach(section -> {
        section.getEntities().filter(entity -> !entity.shouldSave()).forEach(entity -> {
            entity.setRemovalReason(Entity.RemovalReason.DISCARDED);
        });
    });
}
```

`setRemovalReason(UNLOADED_TO_CHUNK)` marks the entity as "temporarily unloaded," distinguished from permanent removal (`DISCARDED` / `KILLED`). These entities will be reloaded in the next `WorldChunk.loadEntities()` when the chunk loads again.

### `trackingStatuses`: How Entity Tracking Status Changes

`ServerEntityManager.trackingStatuses` is an `Int2ObjectMap<Tracking>`, recording the current `EntityTrackingStatus` for each chunk:

```java
public enum EntityTrackingStatus {
    HIDDEN,   // Not tracked, not ticking
    TRACKED,  // Tracked, not ticking
    TICKING   // Tracked and ticking
}
```

`HIDDEN` means entities in this chunk neither sync to clients nor participate in ticking — often regions far beyond view distance but not yet unloaded.

`TRACKED` means entities can sync to clients but don't tick — regions within view distance but outside simulation distance.

`TICKING` means entities both sync to clients and participate in ticking — regions within simulation distance.

When a chunk's level changes, `ChunkTicketManager.tick()` calls `ServerEntityManager.updateTrackingStatus(chunkPos)`:

```java
void updateTrackingStatus(long chunkPos, EntityTrackingStatus trackingStatus) {
    Tracking tracking = this.trackingStatuses.get(chunkPos);

    if (tracking != null && tracking.getStatus() == trackingStatus) {
        return;
    }

    if (trackingStatus == EntityTrackingStatus.HIDDEN) {
        if (tracking != null) {
            tracking.updateStatus(EntityTrackingStatus.HIDDEN, this.listener);
            this.trackingStatuses.remove(chunkPos);
        }
    } else {
        if (tracking != null) {
            tracking.updateStatus(trackingStatus, this.listener);
        } else {
            this.trackingStatuses.put(chunkPos, new Tracking(chunkPos, trackingStatus, this.listener));
        }
    }
}
```

Key point: when the new status is `HIDDEN`, remove the record from `trackingStatuses`; otherwise create or update. The actual start/stop tracking and ticking logic is in `Tracking.updateStatus()`:

```java
void updateStatus(EntityTrackingStatus status, Listener listener) {
    EntityTrackingStatus old = this.status;
    this.status = status;

    boolean oldTracked = old.shouldTrack();
    boolean newTracked = status.shouldTrack();

    if (oldTracked && !newTracked) {
        this.sections.forEach(section -> section.getEntities().forEach(listener::stopTracking));
    } else if (!oldTracked && newTracked) {
        this.sections.forEach(section -> section.getEntities().forEach(listener::startTracking));
    }

    boolean oldTicking = old.shouldTick();
    boolean newTicking = status.shouldTick();

    if (oldTicking && !newTicking) {
        this.sections.forEach(section -> section.getEntities().forEach(listener::stopTicking));
    } else if (!oldTicking && newTicking) {
        this.sections.forEach(section -> section.getEntities().forEach(listener::startTicking));
    }
}
```

The listener here is `ServerWorld.ServerEntityHandler`, which actually calls TACS's `loadEntity()` / `unloadEntity()` and entity system's `startTick()` / `stopTick()`.

### WorldChunk.loadEntities(): Mounting Entities from NBT

When `WorldChunk` is created, the constructor saves an `EntityLoader`:

```java
public WorldChunk(ServerWorld world, ProtoChunk protoChunk, ...) {
    ...
    if (protoChunk instanceof ReadOnlyChunk) {
        this.entityLoader = ((ReadOnlyChunk)protoChunk).getEntityLoader();
    } else {
        this.entityLoader = null;
    }
}
```

`ReadOnlyChunk` is the result from `SerializedChunkDataLoader.loadChunk()`, which wraps the entity NBT list read from the region file. When the chunk is actually mounted (`makeChunkAccessible`), TACS calls `chunk.loadEntities()`:

```java
public void loadEntities() {
    if (this.entityLoader != null) {
        this.entityLoader.run(this);
        this.entityLoader = null;
    }
}
```

This loader ultimately calls `addEntitiesFromNbt()`:

```java
private static void addEntitiesFromNbt(ServerWorld world, List<NbtCompound> nbt) {
    if (!nbt.isEmpty()) {
        world.addEntities(EntityType.streamFromNbt(nbt, world));
    }
}
```

`ServerWorld.addEntities()` then delivers the entity stream to `ServerEntityManager.loadEntities()`. Therefore, `WorldChunk` here is more like a "transfer station triggering mounting": it holds entity NBT from chunk NBT, but entities actually entering the running, query, save, and tracking systems is completed in `ServerEntityManager`. Correspondingly, `ServerWorld.unloadEntities(WorldChunk chunk)` only cleans up block entities and tick scheduler on `WorldChunk`:

```java
public void unloadEntities(WorldChunk chunk) {
    chunk.clear();
    chunk.removeChunkTickSchedulers(this);
}
```

The method name here is misleading: it doesn't directly retrieve and unload regular entities from `WorldChunk`, because regular entities weren't stored in `WorldChunk`'s block array to begin with; the actual entity save and unload is still completed by `ServerEntityManager`'s `pendingUnloads`, `trySave()`, and `unload()`.
