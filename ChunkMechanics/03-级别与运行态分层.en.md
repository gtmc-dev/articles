In the last chapter we learned about `ChunkStatus` — it answers "how much of this chunk has been generated".

But Minecraft has another dimension of question: "what is this chunk **currently doing**?" — Can it be accessed by normal code? Is it running block ticks? Are entities moving?

These two questions are answered by two different systems.

## ChunkStatus ≠ Chunk Heat

This is a common confusion that must first be clarified:

| | ChunkStatus | ChunkLevel / ChunkLevelType |
|---|---|---|
| **Question Answered** | "How far has this chunk been generated?" | "What operations is this chunk currently allowed to perform?" |
| **Determining Factor** | Whether generation pipeline stages are complete | Loading level calculated by the loading ticket system |
| **Change Timing** | Generation progression (usually irreversible) | Loading ticket additions/removals (dynamic up/down) |
| **Typical Values** | `EMPTY`, `BIOMES`, ..., `FULL` | `ENTITY_TICKING`, `BLOCK_TICKING`, `FULL`, `INACCESSIBLE` |

One-sentence summary: **ChunkStatus manages "how much generated", ChunkLevelType manages "what can currently do".**

A chunk can be in `ChunkStatus = FULL` (generation complete) while simultaneously in `ChunkLevelType = INACCESSIBLE` (not accessible) — this is the precise source code explanation for "distant terrain generated but not ticking".

## Loading Level (ChunkLevel)

Loading level is an **integer** that determines a chunk's loading or generation state. Key rules:

- Value range is 44 and below (usually not lower than 11);
- **Lower values mean the chunk is loaded more "thoroughly"**;
- Relationship between loading level and loading distance: `Loading level = 33 - Loading distance`.

For example, a ticket with `radius = 2` gives the center chunk loading level `33 - 2 = 31` (strong loading), and each step outward in Chebyshev distance adds +1 to loading level.

> [!IMPORTANT]
> The upper limit for loading level is **44**. `INACCESSIBLE = 33 + ChunkStatus.getMaxDistanceFromFull()`. In 1.20.1, `getMaxDistanceFromFull()` returns 11, so `INACCESSIBLE = 33 + 11 = 44`. The highest loading level for inaccessible chunks is 44.

## ChunkLevelType: Four Types of Runtime Eligibility

`ChunkLevels.getType(level)` maps loading level to four **`ChunkLevelType`** values:

```java
// Judgment rules
public static ChunkLevelType getType(int level) {
    if (level <= 31) return ChunkLevelType.ENTITY_TICKING;    // Strong loading
    else if (level <= 32) return ChunkLevelType.BLOCK_TICKING; // Weak loading
    else return level <= 33 ? ChunkLevelType.FULL : ChunkLevelType.INACCESSIBLE;
}
```

Precise meaning of the four types:

| ChunkLevelType | Corresponding Level | Block State Accessible | Block Ticks/Redstone | Entity Ticking | Mob Spawning | Client Rendering |
|---|---|---|---|---|---|---|
| `ENTITY_TICKING` | ≤ 31 | ✅ | ✅ | ✅ | ✅ | ✅ |
| `BLOCK_TICKING` | 32 | ✅ | ✅ | ❌ | ❌ | ✅ |
| `FULL` | 33 | ✅ | ❌ | ❌ | ❌ | ❌ |
| `INACCESSIBLE` | ≥ 34 | ❌ | ❌ | ❌ | ❌ | ❌ |

Explained one by one:

### ENTITY_TICKING (Strong Loading, ≤31)

**Most complete runtime state**. Almost all computational logic proceeds normally within the chunk — block ticks (including redstone operations and random ticks), entity AI and movement, mob spawning checks, block entity updates. "Chunks around the player" are typically in this state.

### BLOCK_TICKING (Weak Loading, 32)

The **only difference from strong loading is entity ticking is suspended**. Redstone devices, fluids, scheduled ticks, etc. still run normally. In `World#setBlockState`, you can see the server only triggers client synchronization when the current chunk reaches `BLOCK_TICKING` level. Weak loading chunks are still rendered on the client.

### FULL (Border Loading, 33)

Chunk data is **in memory for reading and writing**, but almost no active operations are executed. Block states can be queried, entities can be recorded (count toward mob cap), but there are no block ticks, redstone operations, or entity movement. The client doesn't render chunks at this level.

This is the "transition zone" — the chunk is loaded enough for nearby chunks to reference its state, but not enough to waste CPU on running its own operations.

### INACCESSIBLE (Unloaded, ≥34)

**Not in active memory**. May be waiting to be generated, or may be queued for unloading. Attempting to access block states will return null or air. Cannot be accessed by normal game logic.

> [!NOTE]
> Why is it called "INACCESSIBLE" rather than "UNLOADED"?
> Because chunks at this level may not have been completely unloaded — they're just "not yet available" or "about to be unavailable". `UNLOADED` would imply the memory state has been cleared, but the ticket system only decides "access eligibility", not directly managing memory release.

## Level Transition: Two-Way Upgrade/Downgrade

Unlike `ChunkStatus` (which advances in one direction during generation), `ChunkLevelType` **changes dynamically bidirectionally**:

- Tickets added → loading level decreases → type may upgrade (`FULL` → `BLOCK_TICKING` → `ENTITY_TICKING`);
- Tickets removed → loading level increases → type may downgrade (`ENTITY_TICKING` → `BLOCK_TICKING` → `FULL` → `INACCESSIBLE`).

Upgrade and downgrade operations in `ChunkHolder`:

```java
// Upgrade: Request higher status
private CompletableFuture<Either<Chunk, Unloaded>> createUpdateFuture(
    ChunkStatus targetStatus, ...) {
    // If current status < target status → schedule generation task
}

// Downgrade: Cancel unreachable status
public void tick() {
    // If new level < old level → set unnecessary Futures to UNLOADED
}
```

Two points deserve attention:

**Upgrade is asynchronous (via CompletableFuture)**: Because generation requires computation time, upgrade tasks are scheduled into the task queue for execution in a future async phase.

**Downgrade is synchronous (immediately invalidate Futures)**: Because downgrade is just "declaring unavailable", no actual data needs to be cleared — just mark corresponding Futures as complete with `UNLOADED_WORLD_CHUNK`, notifying all waiters "this Future is now invalid".

## Common Misconceptions

| Misconception | Reality |
|---|---|
| "If the client can see it, the server is ticking it" | Client rendering is controlled by view distance, while server ticking is controlled by simulation distance. They are independent parameters. |
| "FULL means random ticks run" | `FULL` only guarantees that data is accessible. Random ticks require `BLOCK_TICKING` (`level <= 32`). |
| "Loaded means mobs can spawn" | Mob spawning requires `ENTITY_TICKING` (`level <= 31`). |
| "Near the player means spawning definitely happens" | Spawning still requires additional conditions such as light, space, and mob cap. `ENTITY_TICKING` is necessary, but not sufficient. |
| "Force-loading means everything will run" | `/forceload` achieves `ENTITY_TICKING` via a `FORCED` ticket, but actual operations are still constrained by gamerules, chunk state, and other conditions. |

## Summary

- `ChunkStatus` governs "generation progress," while `ChunkLevelType` governs "runtime eligibility." They answer different questions.
- The four runtime eligibility states progress by level as `INACCESSIBLE` → `FULL` → `BLOCK_TICKING` → `ENTITY_TICKING`.
- Strong loading (`<=31`) allows all operations, weak loading (`32`) suspends entities, border loading (`33`) allows queries only, and inaccessible (`>=34`) is externally invisible.
- The essence of "generated but no longer ticking" is `ChunkStatus = FULL` while `ChunkLevelType != ENTITY_TICKING`.

## [!ADVANCED] Code Walkthrough

### ChunkLevels Threshold Design: Why 31/32/33?

```java
// ChunkLevels.java
private static final int ENTITY_TICKING = 31;
private static final int BLOCK_TICKING = 32;
private static final int FULL = 33;
public static final int INACCESSIBLE = 33 + ChunkStatus.getMaxDistanceFromFull(); // = 44

public static ChunkLevelType getType(int level) {
    if (level <= 31)      return ChunkLevelType.ENTITY_TICKING;
    else if (level <= 32) return ChunkLevelType.BLOCK_TICKING;
    else                  return level <= 33
        ? ChunkLevelType.FULL : ChunkLevelType.INACCESSIBLE;
}
```

These three thresholds were not chosen arbitrarily. Their design is based on the ticket propagation model: a loading ticket has `level = 33 - radius`, and each chunk step outward adds +1 to the level. Therefore:

- `radius >= 2` → level `<= 31`: chunks within Chebyshev distance 2 of the player run **both entities and blocks**. This is the most important gameplay area, where mobs the player can directly see, redstone contraptions, and flowing water all run.
- `radius = 1` → level `= 32`: the ring one step farther out. **Blocks still run** there, including redstone, fluids, and scheduled ticks, but entities are suspended. The design intent of this ring is to preserve visual continuity while saving the CPU cost of entity simulation.
- `radius = 0` → level `= 33`: the outermost "border layer." Data is in memory, but **no active computation runs**. This layer exists so that when the player moves, chunks newly entering strong-loading range do not need to be regenerated. They are already prepared in memory in the `FULL` state.

**Why is `BLOCK_TICKING` 32 rather than some other value?** Notice that 32 = 33 - 1. It corresponds exactly to `radius = 1`, meaning chunks at Chebyshev distance 1 from the player. If it were 31, then even the `radius = 1` chunks would need strong loading, which would mean all entities in a 5×5 area around the player would be moving, at too high a cost. If it were 33, then `radius = 1` and `radius = 0` would be no different, meaning distant water would stop flowing and the visual effect would break.

### Enum Order Determines "Priority"

`ChunkLevelType` is declared as a standard Java enum:

```java
public enum ChunkLevelType {
    INACCESSIBLE,    // ordinal() = 0
    FULL,            // ordinal() = 1
    BLOCK_TICKING,   // ordinal() = 2
    ENTITY_TICKING;  // ordinal() = 3
    
    public boolean isAfter(ChunkLevelType chunkLevelType) {
        return this.ordinal() >= chunkLevelType.ordinal();
    }
}
```

`isAfter` semantically means "current level **at least meets** the requirement of parameter level". Because the declaration order is progressive (INACCESSIBLE → FULL → BLOCK_TICKING → ENTITY_TICKING), `ordinal()` directly reflects "strength of computational ability".

Here's an easily confused point: `isAfter` is **not** comparing "size of level numbers" (that's already done in `ChunkLevels`), but comparing "containment relationship of computational eligibility". `ENTITY_TICKING.isAfter(BLOCK_TICKING)` is true, because strong loading chunks automatically meet all conditions of weak loading. `FULL.isAfter(BLOCK_TICKING)` is false, because "can only read" doesn't meet the requirement of "must run block ticks".

### Why fill with UNLOADED rather than null during downgrade

When ChunkHolder downgrades, it needs to clear generation status Futures that are no longer needed:

```java
// ChunkHolder.tick()
if (bl) {  // old level was accessible
    Either<Chunk, Unloaded> either = Either.right(new Unloaded() { ... });
    for (int i = bl2 ? chunkStatus2.getIndex() + 1 : 0;
         i <= chunkStatus.getIndex(); i++) {
        if (this.futuresByStatus.get(i) == null) {
            this.futuresByStatus.set(i,
                CompletableFuture.completedFuture(either));
        }
    }
}
```

The loop runs from `0` to `old ChunkStatus.index`: if still accessible after downgrade (`bl2=true`), keep Futures for new level's corresponding status and above (start clearing from `new ChunkStatus.index + 1`); if no longer accessible after downgrade (`bl2=false`), clear everything starting from `0`.

**Why use `CompletableFuture.completedFuture(either)` instead of `set(i, null)`?** Because external code may have already obtained this Future through `getFutureFor(someStatus)` and registered callbacks (`.thenAccept()`). If set directly to `null`, those callbacks will wait forever, causing memory leaks. Setting to an already-completed Future (value is `Unloaded`) immediately notifies all waiters of "unavailable" and cleans up callbacks — this is the **graceful termination pattern** of `CompletableFuture`.

Note that `futuresByStatus` uses `AtomicReferenceArray` rather than a normal array — because generation threads and the main thread may access it simultaneously. `AtomicReferenceArray` provides lock-free concurrent safety guarantees, at the cost of one extra CAS operation overhead per element.
