Chapter 7 explained that completing the three `ChunkHolder` futures as `UNLOADED` only closes the corresponding runtime views. Players can no longer access a ticking `WorldChunk` through these futures, but the data may still remain in memory, waiting to be saved, have entities removed, light state released, and be removed from the table structure.

This chapter covers the second half: before a chunk truly leaves memory, how `ThreadedAnvilChunkStorage` (hereafter **TACS**) places it into a three-level unload structure, determines whether it needs to write to disk, converts the in-memory `Chunk` to NBT, and finally hands it to the `.mca` file system.

## Review: "Cooling" ≠ "Unloading"

Cooling is a **runtime state change**; unloading is a **resource reclamation process**. The former occurs in `ChunkHolder.tick()`: `accessibleFuture`, `tickingFuture`, and `entityTickingFuture` complete based on level changes. The latter occurs in TACS's unload-save pipeline: chunks are marked, moved from the current table to the pending unload table, and finally saved and cleared from memory by async tasks.

Therefore, seeing `UNLOADED` doesn't mean "data has disappeared." It's more like a door being closed: external access stops, but the contents inside still need to be inventoried, packed, and moved in order.

## Three-Level Unload Structure

TACS maintains three data structures related to unloading:

```java
// ThreadedAnvilChunkStorage.java (Yarn 1.20.1+build.10)
final LongSet unloadedChunks = new LongOpenHashSet();
private final Long2ObjectLinkedOpenHashMap<ChunkHolder> chunksToUnload = new Long2ObjectLinkedOpenHashMap<>();
private final Queue<Runnable> unloadTaskQueue = Queues.newConcurrentLinkedQueue();
```

The first level is `unloadedChunks`, the **unloaded chunk set**. It only stores `long` coordinates, not `ChunkHolder`. When `setLevel()` finds that a new chunk level is no longer accessible, it immediately adds the coordinate here:

```java
if (holder != null) {
    if (!ChunkLevels.isAccessible(level)) {
        this.unloadedChunks.add(pos);
    } else {
        this.unloadedChunks.remove(pos);
    }
}
```

This layer serves as "coordinate markers for chunks needing to enter the unload process." It's lightweight, only recording the fact: this position has dropped below the range where TACS should continue to maintain a `ChunkHolder` externally.

The second level is `chunksToUnload`, the **pending unload chunk mapping**. When `unloadChunks()` processes `unloadedChunks`, it removes the `ChunkHolder` from `currentChunkHolders` and puts it into `chunksToUnload`:

```java
ChunkHolder chunkHolder = this.currentChunkHolders.remove(pos);
if (chunkHolder != null) {
    this.chunksToUnload.put(pos, chunkHolder);
    this.chunkHolderListDirty = true;
    this.tryUnloadChunk(pos, chunkHolder);
}
```

The key here is "temporarily storing the complete `ChunkHolder`." When a chunk just leaves the current table, the save future may not yet be stable, and async generation or conversion tasks may have just completed. Discarding the holder immediately would leave these trailing tasks without a landing point. More importantly, if the same coordinate is quickly pulled back to accessible by the ticket system, `setLevel()` will first retrieve the old holder from `chunksToUnload`:

```java
holder = this.chunksToUnload.remove(pos);
if (holder != null) {
    holder.setLevel(level);
} else {
    holder = new ChunkHolder(new ChunkPos(pos), level, ...);
}
```

This is reuse: when players walk back and forth across chunk boundaries, the chunk doesn't need to create a new `ChunkHolder` every time, nor reassemble the same intermediate state after unloading and immediately reloading.

The third level is `unloadTaskQueue`, the **unload task queue**. `tryUnloadChunk()` doesn't save and clean up directly in the current call stack, but passes the callback of `holder.getSavingFuture()` to this queue:

```java
completableFuture.thenAcceptAsync(chunk -> {
    // Save, remove entities, refresh light state, etc.
}, this.unloadTaskQueue::add);
```

Then `unloadChunks()` retrieves and executes a batch of `Runnable` from the queue each tick. The real trailing work happens here: `WorldChunk.setLoadedToWorld(false)`, `save(chunk)`, `world.unloadEntities(worldChunk)`, `lightingProvider.updateChunkStatus()`, `chunkToNextSaveTimeMs.remove()`, etc.

In summary, the three-level structure separates "marking that unload is needed," "temporarily holding state to allow reuse or future completion," and "actual resource cleanup and disk write." This avoids immediately discarding holders on level drop or immediately blocking the main thread waiting for file I/O.

## Save Throttling

TACS doesn't save chunks unconditionally every time. After each chunk save, it records a timestamp, and the next save for the same chunk must wait at least 10 seconds. This throttling prevents short-term repeated saves from consuming too many I/O operations and avoids write amplification in areas with high activity.

The implementation uses a `Long2LongOpenHashMap chunkToNextSaveTimeMs` to map chunk positions to the next allowed save time. Before `save(ChunkHolder)` triggers serialization, it checks:

```java
long l = chunk.getPos().toLong();
long m = this.chunkToNextSaveTimeMs.getOrDefault(l, -1L);
long n = System.currentTimeMillis();
if (n < m) {
    return false;
}
```

If the current time hasn't reached the recorded cooldown, save is skipped and `false` is returned. Only after a successful save does the code update the next save time to `n + 10000L` (10 seconds later).

This throttling only applies to the incremental save path in `save(ChunkHolder)`. During normal shutdown, `save(flush=true)` bypasses the cooldown and forces all dirty chunks to be written.

## When Save Is Triggered

Chunk saves aren't only initiated at server shutdown. During normal runtime, TACS saves chunks through multiple paths:

1. **Incremental saves during tick**: `unloadChunks()` saves up to 20 dirty chunks per tick.
2. **Auto-save every 6000 ticks**: `ServerChunkManager.save(boolean suppressLogs)` with `flush=false`, doesn't wait for I/O completion.
3. **Manual `/save-all`**: Same auto-save path, but user-initiated.
4. **Save before unload**: `save(Chunk)` is called in the callback of `tryUnloadChunk()`.
5. **Normal shutdown**: `save(false, true, false)` with `flush=true`, bypasses cooldown, waits for all async writes, and flushes to disk.

Shutdown save is most aggressive, with three key differences:

- `flush=true` calls `StorageIoWorker.completeAll(true)`, waits for all `CompletableFuture`, and force-flushes the file channel.
- Iterates over all holders, ignoring cooldown.
- Calls `pointOfInterestStorage.saveChunk()` and waits for POI writes to complete.

Auto-save and incremental saves use `flush=false`, meaning NBT tasks are submitted to `StorageIoWorker`, but the main thread doesn't wait for write completion. This avoids blocking normal tick progression.

## ChunkSerializer: From Object to NBT

Chunk serialization is handled by `ChunkSerializer`, which provides two static methods:

```java
public static ChunkSerializer.ProtoChunkData deserialize(
    ServerWorld world,
    StructureTemplateManager structureTemplateManager,
    PointOfInterestStorage poiStorage,
    ChunkPos expectedPos,
    NbtCompound nbt
)

public static NbtCompound serialize(
    ServerWorld world,
    Chunk chunk
)
```

`serialize()` converts an in-memory `Chunk` into an `NbtCompound`:

- Writes block states for all sections (including empty sections if they contain non-air blocks)
- Serializes all block entities (chest inventories, furnace states, etc.)
- Serializes scheduled ticks (`block_ticks` and `fluid_ticks`)
- Writes heightmaps, biome palette, light data, entities (for `ProtoChunk`), and structure references

The serialized NBT is the complete snapshot that will be written to the region file. Note that POI (Point of Interest) is saved separately through `PointOfInterestStorage` and doesn't go through `ChunkSerializer`—Chapter 12 will cover this bypass path.

`deserialize()` does the reverse: reads NBT and reconstructs a `ProtoChunk` (for chunks not yet at `FULL` status) or wraps upgrade data into `ProtoChunkData`. If the chunk on disk is at `FULL` status, TACS will directly construct a `WorldChunk` from the deserialized data.

## StorageIoWorker: Async Write Queue

`ChunkSerializer` only handles memory-to-NBT conversion. The actual file I/O is delegated to `StorageIoWorker`, which manages async write tasks.

`ThreadedAnvilChunkStorage` has one worker per dimension:

```java
private final StorageIoWorker worker;
```

When `save(Chunk)` needs to write a chunk, it calls:

```java
private boolean save(Chunk chunk) {
    this.pointOfInterestStorage.saveChunk(chunk.getPos());
    if (!chunk.needsSaving()) {
        return false;
    }
    chunk.setNeedsSaving(false);
    ChunkPos chunkPos = chunk.getPos();
    try {
        ChunkStatus chunkStatus = chunk.getStatus();
        if (chunkStatus.getChunkType() != ChunkType.LEVELCHUNK) {
            // ...
        }
        NbtCompound nbtCompound = ChunkSerializer.serialize(this.world, chunk);
        this.setNbt(chunkPos, nbtCompound);
        return true;
    } catch (Exception e) {
        // ...
    }
}
```

`setNbt()` pushes the NBT write task to `worker`:

```java
protected void setNbt(ChunkPos pos, NbtCompound nbt) {
    this.worker.setResult(pos, nbt);
}
```

Inside `StorageIoWorker`, `setResult()` wraps a `CompletableFuture` representing the write task and adds it to the queue. The worker thread continuously polls tasks and writes them through `RegionBasedStorage` to the region file. If `completeAll(waitForResult=false)` is called, tasks are only submitted but not waited on; if `waitForResult=true`, the caller blocks until all futures complete and the file channel is flushed.

This design separates NBT serialization (done on the main thread) from file I/O (offloaded to worker threads). The main thread doesn't block on I/O during normal operation; only during shutdown does it synchronously wait for all writes to finish.

## Unload Task Execution

The trailing work of chunk unloading is handled by `unloadTaskQueue`. When `tryUnloadChunk()` schedules a save callback, it includes these cleanup steps:

```java
completableFuture.thenAcceptAsync(chunk -> {
    CompletableFuture<?> savingFuture = CompletableFuture.completedFuture(chunk);
    if (chunk instanceof WorldChunk worldChunk) {
        worldChunk.setLoadedToWorld(false);
        savingFuture = this.save(chunk) ? CompletableFuture.completedFuture(chunk)
                                        : this.getUnloadedChunkFuture();
    }

    // Save, unload entities, update light state
    this.world.unloadEntities(worldChunk);
    this.lightingProvider.updateChunkStatus(pos);
    this.chunkToNextSaveTimeMs.remove(pos);

    this.chunksToUnload.remove(pos);
}, this.unloadTaskQueue::add);
```

Each tick, `unloadChunks()` drains up to 20 runnables from the queue (controlled by `shouldKeepTicking` to avoid timeout):

```java
while (this.unloadTaskQueue.size() > 0 && shouldKeepTicking.getAsBoolean()) {
    Runnable runnable = this.unloadTaskQueue.poll();
    if (runnable != null) {
        runnable.run();
    }
}
```

Tasks run on the main thread since they involve world state (unloading entities, updating light). After completion, the chunk holder is removed from `chunksToUnload`, and the position is freed.

## Save vs. Unload: Two Parallel Concerns

It's crucial to distinguish: **save and unload are not atomic**. Unload refers to removing from memory; save refers to writing to disk. A chunk may be saved without being unloaded (incremental save during runtime), or unloaded without being saved (if marked as not needing save, e.g., `needsSaving() == false`).

`save(Chunk)` checks `chunk.needsSaving()` before serializing. Only if the chunk is dirty (block states, block entities, or scheduled ticks changed) does it proceed with NBT conversion and submit to `StorageIoWorker`. If not dirty, save is skipped and the method returns `false`.

Unload, on the other hand, is controlled by level changes and ticket expiry. Even if a chunk hasn't changed since last save, when tickets drop and the level becomes inaccessible, the chunk still enters `unloadedChunks` → `chunksToUnload` → `unloadTaskQueue` to release memory.

During shutdown save, since `flush=true`, the server bypasses cooldown, waits for all write futures, and force-flushes channels. This ensures dirty state is committed to disk before process exit. But during normal runtime auto-save or incremental save, `flush=false` means the main thread submits write tasks without waiting—write completion is fire-and-forget.

## Summary

- Unload is not immediate level-drop eviction but a three-stage pipeline: mark → pending table → async cleanup queue.
- TACS maintains `unloadedChunks`, `chunksToUnload`, and `unloadTaskQueue` to manage the unload lifecycle.
- Save throttling uses a 10-second cooldown per chunk, skipping saves if the cooldown hasn't expired; shutdown save bypasses this cooldown.
- `ChunkSerializer` converts `Chunk` to NBT; `StorageIoWorker` handles async file I/O.
- Auto-save uses `flush=false` (fire-and-forget); shutdown save uses `flush=true` (wait for all writes and force flush).
- Save and unload are orthogonal: a chunk can be unloaded without being saved (if not dirty), or saved without being unloaded (incremental save).

## :advanced Code Walkthrough

### unloadChunks: Top-Level Orchestration

`unloadChunks()` is called every server tick from `tick()` and orchestrates all three unload levels:

```java
private void unloadChunks(BooleanSupplier shouldKeepTicking) {
    LongIterator longIterator = this.unloadedChunks.iterator();
    for (int i = 0; longIterator.hasNext() && (i < 200 || shouldKeepTicking.getAsBoolean()); ++i) {
        long pos = longIterator.nextLong();
        longIterator.remove();
        ChunkHolder chunkHolder = this.currentChunkHolders.remove(pos);
        if (chunkHolder != null) {
            this.chunksToUnload.put(pos, chunkHolder);
            this.chunkHolderListDirty = true;
            this.tryUnloadChunk(pos, chunkHolder);
        }
    }

    int k = 0;
    ObjectIterator<ChunkHolder> objectIterator = this.chunkHolders.values().iterator();
    while (k < 20 && shouldKeepTicking.getAsBoolean() && objectIterator.hasNext()) {
        if (this.save(objectIterator.next())) {
            k++;
        }
    }

    Runnable runnable;
    while (this.unloadTaskQueue.size() > 0 && shouldKeepTicking.getAsBoolean()) {
        runnable = this.unloadTaskQueue.poll();
        if (runnable != null) {
            runnable.run();
        }
    }
}
```

Phase 1 moves marked chunks from `currentChunkHolders` to `chunksToUnload` and schedules their save futures. Phase 2 performs incremental saves on up to 20 dirty holders. Phase 3 drains the unload task queue, executing finalization runnables on the main thread.

### tryUnloadChunk: Scheduling Save and Cleanup

```java
private void tryUnloadChunk(long pos, ChunkHolder holder) {
    CompletableFuture<Chunk> completableFuture = holder.getSavingFuture();
    completableFuture.thenAcceptAsync(chunk -> {
        CompletableFuture<?> savingFuture = CompletableFuture.completedFuture(chunk);
        if (chunk instanceof WorldChunk worldChunk) {
            worldChunk.setLoadedToWorld(false);
            savingFuture = this.save(chunk) ? CompletableFuture.completedFuture(chunk)
                                            : this.getUnloadedChunkFuture();
        }

        this.world.unloadEntities(worldChunk);
        this.lightingProvider.updateChunkStatus(ChunkPos.fromLong(pos), null);
        this.chunkToNextSaveTimeMs.remove(pos);

        this.chunksToUnload.remove(pos);
    }, this.unloadTaskQueue::add);
}
```

The callback waits for `getSavingFuture()` to complete (ensuring generation or upgrade is finished), then saves if the chunk is a `WorldChunk`, unloads entities, clears light state, removes cooldown entry, and finally removes the holder from `chunksToUnload`.

### save(Chunk): Serialization and Worker Submission

```java
private boolean save(Chunk chunk) {
    this.pointOfInterestStorage.saveChunk(chunk.getPos());
    if (!chunk.needsSaving()) {
        return false;
    }
    chunk.setNeedsSaving(false);
    ChunkPos chunkPos = chunk.getPos();
    try {
        ChunkStatus chunkStatus = chunk.getStatus();
        if (chunkStatus.getChunkType() != ChunkType.LEVELCHUNK) {
            if (this.shouldSkipSave(chunkStatus)) {
                return false;
            }
            NbtCompound nbtCompound = ChunkSerializer.serialize(this.world, chunk);
            this.setNbt(chunkPos, nbtCompound);
            return true;
        }

        NbtCompound nbtCompound = ChunkSerializer.serialize(this.world, chunk);
        this.setNbt(chunkPos, nbtCompound);
        return true;
    } catch (Exception e) {
        // ...
    }
}
```

First saves POI via `pointOfInterestStorage.saveChunk()`. Then checks `needsSaving()`—if false, skip. If true, serializes with `ChunkSerializer.serialize()` and submits NBT to `StorageIoWorker` via `setNbt()`.

### StorageIoWorker.completeAll: Flush vs. Fire-and-Forget

```java
public CompletableFuture<Void> completeAll(boolean sync) {
    CompletableFuture<Void> completableFuture = CompletableFuture.allOf(
        this.results.values().toArray(new CompletableFuture[0])
    );
    if (sync) {
        return completableFuture.thenCompose(v -> this.run(() -> {
            try {
                this.storage.sync();
            } catch (Exception e) {
                LOGGER.error("Failed to synchronize chunks", e);
            }
        }));
    }
    return completableFuture.thenCompose(v -> this.run(() -> {}));
}
```

When `sync=true`, the method waits for all write futures and calls `storage.sync()`, which flushes the underlying `FileChannel`. When `sync=false`, it just waits for all futures without forcing a flush—the OS may buffer writes.
