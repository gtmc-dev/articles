Chapter 3 already mentioned: after a chunk reaches **block ticking level** (`BLOCK_TICKING`), the server allows three types of block computation — **Scheduled Tick**, **Random Tick**, and **Block Entity Tick**. For scheduled tick details, see [MicroTiming: Scheduled Ticks and Scheduled Tick Components](../MicroTiming/计划刻与计划刻元件.zh.md); this chapter only fills in the other two: how random ticks and block entity ticks depend on chunk runtime levels.

## Random Ticks

Random tick is a mechanism that samples several random positions within a chunk each game tick, then has the sampled blocks or fluids execute their own random logic. It's not a scheduled tick: scheduled ticks have explicit trigger times, positions, types, and priorities, while random ticks have no reservation queue and don't guarantee a certain block will be executed at a certain gt. A crop block not being sampled for a long time is normal; the same position in a chunk being sampled on consecutive gt is equally possible.

Random ticks first depend on the **random tickable block count** (`randomTickableBlockCount`) introduced in Chapter 1. Each **chunk section** incrementally maintains this count when writing block states; when the count is 0, `ChunkSection.hasRandomTicks()` directly returns false, and `ServerWorld.tickChunk()` won't sample within this 16×16×16 region. The significance of this design isn't to make random ticks more "random," but to skip large numbers of stone, air, and building material sections with no random tick blocks in O(1) time.

Sampling frequency is controlled by **random tick speed** (`randomTickSpeed`, game rule). The server executes `randomTickSpeed` samples for each random tickable section; the default value is 3, setting it to 0 completely skips the random tick loop. Note this game rule controls "how many coordinate samples per random tickable section per gt," not "how many times each crop ticks per gt." Therefore, increasing `randomTickSpeed` increases sampling opportunities but doesn't turn random ticks into deterministic periodic ticks.

What typically needs random ticks are blocks or fluids that "continuously exist in the world, occasionally change spontaneously," such as crop growth, grass block spread, leaf decay, fungus spread, fire changes, ice/snow-related changes, and some fluid logic. Their common characteristic is: they don't need to execute at a precise gt, yet need to gradually progress while the chunk maintains block ticking qualification.

From a macro timing perspective, random ticks and scheduled ticks both belong to the server's per-gt block computation phase (commonly called TT phase), and both depend on chunks reaching `BLOCK_TICKING`. But the two mechanisms are completely different: scheduled ticks are first retrieved from `WorldTickScheduler` as expired tasks during world tick progression, then call `scheduledTick()`; random ticks traverse sections and sample coordinates during chunk tick, then call `randomTick()` or fluid random tick methods. When studying scheduled tick order, don't insert random ticks into the scheduled tick queue; when studying crops, grass blocks, or leaves, don't assume they have a hidden scheduled tick.

## Block Entity Ticks

Block entities are used to store or compute complex data that `BlockState` can't express. BlockMechanics Chapter 1 already outlined the division of labor: **Block State** is suitable for storing finite-valued, quick-lookup information; block entities are suitable for storing complex data like chest items, hopper cooldowns, beacon effects, and sign text. Not all block entities compute every gt, but those that do compute need to enter block entity ticks.

The entry point for block entity ticks isn't "traverse all block entities in a chunk then guess who needs to tick," but is registered by **block entity tickers**. `WorldChunk.updateTicker()` reads the block entity's cached `BlockState`, asks through `blockState.getBlockEntityTicker(world, type)` whether this state provides a ticker behind the **block entity tick invoker** (`BlockEntityTickInvoker`). If there's no ticker, it removes the old invoker; if there is a ticker, it wraps it as a `DirectBlockEntityTickInvoker`, then adds it to the world-level list through `World.addBlockEntityTicker()`.

Here the chunk field directly affects whether the ticker actually executes. `WorldChunk` holds `levelTypeProvider`, can query current `ChunkLevelType` at any time; the wrapped invoker checks `WorldChunk.canTickBlockEntity(pos)` before each `tick()`. On the server, this check requires the block position to be within world boundaries, the chunk still loaded, and `getLevelType().isAfter(ChunkLevelType.BLOCK_TICKING)`. In other words, the ticker can already be in the list, but after the chunk drops to `FULL`, the invoker is blocked before execution.

`World.addBlockEntityTicker()` is responsible for placing the invoker in the world's `blockEntityTickers` list; if currently traversing block entities, it first places it in `pendingBlockEntityTickers`, merging next round to avoid modifying the list during traversal. Then `World.tickBlockEntities()` traverses these invokers each gt: removed invokers are deleted from the list, still-tickable positions call `tick()`. The actual behavior is still determined by the block entity's own ticker.

Different block entities' internal cycles vary widely. Furnaces and moving pistons typically advance state each gt; hoppers enter the ticker each gt but use `transferCooldown` to form the common 8gt transfer rhythm; beacons update effects at roughly 80gt cycles in their own logic; sign block entities mainly store data and may not provide a server ticker. The chunk management system only determines "does this invoker qualify for execution," not the business cycle for each block entity type.

When chunks downgrade or unload, block entity ticks stop. When dropping to `FULL` or lower, `canTickBlockEntity()` no longer passes; even if the invoker remains in the world list, it won't execute the actual ticker; when a block entity is removed, `removeBlockEntityTicker()` replaces the wrapped invoker with a removed empty invoker, which is cleaned from the list during the next `World.tickBlockEntities()` traversal; when a chunk unloads, `WorldChunk.clear()` marks all block entities removed and clears the chunk's own ticker map.

## How It Connects with BLOCK_TICKING

`BLOCK_TICKING` isn't a separate "redstone switch," but a ticking view. Chapter 7 explained that after `ChunkHolder.tickingFuture` completes, the chunk enters a view that can perform block computation; this view supports scheduled ticks, random ticks, and block entity ticks upward.

The three computations depend on it in slightly different ways: scheduled ticks depend on `WorldTickScheduler` determining whether the target chunk's tick future is ready; random ticks depend on `ServerChunkManager` only delivering `WorldChunk` objects that have reached block computation qualification to `ServerWorld.tickChunk()`; block entity ticks check once more during world-level list traversal through `shouldTickBlockPos()` and `WorldChunk.canTickBlockEntity()` whether the chunk is still at `BLOCK_TICKING` or higher. The commonality: as long as the chunk returns to `FULL`, it can still be readable and writable in memory, but these active block computations should all stop.

## Common Misconceptions

| Misconception | Reality |
|---|---|
| "Random ticks are just randomly delayed scheduled ticks" | Random ticks have no reservation structure and don't enter the scheduled tick queue. They're per-gt coordinate sampling. |
| "`randomTickSpeed = 3` means each crop ticks once every 3gt" | It means each random tickable section samples 3 coordinate positions per gt. Whether a single block is sampled is uncertain. |
| "Block entities tick when chunks are accessible" | Accessible `FULL` isn't enough; server block entity tickers require chunks to at least reach `BLOCK_TICKING`. |
| "Block entity ticks equal entity ticks" | Block entities are fixed at block coordinates, belonging to block computation; normal entity movement and AI require `ENTITY_TICKING`. |

## Summary

- Random ticks are a per-gt coordinate sampling mechanism, not part of the scheduled tick queue.
- `randomTickableBlockCount` lets `ServerWorld.tickChunk()` skip sections with no random tick requirements.
- `randomTickSpeed` controls sampling frequency per random tickable section, not a fixed cycle for individual blocks.
- Block entity tickers are registered or removed by `WorldChunk.updateTicker()` based on current `BlockState`.
- `World.tickBlockEntities()` traverses the world-level invoker list, but still checks whether the block position allows ticking before actual execution.
- Scheduled ticks, random ticks, and block entity ticks all depend on the `BLOCK_TICKING` view; after chunks return to `FULL`, data can exist in memory but active block computation stops.

## [!ADVANCED] Code Walkthrough

### ServerWorld.tickChunk(): Random Tick Section

`ServerWorld.tickChunk(WorldChunk chunk, int randomTickSpeed)` processes a `WorldChunk` selected to participate in chunk tick. After weather, thunderstorm, ice/snow logic, the random tick body is in the `tickBlocks` profiler section:

```java
// ServerWorld.java
profiler.swap("tickBlocks");
if (randomTickSpeed > 0) {
    ChunkSection[] chunkSections = chunk.getSectionArray();

    for (int m = 0; m < chunkSections.length; m++) {
        ChunkSection chunkSection = chunkSections[m];
        if (chunkSection.hasRandomTicks()) {
            int n = chunk.sectionIndexToCoord(m);
            int o = ChunkSectionPos.getBlockCoord(n);

            for (int p = 0; p < randomTickSpeed; p++) {
                BlockPos blockPos = this.getRandomPosInChunk(i, o, j, 15);
                BlockState blockState = chunkSection.getBlockState(
                    blockPos.getX() - i,
                    blockPos.getY() - o,
                    blockPos.getZ() - j
                );
                if (blockState.hasRandomTicks()) {
                    blockState.randomTick(this, blockPos, this.random);
                }
                FluidState fluidState = blockState.getFluidState();
                if (fluidState.hasRandomTicks()) {
                    fluidState.onRandomTick(this, blockPos, this.random);
                }
            }
        }
    }
}
```

Three key points.

First, when `randomTickSpeed <= 0`, the entire random tick loop doesn't enter, so gamerule 0 turns off random ticks.

Second, the outer traversal is of the chunk's `ChunkSection[]`, not all 16×16×height blocks. `chunkSection.hasRandomTicks()` is exactly the counter filtering introduced in Chapter 1: if that section has no blocks or fluids declaring random tick requirements, no sampling occurs.

Third, sampling first retrieves the sampled `BlockState`, then separately checks whether the block state and fluid state truly `hasRandomTicks()`. This step shows "section is random tickable" is just coarse filtering; when a specific coordinate samples air, stone, or other non-random-ticking blocks, this sample produces no block random tick behavior.

### World.tickBlockEntities(): List Traversal and Execution

`World` maintains two lists: `blockEntityTickers` stores currently traversable block entity tick invokers, `pendingBlockEntityTickers` temporarily stores invokers added during traversal.

```java
// World.java
public void addBlockEntityTicker(BlockEntityTickInvoker ticker) {
    (this.iteratingTickingBlockEntities
        ? this.pendingBlockEntityTickers
        : this.blockEntityTickers).add(ticker);
}

protected void tickBlockEntities() {
    Profiler profiler = this.getProfiler();
    profiler.push("blockEntities");
    this.iteratingTickingBlockEntities = true;
    if (!this.pendingBlockEntityTickers.isEmpty()) {
        this.blockEntityTickers.addAll(this.pendingBlockEntityTickers);
        this.pendingBlockEntityTickers.clear();
    }

    Iterator<BlockEntityTickInvoker> iterator = this.blockEntityTickers.iterator();

    while (iterator.hasNext()) {
        BlockEntityTickInvoker blockEntityTickInvoker = iterator.next();
        if (blockEntityTickInvoker.isRemoved()) {
            iterator.remove();
        } else if (this.shouldTickBlockPos(blockEntityTickInvoker.getPos())) {
            blockEntityTickInvoker.tick();
        }
    }

    this.iteratingTickingBlockEntities = false;
    profiler.pop();
}
```

`shouldTickBlockPos(pos)` converts the block coordinate to chunk coordinates and calls `shouldTickBlocksInChunk()`. In `ServerWorld`, it ultimately queries the ticket manager's `shouldTickBlocks(chunkPos)`. This binds block entity ticks to the `BLOCK_TICKING` level like scheduled ticks and random ticks.

But there's a second gate here: `BlockEntityTickInvoker.tick()` is implemented in `WorldChunk.DirectBlockEntityTickInvoker`, which calls `WorldChunk.canTickBlockEntity(pos)` again. This step checks world boundaries, whether the chunk is loaded, and `getLevelType().isAfter(ChunkLevelType.BLOCK_TICKING)`. Two layers of checks ensure even if the world-level list briefly retains an invoker, it won't execute actual block entity logic at the wrong level.

### WorldChunk.updateTicker(): Registration, Replacement, and Removal

When block state changes, block entities load, or chunks enter the world, `WorldChunk` updates the corresponding block entity's ticker. The core method is `updateTicker()`:

```java
// WorldChunk.java
private <T extends BlockEntity> void updateTicker(T blockEntity) {
    BlockState blockState = blockEntity.getCachedState();
    BlockEntityTicker<T> blockEntityTicker =
        blockState.getBlockEntityTicker(this.world, (BlockEntityType<T>)blockEntity.getType());
    if (blockEntityTicker == null) {
        this.removeBlockEntityTicker(blockEntity.getPos());
    } else {
        this.blockEntityTickers.compute(blockEntity.getPos(), (pos, ticker) -> {
            BlockEntityTickInvoker blockEntityTickInvoker =
                this.wrapTicker(blockEntity, blockEntityTicker);
            if (ticker != null) {
                ticker.setWrapped(blockEntityTickInvoker);
                return (WorldChunk.WrappedBlockEntityTickInvoker)ticker;
            } else if (this.canTickBlockEntities()) {
                WorldChunk.WrappedBlockEntityTickInvoker wrappedBlockEntityTickInvoker =
                    new WorldChunk.WrappedBlockEntityTickInvoker(blockEntityTickInvoker);
                this.world.addBlockEntityTicker(wrappedBlockEntityTickInvoker);
                return wrappedBlockEntityTickInvoker;
            } else {
                return null;
            }
        });
    }
}
```

Three branches:

1. If `blockEntityTicker == null`, the current block state doesn't provide a ticker, remove the old ticker.
2. If `ticker != null` (invoker already exists), update its internal wrapped object through `setWrapped`, reusing the existing `WrappedBlockEntityTickInvoker`.
3. If `ticker == null` and `canTickBlockEntities()` passes, create a new `WrappedBlockEntityTickInvoker` and add it to the world list.

`canTickBlockEntities()` is the same check as `canTickBlockEntity()`: it depends on `ServerChunkManager.canTick()`, which ultimately checks whether `ChunkHolder.getTickingFuture()` is completed.

Therefore, when a block state changes — whether placed, removed, or state updated — `WorldChunk.setBlockState()` eventually calls `updateTicker()` to adjust the corresponding block entity's ticker registration.

### [!ADVANCED] Block Entity Tick Order and HashMap Resize (Historical Context)

This section records a historically well-known block entity tick order issue: **HashMap resize causing tile entity iteration order changes**.

#### Historical Background

In Minecraft versions before 1.13, many blocks that didn't truly need per-tick computation (like redstone dust, comparators) were also implemented as TileEntity for historical reasons. Block entity tick execution order directly affected redstone update propagation order, making this topic particularly sensitive.

Although 1.13+ removed unnecessary TileEntities, community discussion and related tooling (like `te_swap_calculator.py`) still circulates. This content is kept as historical reference, helping readers understand why "block entity order flip after reload" remains discussed.

#### Root Cause: WorldChunk.blockEntities is a HashMap

```java
// WorldChunk.java
private final Map<BlockPos, BlockEntity> blockEntities = new HashMap<>();
```

`HashMap` doesn't guarantee iteration order. But in actual server operations, barring hash collisions or resize, iteration order tends to remain stable — producing an **illusion of reproducibility**.

However, when the number of block entities in a chunk exceeds the current HashMap capacity threshold (default initial capacity 12, load factor 0.75), resize is triggered:

```java
// HashMap.java (simplified)
final Node<K,V>[] resize() {
    Node<K,V>[] oldTab = table;
    int oldCap = (oldTab == null) ? 0 : oldTab.length;
    int newCap = oldCap << 1;  // Double capacity
    Node<K,V>[] newTab = new Node[newCap];

    for (int j = 0; j < oldCap; ++j) {
        Node<K,V> e;
        if ((e = oldTab[j]) != null) {
            // Redistribute entries to new buckets based on hash & (newCap - 1)
            ...
        }
    }
    return newTab;
}
```

After resize, entries are redistributed based on new capacity's bitmask, potentially changing iteration order.

#### Trigger Condition

For chunks with 12 or fewer block entities, the default HashMap never resizes — iteration order remains stable. Once the 13th block entity is added:

```
12 < threshold (12 * 0.75 = 9) → no resize
13 > threshold → resize to capacity 32
```

After resize to 32, `BlockPos` entries are redistributed based on `hash(pos) & 31` instead of `hash(pos) & 11`, **causing some coordinate pair iteration orders to swap**.

#### Propagation Path to Save File

When `WorldChunk` saves, `ChunkSerializer.serialize()` traverses `blockEntities.values()` and writes block entity NBT to the chunk's `block_entities` list:

```java
// ChunkSerializer.java (simplified)
for (BlockEntity blockEntity : chunk.getBlockEntities().values()) {
    NbtCompound nbt = blockEntity.toNbt();
    blockEntitiesNbt.add(nbt);
}
```

ArrayList insertion order is entirely determined by "which `addBlockEntityTicker()` executed first." And this order comes from NBT list storage order — the iteration order from `getBlockEntityPositions()` during the previous save. **Therefore when `blockEntities` resizes and changes traversal order, it cascades to affect tick execution order on next load**.

#### Actual Impact

For most players, **no noticeable effect**. Reasons:

- Most chunks have far fewer than 12 block entities, never triggering resize
- Even if triggered, impact is limited to **relative order within that chunk**
- Different chunks' block entity tick order is jointly determined by chunk tick order interleaving and each ticker's independent position; resize only exposes order issues in specific, fragile timing-dependent scenarios

Truly affected scenarios:

- **Redstone dust update order** (historical): Before 1.13, redstone dust was also a TileEntity; subsequent versions removed this, but community awareness of "reload causes TE order flip" persists
- **Hopper order and item distribution**: Hopper `BlockEntityTicker` execution order determines item flow; in hopper chains, TE order flip can change item routing
- **Piston timing chains**: Multiple pistons executing sequentially within the same gt; order changes can alter overall behavior

#### Tool: Find Resize Flip Coordinate Pairs

Community open-source tool `te_swap_calculator.py` calculates coordinate pairs whose order flips after resize based on `Vec3i.hashCode()` formula and Java `HashMap` resize rules for a given chunk and TE count:

```
# In chunk(0, 0), find flip pairs when 12 TEs resize to 32 capacity
python te_swap_calculator.py 0 0 -k 12 -n 50
```

Filtering condition: For chunks at BLOCK_TICKING level, only TE order changes falling within `canTickBlockEntity()` range actually affect tick order. This tool is primarily used for redstone contraption debugging and order-sensitive design reference.
