The previous chapters repeatedly mentioned "chunk tickets." This chapter expands on this concept, covering the full lifecycle of every Ticket from creation to destruction, explaining what tickets are, how they work, and how they propagate.

## What is a Chunk Ticket

A chunk ticket (Ticket) is an object used to mark **the reason for chunk loading**. Its core data structure is very simple:

```java
public class ChunkTicket<T> {
    private final ChunkTicketType<T> type;  // Why load
    private final int level;                // What level
    private final T argument;              // Extra parameters (e.g., ChunkPos)
    private long tickCreated;              // Created at which tick
}
```

A ticket answers three questions: **why load** (type), **how far to load** (level), **where to load** (argument).

## Complete Ticket Type Table

1.20.1 has 8 ticket types:

| Type | Parameter Type | Purpose | Typical Expiry | Typical Load Distance |
|---|---|---|---|---|
| `START` | `Unit` | Load spawn on server start | Never expires | 11 (level=22) |
| `DRAGON` | `Unit` | Load main End island during dragon fight | Never expires | 9 (level=24) |
| `PLAYER` | `ChunkPos` | Chunk where player is located | Never expires | Determined by simulation distance |
| `FORCED` | `ChunkPos` | `/forceload` command | Never expires | level=31 |
| `LIGHT` | `ChunkPos` | Chunk needing light calculation | Based on light task | As needed |
| `PORTAL` | `BlockPos` | Load target dimension when passing through portal | 300 gt (15s) | 3 (level=30) |
| `POST_TELEPORT` | `Integer` | Load target chunk after entity teleport | 5 gt | 0~1 |
| `UNKNOWN` | `ChunkPos` | Auto-added when code gets chunk via `getChunk()` | 1 gt | 0~1 |

### Detailed Type Descriptions

**START**: Added by `MinecraftServer.prepareStartRegion()` around spawn with `radius=11` (level=22). This ticket takes effect immediately after server startup and persists after generation completes — ensuring spawn chunks never unload.

**DRAGON**: `EnderDragonFight.tick()` loads the main End island with `radius=9` (level=24) during dragon fights. Removed after battle ends.

**PLAYER**: The most common ticket. Automatically managed by `NearbyChunkTicketUpdater` — when players move, chunks entering view distance gain PLAYER tickets, chunks leaving view distance lose them. It's not "one ticket per player," but "one PLAYER ticket per chunk within view distance."

**FORCED**: Added through `ChunkTicketManager.setChunkForced()` via `/forceload`, with level fixed at `ENTITY_TICKING` (31), never expires. Only removed when manually executing `/forceload remove`.

**LIGHT**: Added by the lighting system when needing to calculate light for a chunk. This is a temporary ticket — expires automatically after light calculation completes.

**PORTAL**: Added in the target dimension by `PortalForcer.getPortalRect()` when entities pass through Nether portals. `radius=3` means 3 chunks around the target portal are loaded, level=30 (entity ticking). The 300 gt (15 second) grace period ensures entities have enough time to pass through and stabilize.

**POST_TELEPORT**: Added after teleport operations like `/tp`. `radius` is usually 0 or 1, expires after 5 gt — only ensures the landing chunk is available briefly.

**UNKNOWN**: Automatically added when code gets chunks through `World.getChunk()` and similar methods. `radius=0`, expires after 1 gt. Its purpose is to **prevent chunks from being unloaded immediately after retrieval** — giving the caller at least 1 gt to complete operations on the chunk.

## Adding and Removing Tickets

### Adding Tickets

```java
// ChunkTicketManager.java
public <T> void addTicket(ChunkTicketType<T> type, ChunkPos pos, int radius, T argument) {
    ChunkTicket<T> ticket = new ChunkTicket<>(type,
        ChunkLevels.getLevelFromType(ChunkLevelType.FULL) - radius, argument);
    // = new ChunkTicket<>(type, 33 - radius, argument)
    ...
}
```

`radius` is converted to `level = 33 - radius`. Therefore:
- `radius=0` → level=33 (`FULL`)
- `radius=1` → level=32 (`BLOCK_TICKING`)
- `radius=2` → level=31 (`ENTITY_TICKING`)
- `radius=11` → level=22 (far beyond entity ticking, sufficient to cover spawn area)

So when code says "add a player ticket with radius=10," it actually means "add a ticket with level=23 at the player's chunk."

### Removing Tickets

```java
// ChunkTicketManager.java
public <T> void removeTicket(ChunkTicketType<T> type, ChunkPos pos, int radius, T argument) {
    ChunkTicket<T> ticket = new ChunkTicket<>(type, 33 - radius, argument);
    this.ticketsByPosition.get(pos.toLong()).remove(ticket);
    this.shouldTick = true;
}
```

Note that ticket removal does **not mean the chunk unloads immediately**. If multiple tickets exist for that chunk, only the target ticket is removed; the remaining tickets continue to hold it. Only when all tickets expire or are removed, and propagation recalculates the chunk's level back above the unload threshold, will the chunk actually be scheduled for unloading.

## Ticket Propagation Mechanism

Tickets not only affect their target chunk, but also **propagate to surrounding chunks**. The rule is simple:

> If a chunk has level `n`, its distance-1 neighbors get level **at least** `n+1`, distance-2 neighbors get level **at least** `n+2`, and so on.

This is implemented by `ChunkLevels.TicketDistanceLevelPropagator`:

```java
protected int propagateLevel(long id, int level, int currentLevel) {
    return level >= currentLevel ? level : currentLevel + 1;
}
```

Interpretation: If the newly calculated level (`level`) is already lower (smaller number = higher priority) than the current neighbor level (`currentLevel`), then directly use `level`; otherwise use `currentLevel + 1`. This ensures a smooth decrease from the ticket's center outward, rather than a cliff-like drop.

### Propagation Example

Suppose chunk A gets a `START` ticket with level=22, and initially all surrounding chunks had level=MAX_LEVEL (unloaded):

```
Before:
  ...  ...  ...  ...  ...
  ... [MAX][MAX][MAX] ...
  ... [MAX][ 22][MAX] ...
  ... [MAX][MAX][MAX] ...
  ...  ...  ...  ...  ...

After first propagation:
  ...  ...  ...  ...  ...
  ... [MAX][ 23][MAX] ...
  ... [ 23][ 22][ 23] ...
  ... [MAX][ 23][MAX] ...
  ...  ...  ...  ...  ...

After second propagation:
  ...  ...  ...  ...  ...
  ... [ 24][ 23][ 24] ...
  ... [ 23][ 22][ 23] ...
  ... [ 24][ 23][ 24] ...
  ...  ...  ...  ...  ...
```

The center chunk's level=22 creates a circular gradient outward. The edge chunks' propagated level depends on the center's level plus distance, stopping when reaching level 33 (FULL) or beyond.

## Ticket Lifespan and Expiration

Tickets with `comparator` automatically participate in expiration checks. `ChunkTicketManager.purge()` checks each ticket's age every tick:

```java
private boolean shouldTick = true;

public void tick(ServerChunkManager chunkManager) {
    ++this.age; // world time
    ...
    if (this.shouldTick) {
        this.purge(chunkManager);
        this.shouldTick = false;
    }
}
```

Note the `shouldTick` flag: ticket addition and removal set this flag to true, prompting the next tick to run `purge()`. If no tickets are added or removed this tick, `purge()` is skipped, saving CPU.

```java
private void purge(ServerChunkManager chunkManager) {
    ...
    for (ObjectIterator<Entry<ChunkTicket<?>>> iterator = sortedArraySet.iterator(); iterator.hasNext();) {
        ChunkTicket<?> ticket = iterator.next().getKey();
        if (ticket.isExpired(this.age)) {
            iterator.remove();
            this.shouldTick = true;
        }
    }
    ...
}
```

A ticket is expired if: `currentAge - tickCreated > expiryTicks`. For example, `PORTAL` tickets have `expiryTicks=300`, so they're removed 300 gt after creation. `PLAYER` and `START` tickets have `expiryTicks=Long.MAX_VALUE`, effectively never expiring.

## Relationship Between Tickets and ChunkLevel

Tickets determine chunk level through this flow:

1. **Add ticket** → `ChunkTicketManager.addTicket()` → store in `ticketsByPosition`
2. **Tick triggers propagation** → `ChunkTicketManager.tick()` → `TicketDistanceLevelPropagator.update()` → recalculate each chunk's level
3. **Level changed** → `ChunkTicketManager.tick()` → call `chunkManager.setLevel()` → update `ChunkHolder.level`
4. **ChunkHolder responds** → `ChunkHolder.tick()` → upgrade or downgrade chunk state based on new level

This is a single-direction flow: tickets never care about what state the chunk is in; they only say "I want this area at at least level n." The chunk management system (TACS and ChunkHolder) then converts level to actual load, generation, and ticking operations.

## Common Mistakes

| Mistake | Fact |
|---|---|
| "One player = one ticket" | PLAYER tickets are per-chunk-within-view-distance, not per-player. Multiple players in the same chunk don't create multiple tickets. |
| "Removing a ticket unloads the chunk immediately" | Chunks only schedule for unloading when all tickets expire. A chunk with multiple ticket types won't unload when just one is removed. |
| "All tickets expire" | `START`, `DRAGON`, `PLAYER`, and `FORCED` tickets never expire. |
| "Tickets only affect their target chunk" | Tickets propagate to surrounding chunks through the distance propagator, creating a gradient effect. |

## Summary

- A chunk ticket marks **why** (type), **how far** (level), and **where** (argument) to load.
- The 8 ticket types cover server start, dragon fights, players, force-load, lighting, portals, teleports, and code access.
- Ticket level = `33 - radius`; smaller numbers mean higher load priority.
- Tickets propagate through `TicketDistanceLevelPropagator`, affecting neighboring chunks with level+1 each step.
- Tickets with `comparator` participate in expiration checks; expired tickets are automatically removed.
- Tickets only determine target level; actual chunk state management is the job of TACS and ChunkHolder.

### NearbyChunkTicketUpdater: Player Ticket Manager

Chapter 4 briefly mentioned `NearbyChunkTicketUpdater` — the component managing PLAYER tickets. Here we'll see how it concretely implements "player moves → add/remove nearby chunk tickets."

`NearbyChunkTicketUpdater` exists in `ThreadedAnvilChunkStorage` and is called every tick through `tickPlayerMovement()`:

```java
// ThreadedAnvilChunkStorage.java

    NearbyChunkTicketUpdater.ZERO_TICKET_UPDATE_DISTANCE

public void tick() {
    ...
    this.nearbyChunkTicketUpdater.setWatchDistance(this.watchDistance);
    this.tickPlayerMovement();
    ...
}

private void tickPlayerMovement() {
    List<ServerPlayerEntity> players = this.world.getPlayers();
    for (ServerPlayerEntity player : players) {
        this.nearbyChunkTicketUpdater.updateTickets(player, this.ticketManager);
    }
}
```

### updateTickets(): Add and Remove Tickets

`NearbyChunkTicketUpdater.updateTickets()` compares last tick's chunk position with the current position. If the player moved, it determines which new chunks entered view distance (add tickets) and which left view distance (remove tickets):

```java
// NearbyChunkTicketUpdater.java
public void updateTickets(long pos, IntConsumer addTicket, IntConsumer removeTicket) {
    int newChunkX = ChunkPos.getPackedX(pos);
    int newChunkZ = ChunkPos.getPackedZ(pos);

    // Last tick's chunk position
    Ticket oldTicket = this.positions.get(pos);
    int oldChunkX = ChunkSectionPos.unpackX(oldTicket.lastChunkKey);
    int oldChunkZ = ChunkSectionPos.unpackZ(oldTicket.lastChunkKey);

    // Compare
    if (newChunkX == oldChunkX && newChunkZ == oldChunkZ) {
        // Didn't move
        return;
    }

    // Iterate old chunk range
    for (int dx = -oldDistance; dx <= oldDistance; dx++) {
        for (int dz = -oldDistance; dz <= oldDistance; dz++) {
            long oldChunk = ChunkPos.toLong(oldChunkX + dx, oldChunkZ + dz);
            if (!isInNewRange(oldChunk, newChunkX, newChunkZ, newDistance)) {
                // This chunk is in old range but not new range → remove ticket
                removeTicket.accept(oldChunk);
            }
        }
    }

    // Iterate new chunk range
    for (int dx = -newDistance; dx <= newDistance; dx++) {
        for (int dz = -newDistance; dz <= newDistance; dz++) {
            long newChunk = ChunkPos.toLong(newChunkX + dx, newChunkZ + dz);
            if (!isInOldRange(newChunk, oldChunkX, oldChunkZ, oldDistance)) {
                // This chunk is in new range but not old range → add ticket
                addTicket.accept(newChunk);
            }
        }
    }

    // Update player's last chunk position
    oldTicket.lastChunkKey = ChunkSectionPos.asLong(newChunkX, 0, newChunkZ);
}
```

The actual `addTicket` and `removeTicket` callbacks eventually call `ChunkTicketManager.addTicket()` and `removeTicket()`. This means:

- **Player position update**: As soon as player `ChunkPos` changes, nearby chunk tickets automatically add/remove.
- **Gradual propagation**: New tickets propagate outward through `TicketDistanceLevelPropagator`, gradually loading new chunks and unloading old ones.
- **Distance control**: Distance range comes from `this.watchDistance` — server simulation distance.

### Ticket Update Isn't Instant World State Update

One common mistake: thinking "player steps into new chunk → that chunk loads instantly → blocks readable same tick." Actually, player movement triggers ticket addition, but:

1. **Ticket addition** only sets `shouldTick=true`
2. **Next tick's `ChunkTicketManager.tick()`** runs propagation
3. **Propagation updates level**, triggering `ChunkHolder.tick()`
4. **ChunkHolder initiates generation task** (if not yet generated)
5. **Generation task completes**, chunk becomes `WorldChunk`, `accessibleFuture` completes
6. **Only now** can `World.getChunk(ChunkPos, ChunkStatus.FULL)` return a readable chunk

This is an **asynchronous process**, typically taking multiple ticks. Attempting to read a chunk within the same tick as entering view distance usually fails (returns null or waits).

## [!ADVANCED] START vs PLAYER Tickets: Light Suppressor Efficiency Analysis

This section defines "light suppressor efficiency" as the **LQ net growth rate**. LQ refers to the backlog of lighting tasks formed jointly by `ServerLightingProvider.pendingTasks` and the `ChunkTaskPrioritySystem` priority queue ahead of it. Higher efficiency doesn't mean faster lighting processing, but rather faster backlog growth, making chunk loading more likely to stall at `ChunkStatus.LIGHT`.

### LQ Net Growth Rate: The True Definition of Suppressor Efficiency

```text
LQ net growth rate = enqueue rate - dequeue rate
```

The enqueue rate is determined by machine tick frequency, the number of lighting updates each machine generates, and the timing of wrapping these updates into lighting tasks. The dequeue rate is limited by `ServerLightingProvider.runTasks()`: line 196 first takes `Math.min(this.pendingTasks.size(), 1000)`, and lines 200-217 execute only `PRE_UPDATE`, `super.doLightUpdates()`, and `POST_UPDATE` for these `i` tasks.

```java
// ServerLightingProvider.java lines 195-217
private void runTasks() {
    int i = Math.min(this.pendingTasks.size(), 1000);
    ObjectListIterator<Pair<ServerLightingProvider.Stage, Runnable>> objectListIterator = this.pendingTasks.iterator();
    ...
    super.doLightUpdates();
    ...
    objectListIterator.remove();
}
```

So during normal PLAYER tick progression, the effective dequeue rate of lighting tasks is fixed at **≤ 1000 tasks/gt**. When machines generate lighting tasks faster than this limit, `LQ net growth rate > 0`, the queue backlog grows, and suppressor efficiency is high. When enqueuing is dispersed below the dequeue capacity by priority, loading timing, or blocking clearance, `LQ net growth rate ≤ 0`, the backlog can't grow continuously, and suppressor efficiency is low.

### Priority Queue Mechanism for Lighting Tasks

Lighting tasks aren't simply executed in chunk tick order. `ServerLightingProvider.enqueue()` at lines 132-137 passes tasks to `ChunkTaskPrioritySystem.createMessage()`, along with chunk coordinates and `completedLevelSupplier`:

```java
// ServerLightingProvider.java lines 131-137
private void enqueue(int x, int z, IntSupplier completedLevelSupplier, ServerLightingProvider.Stage stage, Runnable task) {
    this.executor.send(ChunkTaskPrioritySystem.createMessage(() -> {
        this.pendingTasks.add(Pair.of(stage, task));
        if (this.pendingTasks.size() >= 1000) {
            this.runTasks();
        }
    }, ChunkPos.toLong(x, z), completedLevelSupplier));
}
```

`createMessage()` at `ChunkTaskPrioritySystem.java` lines 49-53 wraps the `Runnable` into `Task<Runnable>`, preserving `pos` and `lastLevelUpdatedToProvider`. Then `enqueueChunk()` at lines 124-130 reads `lastLevelUpdatedToProvider.getAsInt()` and inserts the task into `LevelPrioritizedQueue` with that level.

```java
// ChunkTaskPrioritySystem.java lines 49-53
public static ChunkTaskPrioritySystem.Task<Runnable> createMessage(Runnable task, long pos, IntSupplier lastLevelUpdatedToProvider) {
    return new ChunkTaskPrioritySystem.Task<>(yield -> () -> {
        task.run();
        yield.send(Unit.INSTANCE);
    }, pos, lastLevelUpdatedToProvider);
}

// ChunkTaskPrioritySystem.java lines 124-130
int i = lastLevelUpdatedToProvider.getAsInt();
levelPrioritizedQueue.add(Optional.of(task), chunkPos, i);
```

The core data structure of `LevelPrioritizedQueue` is a level-bucketed system where each level maintains a linked map preserving insertion order by chunk position:

```java
// LevelPrioritizedQueue.java lines 18-22
public static final int LEVEL_COUNT = ChunkLevels.INACCESSIBLE + 2;
private final List<Long2ObjectLinkedOpenHashMap<List<Optional<T>>>> levelToPosToElements = IntStream.range(0, LEVEL_COUNT)
    .mapToObj(i -> new Long2ObjectLinkedOpenHashMap())
    .collect(Collectors.toList());
private volatile int firstNonEmptyLevel = LEVEL_COUNT;
```

When dequeuing, `poll()` starts directly from `firstNonEmptyLevel`. Lower level numbers mean stronger loading priority. Within the same level, line 93's `firstLongKey()` and line 94's `removeFirst()` retrieve the earliest-inserted chunk in that `Long2ObjectLinkedOpenHashMap`.

```java
// LevelPrioritizedQueue.java lines 82-100
public Stream<Either<T, Runnable>> poll() {
    if (this.blockingChunks.size() >= this.maxBlocking) return null;
    if (!this.hasQueuedElement()) return null;

    int i = this.firstNonEmptyLevel;
    Long2ObjectLinkedOpenHashMap<List<Optional<T>>> long2ObjectLinkedOpenHashMap = this.levelToPosToElements.get(i);
    long l = long2ObjectLinkedOpenHashMap.firstLongKey();
    List<Optional<T>> list = long2ObjectLinkedOpenHashMap.removeFirst();
    ...
}
```

So the execution order of lighting tasks is first sorted by level (lower = higher priority), then by insertion order within each level (earlier = processed first).

### Decoupling of Chunk Ticking and Lighting Tasks

When does a chunk's lighting task enqueue? Not directly within the same tick when the chunk is ticked. `chunk.tick()` → `BlockState.randomTick()` → `block.randomTick()` simply changes block state and adds block updates to the pending update list. The lighting updates triggered by these block state changes are wrapped into tasks and sent to the main thread task queue. These tasks are only actually processed by `ServerChunkManager.tick()` at lines 353-356 through `ChunkTaskPrioritySystem.pollTask()`.

```java
// ServerChunkManager.java lines 352-357
public boolean tick() {
    boolean bl = this.chunkTaskPrioritySystem.pollTask();  // Process highest-priority chunk task
    this.lightingProvider.tick();                          // Then process lighting tasks
    ...
}
```

So the `completedLevel` that determines task priority reflects **the chunk's completion state at enqueue time**, not chunk tick order. For PLAYER loading, most chunks tick at completed level 31 (entity ticking), so their lighting tasks also queue at level 31. For START loading, chunks are in concurrent loading with a gradient from level 22 to 33, causing lighting tasks to be naturally bucketed across multiple levels — level 22 finishes before level 23, level 23 finishes before level 24.

### Machine Distribution Impact: Gradient vs Flat

Consider two machine distribution patterns:

1. **Gradient distribution**: Machines spread from the center outward, following START or PLAYER propagation gradients, with different completed levels at enqueue time.
2. **Flat distribution**: All machines concentrated in the same effective completed level.

The lighting task execution flow differs significantly:

**Gradient distribution**:
- Tasks enqueue dispersed across levels 22~33
- `LevelPrioritizedQueue` processes level 22 first, then level 23, then level 24...
- Each level's backlog is cleared before moving to the next level
- Enqueue rate is distributed across levels → difficult to concentrate pressure → dequeue keeps pace with enqueue → **low LQ net growth rate → low suppressor efficiency**

**Flat distribution** (example: all at level 31):
- All tasks enqueue at the same level (level 31)
- `LevelPrioritizedQueue` has no level layering to disperse them
- Tasks enqueue concentrated → directly challenge the 1000/gt limit → easy to exceed dequeue capacity → **high LQ net growth rate → high suppressor efficiency**

This explains why the same light suppressor design has completely different effects during START vs PLAYER loading.

### START vs PLAYER: Fundamental Differences

Both `START` and `PLAYER` tickets never expire, but their execution timing produces fundamentally different performance characteristics:

| Aspect | START Loading | PLAYER Loading |
|---|---|---|
| Trigger | Server startup `prepareStartRegion()` | Player movement, view distance changes |
| Task progression | `runTasksTillTickEnd()` blocking clearance | Normal tick with 1000/gt batch limit |
| Dequeue rate | ≈ ∞ (cleared immediately) | ≤ 1000 tasks/gt |
| Machine distribution | START radius=11 naturally forms level 22~33 gradient | Flat distribution at same level (e.g., all level 31) |
| LQ net growth rate | ≤ 0, tasks cleared blockingly | Depends on distribution: low for gradient, high for flat |
| Suppressor effect | Nearly ineffective | Low for gradient, high for flat |

### Influence of Same-Level Insertion Order

Tasks at the same level have no secondary numeric priority. `LevelPrioritizedQueue.add()` at lines 49-51 uses `computeIfAbsent(pos, ...)` to append tasks for the same chunk into that chunk's list. `poll()` at lines 93-94 retrieves the earliest-inserted chunk in that level via `firstLongKey()` and `removeFirst()`.

```java
// LevelPrioritizedQueue.java lines 49-51
protected void add(Optional<T> element, long pos, int level) {
    this.levelToPosToElements.get(level).computeIfAbsent(pos, l -> Lists.newArrayList()).add(element);
    this.firstNonEmptyLevel = Math.min(this.firstNonEmptyLevel, level);
}
```

So even if all machines are at the same level, chunks loaded first and inserting tasks into that level bucket first will be processed first. The spatial arrangement of machines changes chunk first-load order and task insertion order, thus changing which machines get digested first at the same level and which machines are more likely to accumulate at the back of the queue.

### Minor Impact of Existing Backlog on Efficiency

`ServerLightingProvider.enqueue()` doesn't only wait for the next tick to process. After a wrapped lighting task actually runs and appends to `pendingTasks`, lines 134-136 immediately call `runTasks()` when the queue size reaches 1000:

```java
// ServerLightingProvider.java lines 132-136
this.pendingTasks.add(Pair.of(stage, task));
if (this.pendingTasks.size() >= 1000) {
    this.runTasks();
}
```

If LQ already has backlog, newly enqueued tasks push `pendingTasks.size()` to 1000 faster, triggering batch processing immediately within the current task execution chain instead of waiting for the next `ServerLightingProvider.tick()`. This mechanism improves "batch trigger responsiveness" but doesn't change the long-term 1000/gt dequeue limit. Its effect is a minor reduction in latency from waiting for the next tick.

### Practical Application Recommendations

To improve light suppressor efficiency, the goal isn't to have machines cover more different loading levels, but to have light-task-producing machines at the same effective level and enqueue in the same time window. In PLAYER scenarios, placing machines in chunks at the same completed level within player view distance eliminates the level-layering dispersion effect of `LevelPrioritizedQueue`, allowing concentrated enqueuing to directly exceed the 1000/gt limit of `ServerLightingProvider.runTasks()`.

Conversely, if machines spread along the START radius or other ticket propagation gradients, tasks are first processed layer by layer from low to high levels. Each layer is digested before the next, lowering LQ net growth rate and suppressor efficiency. START spawn loading also stacks `runTasksTillTickEnd()` blocking clearance, so even with lighting updates present, the queue struggles to form sustained backlog.
