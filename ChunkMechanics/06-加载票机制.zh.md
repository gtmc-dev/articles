前几章反复提到了"加载票"这个词。本章将它单独展开，从每一个 Ticket 的诞生到消亡，讲清楚"票"到底是什么、怎么用、怎么传播。

## 什么是加载票

加载票（Ticket）是一个用于标明**区块加载原因**的对象。它的核心数据结构非常简单：

```java
public class ChunkTicket<T> {
    private final ChunkTicketType<T> type;  // 什么原因
    private final int level;                // 多少等级
    private final T argument;              // 附加参数（如 ChunkPos）
    private long tickCreated;              // 创建于第几 tick
}
```

一张票回答三个问题：**为什么加载**（type）、**加载到什么程度**（level）、**加载哪里**（argument）。

## 加载票类型全表

1.20.1 中一共有 8 种加载票类型：

| 类型 | 参数类型 | 用途 | 典型过期时间 | 典型加载距离 |
|---|---|---|---|---|
| `START` | `Unit` | 服务端启动时加载出生点 | 不休眠 | 11（level=22） |
| `DRAGON` | `Unit` | 龙战期间加载末地主岛 | 不休眠 | 9（level=24） |
| `PLAYER` | `ChunkPos` | 玩家所在的区块 | 不休眠 | 由模拟距离决定 |
| `FORCED` | `ChunkPos` | `/forceload` 指令强加载 | 永不过期 | level=31 |
| `LIGHT` | `ChunkPos` | 需要计算光照的区块 | 根据光照任务 | 视需要 |
| `PORTAL` | `BlockPos` | 穿过传送门时加载目标维度 | 300 gt（15秒） | 3（level=30） |
| `POST_TELEPORT` | `Integer` | 实体传送后加载目标区块 | 5 gt | 0~1 |
| `UNKNOWN` | `ChunkPos` | 代码通过 `getChunk()` 获取区块时自动添加 | 1 gt | 0~1 |

### 各类型详解

**START**：`MinecraftServer.prepareStartRegion()` 在出生点周围以 `radius=11`（level=22）添加。这张票在服务端启动后立即生效，并在生成完成后一直存在——确保出生点区块永不卸载。

**DRAGON**：`EnderDragonFight.tick()` 在龙战期间以 `radius=9`（level=24）加载末地主岛。战斗结束后移除。

**PLAYER**：这是最常见的票。由 `NearbyChunkTicketUpdater` 自动管理——当玩家移动时，进入视距的区块获得 PLAYER 票，离开视距的区块失去。它不是"每个玩家一张票"，而是"每个在视距内的区块各一张 PLAYER 票"。

**FORCED**：`/forceload` 通过 `ChunkTicketManager.setChunkForced()` 添加，level 固定为 `ENTITY_TICKING`（31），永不过期。只有当手动执行 `/forceload remove` 时才被移除。

**LIGHT**：光照系统在需要计算某个区块的光照时添加。这是一张临时票——光照计算完成后自动过期。

**PORTAL**：实体穿过下界传送门时，`PortalForcer.getPortalRect()` 在目标维度添加。`radius=3` 意味着目标传送门周围 3 区块都被加载，level=30（强加载）。300 gt（15 秒）的宽限期确保实体有足够时间穿过并站稳。

**POST_TELEPORT**：`/tp` 等传送操作后添加。`radius` 通常为 0 或 1，5 gt 后过期——只保证传送落地的区块在短时间内可用。

**UNKNOWN**：当代码通过 `World.getChunk()` 等方式获取区块时自动添加。`radius=0`，1 gt 后过期。它的作用是**防止区块在获取后立即被卸载**——给了调用者至少 1 gt 的时间来完成对区块的操作。

## 票的添加与移除

### 添加票

```java
// ChunkTicketManager.java
public <T> void addTicket(ChunkTicketType<T> type, ChunkPos pos, int radius, T argument) {
    ChunkTicket<T> ticket = new ChunkTicket<>(type,
        ChunkLevels.getLevelFromType(ChunkLevelType.FULL) - radius, argument);
    // = new ChunkTicket<>(type, 33 - radius, argument)
    ...
}
```

`radius` 被转换为 `level = 33 - radius`。因此：
- `radius=0` → level=33（`FULL`）
- `radius=1` → level=32（`BLOCK_TICKING`）
- `radius=2` → level=31（`ENTITY_TICKING`）
- `radius=11` → level=22（远超强加载，足够覆盖出生点区域）

添加后，票被存入 `ticketsByPosition`——一个以 `long` 坐标索引的 `SortedArraySet<ChunkTicket>`。同一区块的所有票按 level 升序排列，`getLevel()` 返回集合中第一个（即 **level 最小的，也就是最"强"的**）票的 level。

### 移除票

移除票后，如果某区块的票集合变为空，该区块从 `ticketsByPosition` 中移除。然后 `distanceFromTicketTracker` 重新计算该区块的 level——当没有任何票时，level 变为 `INACCESSIBLE + 1`。

## 票的传播

一张票加到中心区块后，周围区块如何确定自己的加载等级？`TicketDistanceLevelPropagator` 负责这个计算。

传播规则严格遵循切比雪夫距离：

```text
对于中心区块 (cx, cz) 上的票，其 level = L：
周围区块 (x, z) 的 level = L + max(|x - cx|, |z - cz|)
```

即：每向外走一个区块（包括对角线），level +1。

例如，一张 level=31（强加载）的票加在 `(0, 0)`：

```
35  34  33  34  35      ← 向外 2 格 = level 33
34  33  32  33  34
33  32 [31] 32  33      ← 中心 = level 31
34  33  32  33  34
35  34  33  34  35
```

`TicketDistanceLevelPropagator` 继承自 `ChunkPosDistanceLevelPropagator`，使用经典的 level 传播算法——`propagateLevel` 向 8 个邻居广播，`recalculateLevel` 取所有邻居的 `min(level+1)`。

## 三个追踪器的分工

`ChunkTicketManager` 维护了四个追踪器，各自负责一种 level 的计算：

| 追踪器 | 负责的 ticket | 传播的粒度 | 用途 |
|---|---|---|---|
| `TicketDistanceLevelPropagator` | 所有非 PLAYER ticket | 每区块一个综合最低 level | 驱动 ChunkHolder 的加载/卸载 |
| `DistanceFromNearestPlayerTracker` | 玩家位置（不直接管理 ticket） | 每区块到最近玩家的距离 | 控制客户端数据发送（视距） |
| `NearbyChunkTicketUpdater` | 自动增删 PLAYER ticket | 视距内的区块被加 ticket | 实现玩家周围区块加载 |
| `SimulationDistanceLevelPropagator` | 独立记录并传播 level | 单独的 level 表 | 决定方块/实体运算的权限 |

## 票的过期与回收

`ChunkTicketManager.purge()` 每 tick 被调用一次，遍历所有票：

```java
protected void purge() {
    this.age++;
    for (entry : ticketsByPosition) {
        for (ticket : entry.getValue()) {
            if (ticket.isExpired(this.age)) {
                iterator.remove();  // 票过期，移除
                simulationDistanceTracker.remove(...);  // 同步从模拟距离表移除
            }
        }
        if (list became empty) { remove entry from ticketsByPosition; }
        if (any ticket removed) { distanceFromTicketTracker.updateLevel(...); }  // 重新计算 level
    }
}
```

过期的判定基于 `tickCreated` 和票类型：

- `POST_TELEPORT`：`age - tickCreated >= 5`
- `UNKNOWN`：`age - tickCreated >= 1`
- `PORTAL`：`age - tickCreated >= 300`
- `PLAYER`、`FORCED`、`START`、`DRAGON`：`isExpired()` 始终返回 `false`——不休眠


## 小结

- 8 种加载票类型覆盖了启动、玩家、传送门、指令、光照等各种加载原因。
- 票的核心属性是 level，同一区块取最低 level；level 通过切比雪夫距离向外传播。
- 票的过期时间因类型而异：`POST_TELEPORT`（5gt）到永不过期（`FORCED`）。
- 三个追踪器各自负责 level 的传播和计算，共同驱动 ChunkHolder 的状态变化。
- 票系统不是引用计数，而是等级传播系统——加一张 level=31 的票比加三张 level=33 的票更"强"。

### ChunkTicket 比较器：SortedArraySet 与"最强票优先"

```java
// ChunkTicket.java
public final class ChunkTicket<T> implements Comparable<ChunkTicket<?>> {
    private final ChunkTicketType<T> type;
    private final int level;
    private final T argument;
    private long tickCreated;

    public int compareTo(ChunkTicket<?> other) {
        int i = Integer.compare(this.level, other.level);
        if (i != 0) return i;  // level 不同：level 小的排前面（"更强"的票优先）
        // level 相同 → 第二排序键：type 的 identityHashCode
        int j = Integer.compare(
            System.identityHashCode(this.type),
            System.identityHashCode(other.type));
        return j != 0 ? j
            : this.type.getArgumentComparator().compare(this.argument, other.argument);
    }
}
```

`ChunkTicket` 实现 `Comparable`，按 level 升序排列——level 越小，票越"强"，排在 `SortedArraySet` 的最前面。`ticketsByPosition` 中每区块的 ticket 集合就是一个 `SortedArraySet`，`getLevel()` 直接取第一个元素的 level 作为该区块的综合加载等级。

**为什么第二排序键用 `identityHashCode` 而不是 `type` 本身的比较？** 因为 `ChunkTicketType` 没有实现 `Comparable`——设计者认为不同类型的票之间不应该有序，它们只是以不同的理由要求加载同一个区块。`identityHashCode` 是一个稳定的、不依赖字段值的 hash（由 JVM 为每个对象分配），保证了同一 JVM 运行期间相同 type 的票排序一致，且不需要 type 实现任何比较接口。

### isExpired：基于超时而非引用计数的过期机制

```java
// ChunkTicket.java
protected boolean isExpired(long currentTick) {
    long l = this.type.getExpiryTicks();
    return l != 0L && currentTick - this.tickCreated > l;
}
```

```java
// ChunkTicketType.java
public static final ChunkTicketType<BlockPos> PORTAL = create("portal", ..., 300);  // 300 gt
public static final ChunkTicketType<Integer> POST_TELEPORT = create("post_teleport", ..., 5);  // 5 gt
public static final ChunkTicketType<ChunkPos> UNKNOWN = create("unknown", ..., 1);  // 1 gt
// 以下不传 expiryTicks → 内部 expiryTicks=0 → 永不过期
public static final ChunkTicketType<Unit> START = create("start", ...);
public static final ChunkTicketType<ChunkPos> PLAYER = create("player", ...);
public static final ChunkTicketType<ChunkPos> FORCED = create("forced", ...);
```

**为什么用超时而不是引用计数？** 因为加载票的持有者（玩家位置、传送门逻辑、光照系统）可能在多个不同的代码路径中被添加和移除——没有统一的"计数器"。更重要的是，有些持有者可能"悄悄地消失了"而没有机会调用删除（如光照任务在异步线程上完成后线程直接回收）。超时机制保证了即使持有者忘记清理，票也会在过期后自动回收，避免死票堆积。

**`expiryTicks = 0` 的设计意义：** 用 `0` 表示"永不过期"，而不是 `-1` 或 `Long.MAX_VALUE`。`isExpired` 的条件是 `l != 0L && ...`——如果 `expiryTicks = 0`，`l != 0L` 为 false，整个表达式短路为 false。这是一个经典的**哨兵值模式**——不需要额外的 `boolean` 字段来标识"是否过期"，零值本身就是哨兵。

### 传播算法的设计

`ChunkPosDistanceLevelPropagator` 继承自 `LevelPropagator`——这是一个通用的数值传播框架，用于光照传播等场景。区块管理系统复用了这个框架来实现加载等级的传播。

```java
// ChunkPosDistanceLevelPropagator.java
protected void propagateLevel(long id, int level, boolean decrease) {
    ChunkPos chunkPos = new ChunkPos(id);
    for (int k = -1; k <= 1; k++) {
        for (int l = -1; l <= 1; l++) {
            long m = ChunkPos.toLong(chunkPos.x + k, chunkPos.z + l);
            if (m != id) this.propagateLevel(id, m, level, decrease);
        }
    }
}

protected int getPropagatedLevel(long sourceId, long targetId, int level) {
    return sourceId == ChunkPos.MARKER
        ? this.getInitialLevel(targetId)    // 中心：取票的 level
        : level + 1;                        // 邻居：源 level + 1
}
```

**`ChunkPos.MARKER` 是什么？** 它是一个特殊的 `long` 值（`1875066, 1875066` 的打包），用作传播的**虚拟源点**。当 `TicketDistanceLevelPropagator.setLevel()` 被调用时，它不直接更新目标区块的 level——而是更新 `ChunkPos.MARKER` 到目标区块的传播路径。这样设计的原因：可能有多个区块都有 ticket（多个玩家在不同的块），如果直接更新每个区块的 level，在 ticket 变化时需要回退所有传播。通过一个虚拟 MARKER，所有 ticket 的 level 都被当作"从 MARKER 到目标区块的传播起点"，删除时只需去掉这条路径，不影响其他 ticket 的传播。

**传播范围由 `LevelPropagator` 的构造函数参数控制**：`new LevelPropagator(maxLevel + 1, 16, 256)`——16 是每轮处理的最大更新数，256 是 pending update 队列的容量。这两个参数限制了传播的性能开销：不能在单次 `applyPendingUpdates` 中处理太多区块（会阻塞 tick），也不能积压太多未处理的更新（会浪费内存）。

## [!ADVANCED] START 与 PLAYER 票的执行时序差异：光照抑制器效率分析

本节把"光照抑制器效率"定义为 **LQ 净增长速率**。这里的 LQ 指 `ServerLightingProvider.pendingTasks` 以及它前面的 `ChunkTaskPrioritySystem` 优先级队列所共同形成的光照任务积压；效率越高，不是指光照处理越快，而是指积压增长越快，区块加载越容易被 `ChunkStatus.LIGHT` 卡住。

### LQ 净增长速率：抑制器效率的真实定义

```text
LQ 净增长速率 = 入队速度 - 出队速度
```

入队速度由机器 tick 频率、每次机器更新制造的光照更新数、这些更新被包装成光照任务的时序共同决定。出队速度由 `ServerLightingProvider.runTasks()` 限制：line 196 先取 `Math.min(this.pendingTasks.size(), 1000)`，line 200-217 只围绕这 `i` 个任务执行 `PRE_UPDATE`、`super.doLightUpdates()` 和 `POST_UPDATE`。

```java
// ServerLightingProvider.java lines 195-217
private void runTasks() {
    int i = Math.min(this.pendingTasks.size(), 1000);
    ObjectListIterator<Pair<ServerLightingProvider.Stage, Runnable>> objectListIterator = this.pendingTasks.iterator();
    ...
    super.doLightUpdates();
    ...
    objectListIterator.remove();
}
```

所以在 PLAYER 正常 tick 推进时，光照任务的有效出队速度固定为 **≤ 1000 任务/gt**。当机器制造光照任务的入队速度高于这个上限，`LQ 净增长速率 > 0`，队列积压增长，抑制器效率高；当入队被优先级、加载时序或阻塞式清空分散到低于出队能力，`LQ 净增长速率 ≤ 0`，积压无法持续增长，抑制器效率低。

### 光照任务的优先级队列机制

光照任务不是单纯按区块 tick 的先后直接执行。`ServerLightingProvider.enqueue()` 在 line 132-137 把任务交给 `ChunkTaskPrioritySystem.createMessage()`，并传入区块坐标和 `completedLevelSupplier`：

```java
// ServerLightingProvider.java lines 131-137
private void enqueue(int x, int z, IntSupplier completedLevelSupplier, ServerLightingProvider.Stage stage, Runnable task) {
    this.executor.send(ChunkTaskPrioritySystem.createMessage(() -> {
        this.pendingTasks.add(Pair.of(stage, task));
        if (this.pendingTasks.size() >= 1000) {
            this.runTasks();
        }
    }, ChunkPos.toLong(x, z), completedLevelSupplier));
}
```

`createMessage()` 在 `ChunkTaskPrioritySystem.java` line 49-53 把 `Runnable` 包装成 `Task<Runnable>`，保留 `pos` 和 `lastLevelUpdatedToProvider`。随后 `enqueueChunk()` 在 line 124-130 读取 `lastLevelUpdatedToProvider.getAsInt()`，把任务以这个 level 插入 `LevelPrioritizedQueue`。

```java
// ChunkTaskPrioritySystem.java lines 49-53
public static ChunkTaskPrioritySystem.Task<Runnable> createMessage(Runnable task, long pos, IntSupplier lastLevelUpdatedToProvider) {
    return new ChunkTaskPrioritySystem.Task<>(yield -> () -> {
        task.run();
        yield.send(Unit.INSTANCE);
    }, pos, lastLevelUpdatedToProvider);
}

// ChunkTaskPrioritySystem.java lines 124-130
int i = lastLevelUpdatedToProvider.getAsInt();
levelPrioritizedQueue.add(Optional.of(task), chunkPos, i);
```

`LevelPrioritizedQueue` 的核心数据结构是按 level 分桶、每个 level 内再按区块坐标保存插入顺序的链式 map：

```java
// LevelPrioritizedQueue.java lines 18-22
public static final int LEVEL_COUNT = ChunkLevels.INACCESSIBLE + 2;
private final List<Long2ObjectLinkedOpenHashMap<List<Optional<T>>>> levelToPosToElements = IntStream.range(0, LEVEL_COUNT)
    .mapToObj(i -> new Long2ObjectLinkedOpenHashMap())
    .collect(Collectors.toList());
private volatile int firstNonEmptyLevel = LEVEL_COUNT;
```

出队时，`poll()` 直接从 `firstNonEmptyLevel` 开始；level 数字越小，加载等级越强，优先级越高。进入同一个 level 后，line 93 的 `firstLongKey()` 和 line 94 的 `removeFirst()` 取的是该 `Long2ObjectLinkedOpenHashMap` 中最早插入的区块。

```java
// LevelPrioritizedQueue.java lines 82-100
public Stream<Either<T, Runnable>> poll() {
    if (this.blockingChunks.size() >= this.maxBlocking) return null;
    if (!this.hasQueuedElement()) return null;

    int i = this.firstNonEmptyLevel;
    Long2ObjectLinkedOpenHashMap<List<Optional<T>>> map = this.levelToPosToElements.get(i);
    long l = map.firstLongKey();
    List<Optional<T>> list = map.removeFirst();
    ...
    return list.stream().map(optional -> optional.map(Either::left).orElseGet(() -> Either.right(this.createBlockingAdder(l))));
}
```

结论是确定的：光照任务先按 **level 从小到大**处理；同 level 内按**区块首次进入该 level 桶的插入顺序**处理；同一区块下的多个任务保存在同一个 `List<Optional<T>>` 中，随该区块一起被取出。

### 区块 tick 与光照任务的解耦

### 机器分布对 LQ 净增速的影响

#### 梯度分布（不同 level）

梯度分布指机器落在 level=22、23、24、...、31 等不同加载等级的区块中。由于 `LevelPrioritizedQueue.poll()` 固定从 `firstNonEmptyLevel` 取任务，level=22 的机器任务先被处理，然后才轮到 level=23，继续向更大的 level 推进。

这种分布会把入队时序拆成多层：低 level 区块的光照任务先进入处理通道并被消化，高 level 区块的任务在优先级队列后方等待。只要每一层进入 `pendingTasks` 的速度没有持续压过 `runTasks()` 的 1000/gt 出队上限，LQ 净增长速率就低，队列不容易形成持续积压。因此，梯度分布下抑制器效率低。

#### 平坦分布（同一 level）

平坦分布指机器集中在同一加载等级，例如玩家视距内大量 level=31 的强加载区块。所有机器任务拥有相同优先级，`LevelPrioritizedQueue` 不再把它们拆成多个 level 层，只在同 level 内按区块插入顺序推进。

同时，区块 tick 在 `Collections.shuffle(list)` 后每 tick 随机访问这些机器区块，多个机器会在同一个 gt 的相近时间段制造大量光照更新。由于这些任务优先级相同，它们集中进入 `pendingTasks`；当集中入队超过 `runTasks()` 的 1000/gt 上限时，`LQ 净增长速率 > 0`，队列快速积压。因此，平坦分布下抑制器效率高。

#### 对比表格

| 指标 | 梯度分布（不同 level） | 平坦分布（同一 level） |
|---|---|---|
| 优先级结构 | 多个 level 分层，level 小的先出队 | 全部处于同一 level，只剩插入顺序 |
| 任务入队节奏 | 分层进入 `pendingTasks`，时间上更分散 | 同优先级任务集中进入 `pendingTasks` |
| 主要限制 | 每层任务先被处理，后层延迟进入 | 1000/gt 出队上限直接面对集中入队 |
| LQ 净增长速率 | 低，持续积压弱 | 高，集中入队时快速积压 |
| 抑制器效率 | 低 | 高 |

### START vs PLAYER 的根本差异

`START` 和 `PLAYER` 都是不休眠票，但它们驱动任务队列的方式不同。

`MinecraftServer.prepareStartRegion()` 在 line 513 添加 `START` 票，radius=11；按前文 `level = 33 - radius`，出生点中心为 level=22，周围区块自然形成 22 到 33 的梯度。line 515-521 用 `while` 等待 441 个出生点区块加载完成，并在循环内反复调用 `runTasksTillTickEnd()`。

```java
// MinecraftServer.java lines 513-521
serverChunkManager.addTicket(ChunkTicketType.START, new ChunkPos(blockPos), 11, Unit.INSTANCE);

while (serverChunkManager.getTotalChunksLoadedCount() != 441) {
    this.timeReference = Util.getMeasuringTimeMs() + 10L;
    this.runTasksTillTickEnd();
}

this.timeReference = Util.getMeasuringTimeMs() + 10L;
this.runTasksTillTickEnd();
```

`runTasksTillTickEnd()` 在 `MinecraftServer.java` line 790-793 先执行一次 `runTasks()`，再持续 `runTasks(() -> !this.shouldKeepTicking())`。在出生点准备阶段，服务器用这个阻塞循环等待加载目标完成，所以光照相关主线程任务不会只按正常玩家 tick 的节奏缓慢推进。对 LQ 来说，START 的出队能力等价于"持续清空直到本阶段加载完成"，净增长速率被压到 `≤ 0`，抑制器几乎无效。

PLAYER 加载走正常 tick。`ServerLightingProvider.tick()` 只在有 pending 光照任务或底层光照更新时投递一次 `runTasks()`，而 `runTasks()` 每次最多取 1000 个 pending task。当 PLAYER 视距内的机器全部布置在同一 completed level（本节例子取 level=31 的强加载区块）时，入队更平坦、更集中；只要入队速度超过 1000/gt，LQ 就正增长，区块加载被光照阶段拖住。

| | START（出生点加载） | PLAYER（玩家加载） |
|---|---|---|
| 执行方式 | `prepareStartRegion()` 阻塞等待 441 区块，循环调用 `runTasksTillTickEnd()` | 正常 tick 异步推进，光照 provider 每轮 `runTasks()` |
| 出队速度 | 持续清空到启动加载阶段完成，等效无固定 gt 上限 | `Math.min(pendingTasks.size(), 1000)`，≤ 1000 任务/gt |
| 机器分布特征 | START radius=11，天然形成 level=22~33 梯度 | 同 level 平坦分布（例如全部 level=31） |
| LQ 净增速 | ≤ 0，任务被阻塞式清空 | 由分布决定：梯度低，平坦高 |
| 抑制器效果 | 几乎无效 | 梯度分布低效，平坦分布高效 |

### 同 level 内插入顺序的影响

同 level 的任务没有第二个数值优先级。`LevelPrioritizedQueue.add()` 在 line 49-51 用 `computeIfAbsent(pos, ...)` 把同一区块的任务追加进该区块的 list；`poll()` 在 line 93-94 通过 `firstLongKey()` 和 `removeFirst()` 取出该 level 内最早插入的区块。

```java
// LevelPrioritizedQueue.java lines 49-51
protected void add(Optional<T> element, long pos, int level) {
    this.levelToPosToElements.get(level).computeIfAbsent(pos, l -> Lists.newArrayList()).add(element);
    this.firstNonEmptyLevel = Math.min(this.firstNonEmptyLevel, level);
}
```

因此，即使机器都在同一个 level，先被加载、先向该 level 桶插入任务的区块也会先被处理。机器的空间排列会改变区块首次加载顺序和任务插入顺序，从而改变同 level 内哪些机器先被消化、哪些机器更容易留在队列后方积压。

### 原有积压对效率的微小影响

`ServerLightingProvider.enqueue()` 不是只等下一个 tick 才处理。当包装后的光照任务真正运行并追加到 `pendingTasks` 后，line 134-136 会在队列大小达到 1000 时立即调用 `runTasks()`：

```java
// ServerLightingProvider.java lines 132-136
this.pendingTasks.add(Pair.of(stage, task));
if (this.pendingTasks.size() >= 1000) {
    this.runTasks();
}
```

如果 LQ 已有积压，新入队任务更快把 `pendingTasks.size()` 推到 1000，批处理会在当前任务执行链中立刻触发，而不是等待下一次 `ServerLightingProvider.tick()`。这个机制提高的是"触发批处理的及时性"，不是 1000/gt 的长期出队上限；它带来的效果是微小减少等待下一个 tick 的延迟。

### 实际应用建议

要提高光照抑制器效率，目标不是让机器覆盖更多不同加载等级，而是让产生光照任务的机器尽量处于同一个有效 level，并在同一时间窗口内集中入队。PLAYER 场景下，把机器放在玩家视距内相同 completed level 的区块，能让 `LevelPrioritizedQueue` 失去 level 分层的分散效果，使集中入队直接压过 `ServerLightingProvider.runTasks()` 的 1000/gt 上限。

反过来，若机器沿 START 半径或其他票传播梯度铺开，任务会先按小 level 到大 level 分层处理；每层被优先消化后才轮到下一层，LQ 净增长速率下降，抑制器效率随之下降。START 出生点加载还叠加 `runTasksTillTickEnd()` 的阻塞式清空，所以即使存在光照更新，队列也难以形成持续积压。
