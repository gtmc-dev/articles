按下 `F3 + G` 后，地面上会出现一张整齐的彩色网格。无论地形怎样起伏，这些边界始终沿 X、Z 方向每隔 16 格出现一次。

这些网格展示的就是**区块边界**。

## 为什么需要区块

Minecraft 的维度在水平方向上非常大。如果游戏把整个维度当成一个不可分割的整体，那么读取一个方块、保存一次修改，甚至只加载玩家附近的地形都会变得十分困难。

因此，游戏将维度沿水平方向切分成许多 `16 × 16` 的竖直区域。每一个这样的区域就是一个**区块**（Chunk）。

一个区块的本质定义：**水平尺寸固定为 16×16、覆盖所在维度完整可用高度的竖直区域**。它不是 `16 × 16 × 16` 的小立方体——主世界从 Y=`-64` 到 Y=`319` 的同一列方块，都属于同一个区块。

## 从方块坐标到区块坐标

区块只有 X、Z 坐标，没有单独的 Y 坐标。换算规则严格由以下三个位运算决定：

```text
区块 X = 方块 X >> 4      （算术右移 4 位 = 向下取整除以 16）
区块 Z = 方块 Z >> 4
区块内 X = 方块 X & 15    （取低 4 位 = 除以 16 的余数）
区块内 Z = 方块 Z & 15
```

反算规则同样严格：

```text
区块起始方块 X = 区块 X << 4
区块最东侧方块 X = 区块起始方块 X + 15
```

验证表格：

| 方块 X | 区块 X | 区块内 X |
| ------ | ------ | -------- |
| 0      | 0      | 0        |
| 15     | 0      | 15       |
| 16     | 1      | 0        |
| -1     | -1     | 15       |
| -16    | -1     | 0        |
| -17    | -2     | 15       |

**关键规则**：由于 Java 的 `>>` 是算术右移（向下取整），负坐标的区块归属容易算错。方块 X=`-1` 不在区块 0——它在区块 -1 的最东侧（区块内 X=15）。记忆方法：**负坐标区块向 -∞ 方向取整**。

## 子区块

区块本身很高，但游戏不需要每次都遍历整根竖直柱体。它会继续沿 Y 方向把区块切成 `16 × 16 × 16` 的**子区块**（Chunk Section）。

换算规则与区块坐标**完全同构**：

```text
子区块 Y = 方块 Y >> 4
子区块内 Y = 方块 Y & 15
子区块起始 Y = 子区块 Y << 4
```

每个子区块包含 4096（16³）个坐标。`Chunk` 根据维度高度创建一个 `ChunkSection[]`；主世界高度为 384 格，因此一个完整的主世界区块拥有 384/16 = 24 个子区块。

**子区块坐标 ≠ 数组下标**。主世界最底部的子区块坐标为 -4（`-64 >> 4 = -4`），但在 `ChunkSection[]` 中的数组下标是 0。转换公式为：

```text
数组下标 = 子区块坐标 - 最底部子区块坐标
```

所以 `sectionArray[0]` 对应子区块坐标 -4，`sectionArray[23]` 对应子区块坐标 19（即 Y=304 到 Y=319）。

## 区块里有什么

从技术研究的角度看，区块远不只是"4096 的很多倍个方块"。`Chunk` 中保存或关联了以下数据：

| 数据类别 | 存储位置 | 说明 |
|---|---|---|
| 方块状态 | `ChunkSection[].PalettedContainer<BlockState>` | 使用调色板+紧凑数据，节省空间 |
| 高度图 | `Map<Heightmap.Type, Heightmap>` | 四种高度图：MOTION_BLOCKING、MOTION_BLOCKING_NO_LEAVES、OCEAN_FLOOR、WORLD_SURFACE |
| 方块实体 | `Map<BlockPos, BlockEntity>` + `Map<BlockPos, NbtCompound>` | 已加载的方块实体和待加载的 NBT |
| 结构信息 | `Map<Structure, StructureStart>` + `Map<Structure, LongSet>` | 结构起点和结构引用 |
| 生物群系 | `PalettedContainer<RegistryEntry<Biome>>` | 每子区块 4×4×4 分辨率 |
| 其他元数据 | `inhabitedTime`, `upgradeData`, `needsSaving` | 已居住时间、升级数据、保存标记 |

子区块还维护三项计数，用于快速跳过不需要处理的子区块：
- `nonEmptyBlockCount`：非空气方块数
- `randomTickableBlockCount`：需要随机刻的方块数
- `nonEmptyFluidCount`：非空流体方块数

> [!IMPORTANT]
> 普通实体在 1.20.1 中由独立的 `ServerEntityManager` 和 `EntityChunkDataAccess` 维护，与方块状态不使用同一套区块存储结构。我们仍会说"实体位于某个区块"，是因为实体的位置决定了它和哪些区块的加载等级关联，但这不等于实体数据存储在 `Chunk` 对象内部。

## 生成完成不等于正在运算

你可能观察过这样的现象：远处地形已经在客户端出现，但那里的红石装置或实体并不一定正常运算。

这是因为"区块存在"不是简单的是非判断。一个区块从不存在到完全运作，需要依次经历四个维度的判定：

| 维度 | 判定标准 | 发生了什么事 |
|---|---|---|
| **是否已生成** | 达到 `ChunkStatus.FULL` | 地形、结构、洞穴、地物、光照全部完成，`ProtoChunk` 转换为 `WorldChunk` |
| **是否已完整加载** | 加载等级 ≤ 33（`FULL`） | 区块数据在内存中，可供读写 |
| **是否进行方块运算** | 加载等级 ≤ 32（`BLOCK_TICKING`） | 红石运算、计划刻、随机刻等正常执行 |
| **是否进行实体运算** | 加载等级 ≤ 31（`ENTITY_TICKING`） | 实体 AI、移动、刷怪等正常执行 |

这四个维度**依次递进**：后面的维度成立时，前面的必然已经成立。但反过来不一定——一个可能已经生成并加载的区块，如果尚未达到 `BLOCK_TICKING`，其红石装置就不会运作。

生成过程本身也分为多个阶段，从 `EMPTY` → `STRUCTURE_STARTS` → `STRUCTURE_REFERENCES` → `BIOMES` → `NOISE` → `SURFACE` → `CARVERS` → `FEATURES` → `INITIALIZE_LIGHT` → `LIGHT` → `SPAWN` → `FULL`，共 12 步。每个阶段都有对应的任务（`GenerationTask` 或 `LoadTask`），必须按顺序完成。

加载票如何决定一个区块处于哪个加载等级，将在[加载票](../LoadingTicket/README.zh.md)章节中讨论。

## 小实验

1. 在创造模式中按下 `F3 + G`。
2. 找到 X=`15` 与 X=`16` 两列方块，观察它们是否位于边界两侧。
3. 再前往 X=`-1` 与 X=`0`，观察负坐标侧的边界。
4. 使用调试界面记录这四个位置的区块坐标。

这个实验足以验证区块坐标采用向下取整，而不是简单地去掉小数部分。

## 小结

- 区块的本质定义：水平 16×16、覆盖维度完整高度的竖直区域。
- 区块坐标由 `方块 X>>4`、`方块 Z>>4` 得到；区块内坐标由 `&15` 得到。负坐标向 -∞ 取整。
- 每个区块按高度分为 16×16×16 的子区块；子区块坐标与数组下标不是同一概念，差值为 `-bottomSectionCoord`。
- 方块状态保存在子区块的 `PalettedContainer<BlockState>` 中；子区块还维护三项计数优化跳空。
- 区块数据不仅包含方块状态，还包含高度图、方块实体、生物群系、结构信息和元数据。
- 一个区块的"存在"有四个递进维度：已生成 → 已加载 → 方块运算 → 实体运算，不可混淆。

## [!ADVANCED] 源码分析

### 从方块坐标到区块坐标

区块坐标的换算核心在 `ChunkSectionPos` 中：

```java
// ChunkSectionPos.java
public static int getSectionCoord(int coord) {
    return coord >> 4;       // 向下取整除以 16
}

public static int getLocalCoord(int coord) {
    return coord & 15;       // 区块内坐标 0~15
}

public static int getBlockCoord(int sectionCoord) {
    return sectionCoord << 4; // 反算：区块坐标 → 方块起始坐标
}
```

`ChunkPos` 构造时就调用这些方法：

```java
// ChunkPos.java
public ChunkPos(BlockPos pos) {
    this.x = ChunkSectionPos.getSectionCoord(pos.getX());
    this.z = ChunkSectionPos.getSectionCoord(pos.getZ());
}

public int getStartX() {
    return ChunkSectionPos.getBlockCoord(this.x); // 区块最西侧方块 X
}

public int getEndX() {
    return this.getOffsetX(15);                   // 区块最东侧方块 X
}
```

这里可以看出，`getSectionCoord` 使用 `>> 4`（算术右移），对负数向下取整。`-1 >> 4 = -1`、`-16 >> 4 = -1`、`-17 >> 4 = -2`，这正是正文中表格的来源。

### 子区块坐标与数组索引

`ChunkSection[]` 的数组下标从 0 开始，对应维度最底部的子区块。`HeightLimitView` 负责两者间的转换：

```java
// HeightLimitView.java
default int getTopY() {
    return this.getBottomY() + this.getHeight();   // 上界（不含）
}

default int countVerticalSections() {
    return this.getTopSectionCoord() - this.getBottomSectionCoord();
}

default int sectionCoordToIndex(int coord) {
    return coord - this.getBottomSectionCoord();   // 子区块坐标 → 数组下标
}

default boolean isOutOfHeightLimit(int y) {
    return y < this.getBottomY() || y >= this.getTopY();
}
```

主世界 `bottomY = -64`、`height = 384`，所以 `topY = 320`。`-64 >> 4 = -4` 是底部子区块坐标，对应 `sectionArray[0]`。`sectionCoordToIndex(-4)` 返回 `-4 - (-4) = 0`。

### 区块数据组织

`Chunk` 的核心字段：

```java
// Chunk.java
protected final ChunkSection[] sectionArray;                       // 子区块数组
protected final Map<Heightmap.Type, Heightmap> heightmaps;         // 高度图
protected final Map<BlockPos, BlockEntity> blockEntities;          // 已加载的方块实体
protected final Map<BlockPos, NbtCompound> blockEntityNbts;       // 待加载的方块实体 NBT
private final Map<Structure, StructureStart> structureStarts;      // 结构起点
private final Map<Structure, LongSet> structureReferences;         // 结构引用
protected volatile boolean needsSaving;                            // 是否需要保存
private long inhabitedTime;                                        // 已居住时间
protected final UpgradeData upgradeData;                           // 升级数据
```

子区块使用 `PalettedContainer<BlockState>` 按调色板 + 紧凑数据方式存储方块状态，为空气为主或方块单一的区块节省空间。`ChunkSection` 还维护三项计数：

```java
// ChunkSection.java
private short nonEmptyBlockCount;        // 非空气方块数
private short randomTickableBlockCount;  // 需要随机刻的方块数
private short nonEmptyFluidCount;        // 非空流体方块数
```

`setBlockState` 方法在写入新状态时同步更新这三项计数和调色板容器：

```java
// ChunkSection.java
public BlockState setBlockState(int x, int y, int z, BlockState state, boolean lock) {
    BlockState blockState;
    if (lock) {
        blockState = this.blockStateContainer.swap(x, y, z, state);
    } else {
        blockState = this.blockStateContainer.swapUnsafe(x, y, z, state);
    }
    // 减少旧方块的计数
    if (!blockState.isAir()) { this.nonEmptyBlockCount--; ... }
    if (!fluidState.isEmpty()) { this.nonEmptyFluidCount--; }
    // 增加新方块的计数
    if (!state.isAir()) { this.nonEmptyBlockCount++; ... }
    if (!fluidState2.isEmpty()) { this.nonEmptyFluidCount++; }
    return blockState;
}
```

### 区块生成状态（ChunkStatus）

区块不是"一次性生成完就使用"的。生成过程从 `EMPTY` 到 `FULL` 经过一系列步骤：

| 状态 | 主要任务 |
|---|---|
| `EMPTY` | 起点，不包含任何数据 |
| `STRUCTURE_STARTS` | 确定结构起始点 |
| `STRUCTURE_REFERENCES` | 添加结构引用 |
| `BIOMES` | 填充生物群系 |
| `NOISE` | 生成噪声地形 |
| `SURFACE` | 构建地表 |
| `CARVERS` | 挖掘洞穴 |
| `FEATURES` | 生成地物（树木、矿石等） |
| `INITIALIZE_LIGHT` | 初始化光照 |
| `LIGHT` | 完整光照计算 |
| `SPAWN` | 生成初始生物 |
| `FULL` | 可以转换为 `WorldChunk` |

每个状态都有对应的 `GenerationTask` 或 `LoadTask`，定义了从上一个状态推进到当前状态需要执行的操作。`ChunkStatus.ChunkType` 区分 `PROTOCHUNK`（生成中，使用 `ProtoChunk`）和 `LEVELCHUNK`（已完成，使用 `WorldChunk`）。

### 加载等级与运算资格

区块是否参与方块/实体运算，取决于它的加载等级（chunk level）：

```java
// ChunkLevels.java
private static final int FULL = 33;
private static final int BLOCK_TICKING = 32;
private static final int ENTITY_TICKING = 31;

public static ChunkLevelType getType(int level) {
    if (level <= 31) return ChunkLevelType.ENTITY_TICKING;   // 实体运算
    else if (level <= 32) return ChunkLevelType.BLOCK_TICKING; // 方块运算
    else return level <= 33 ? ChunkLevelType.FULL : ChunkLevelType.INACCESSIBLE;
}
```

`ChunkLevelType` 是一个简单的枚举，按 `ordinal()` 比较"级别深度"：

```java
// ChunkLevelType.java
public enum ChunkLevelType {
    INACCESSIBLE,    // 尚未达到完整可访问状态
    FULL,            // 区块数据完整可用
    BLOCK_TICKING,   // 方块运算可以进行
    ENTITY_TICKING;  // 实体运算也可以进行
}
```

`World#setBlockState` 中可以看到，只有当前区块达到了 `BLOCK_TICKING` 级别，服务端才会通知客户端：

```java
// World.java setBlockState 中的判断
(this.isClient || worldChunk.getLevelType() != null
    && worldChunk.getLevelType().isAfter(ChunkLevelType.BLOCK_TICKING))
```

这就是为什么远处地形可以在客户端显示，但红石装置不运算：区块的加载等级可能只达到了 `FULL`，尚未达到 `BLOCK_TICKING`。加载票（Loading Ticket）如何决定这些等级，将在[加载票](../LoadingTicket/README.zh.md)章节详述。
