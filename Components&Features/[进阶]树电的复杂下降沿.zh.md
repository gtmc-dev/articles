## 引言

基础篇介绍了树电的基本原理：树叶通过 PP 更新驱动的计划刻检查自己到原木的距离，当距离发生变化时发出更新，形成连锁传播。

但实际应用中，树电的下降沿（原木移除后，`distance` 方块状态 逐层增大的传播过程）远比上升沿复杂。这篇文章会深入源码，解释树电下降沿顺序混乱的要因。

## 原木移除与 PP 更新的触发

树电的下降沿始于**原木与树叶串断开连接**。当相邻的树叶接收到 PP 更新后，会通过 `getStateForNeighborUpdate` 调度一个计划刻：

```java
// LeavesBlock.java, lines 69-82
@Override
public BlockState getStateForNeighborUpdate(
    BlockState state, Direction direction, BlockState neighborState, WorldAccess world, BlockPos pos, BlockPos neighborPos
) {
    if (state.get(WATERLOGGED)) {
        world.scheduleFluidTick(pos, Fluids.WATER, Fluids.WATER.getTickRate(world));
    }

    int i = getDistanceFromLog(neighborState) + 1;
    if (i != 1 || state.get(DISTANCE) != i) {
        world.scheduleBlockTick(pos, this, 1);
    }

    return state;
}
```
我们可以注意到一个条件：

> 如果「根据相邻方块们计算出的距离」加1后，结果不是 1（即相邻方块不是原木），**或者**树叶自身的 `distance` 与该结果不同，则添加延迟为 1 的计划刻


```java
// LeavesBlock.java, lines 58-61
@Override
public void scheduledTick(BlockState state, ServerWorld world, BlockPos pos, Random random) {
    world.setBlockState(pos, updateDistanceFromLogs(state, world, pos), Block.NOTIFY_ALL);
}
```

计划刻请求被添加到 `ChunkTickScheduler`：

```java
// ChunkTickScheduler.java, lines 59-71
@Override
public void scheduleTick(OrderedTick<T> orderedTick) {
    if (this.queuedTicks.add(orderedTick)) {
        this.queueTick(orderedTick);
    }
}

```

值得注意的是`queuedTicks` 是一个遵循 `OrderedTick.HASH_STRATEGY` 的 `Set`，因此**同一位置、同一方块类型的计划刻不会重复添加**。就算树叶在同一 gt 内接收到多次 PP 更新，也只会计划一个计划刻。[^2]

[^2]: `HASH_STRATEGY` 定义在 `OrderedTick.java` 第 22-36 行，哈希值由 `pos.hashCode()` 和 `type.hashCode()` 组合计算。

## 距离计算

树叶的 `distance` 计算由 `updateDistanceFromLogs` 方法完成：

```java
// LeavesBlock.java, lines 84-96
private static BlockState updateDistanceFromLogs(BlockState state, WorldAccess world, BlockPos pos) {
    int i = 7;
    BlockPos.Mutable mutable = new BlockPos.Mutable();

    for (Direction direction : Direction.values()) {
        mutable.set(pos, direction);
        i = Math.min(i, getDistanceFromLog(world.getBlockState(mutable)) + 1);
        if (i == 1) {
            break;
        }
    }

    return state.with(DISTANCE, i);
}
```

这个方法会检查六个方向的相邻方块，找到最小的 `distance` 值，然后 +1 作为自己的新 `distance`。如果找到原木（`getDistanceFromLog` 为 0），则立即返回 1。

但这个"六方向最小值"的计算，在多邻居环境中会产生反直觉的结果
：
原木移除时，起初仅有它周围的树叶会试图刷新，而树叶串的上的其它方块还保持在旧的状态。

```
原木 - 叶A - 叶B 
       |
       叶C
```
（叶A与原木，B，C相邻

1. 叶A 接收到 PP 更新，调度计划刻
2. 计划刻执行时，叶A 计算 `distance`：
   - 原木位置现在是空气，`getDistanceFromLog` 返回 7
   - 叶B 的distance仍然是旧状态，读为2
   - 叶C 仍然是旧状态，同理
   - 最小值是 2，尽管已经没有与叶串连接的原木，叶A 的新 `distance`仍然是3，而非7。
3. 叶A 改变，向叶B 和叶D 发出 PP 更新
4. 叶B 和叶D 调度计划刻
5. 计划刻执行时：
   - 叶B 读取叶A为3，最小值 3，新 `distance`为4
   - 叶C读取叶A为3，最小值 3，新 `distance`为4
6. 树叶间来回传播，直至全部 `distance ` 到达7

这个过程是复杂而多变的，它需要经过数gt来回“荡漾”得到最终结果。因此它对叶串结构、更新顺序、计划刻的执行顺序都相当敏感。

## 总结

树电的下降沿是一个复杂的过程：

在树叶串中，`distance` 的传播策略在下降沿反过来阻碍`distance` 因为原木的移除而一次性增长为7，因为仅有原木周围的树叶被初次更新，它们尝试刷新自身`distance` 时，其它树叶还处在旧的状态。

在这样的情况下，整条树叶串需要耗费数gt来回互相更新，最终将`distance` 收敛到固定状态。而方向，原木的位置，树叶串的形状都会对这个过程产生相当的影响。

实际上，同样的情况在红石粉的熄灭，水，岩浆等流体的流失中，也因类似原因出现。
