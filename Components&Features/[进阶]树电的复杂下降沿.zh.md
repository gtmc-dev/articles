## 引言

> [!NOTE]
> 本文的源码描述基于 Minecraft Java 版 1.20.1、Yarn `1.20.1+build.10` 映射。代码片段与行号均来自 `D:\guardian` 中的该版本源码。

基础篇介绍了树电的基本原理：树叶通过 PP 更新驱动的计划刻检查自己到原木的距离，当距离发生变化时发出更新，形成连锁传播。

但实际应用中，树电的下降沿（原木移除后，`distance` 逐层增大的传播过程）远比上升沿复杂。这篇文章会深入源码，解释树电下降沿的拓扑计算、计划刻调度、状态回写，以及与脚电的对比。

## 原木移除与 PP 更新的触发

树电的下降沿始于**原木不再位于树叶的距离计算路径中**。当相应操作写入替代状态，且没有使用 `FORCE_STATE` 跳过状态—邻居处理时，`World.setBlockState` 会执行后续的 PP 更新路径。[^1]

[^1]: 源码路径 `World.java` 第 234-285 行的 `setBlockState` 方法。第 274-278 行表明：未设置 `FORCE_STATE` 且更新深度仍大于 0 时，旧状态与新状态会依次执行 `prepare`／`updateNeighbors` 等更新。

相邻的树叶接收到 PP 更新后，会通过 `getStateForNeighborUpdate` 调度一个计划刻：

```java
// LeavesBlock.java, lines 69-82
@Override
public BlockState getStateForNeighborUpdate(
    BlockState state, Direction direction, BlockState neighborState, WorldAccess world, BlockPos pos, BlockPos neighborPos
) {
    if (state.get(WATERLOGGED)) {
        world.scheduleFluidTick(pos, Fluids.WATER, Fluids.WATER.getTickRate(world));
    }

    int i = getDistanceFromLog(neighborState) + 1;
    if (i != 1 || state.get(DISTANCE) != i) {
        world.scheduleBlockTick(pos, this, 1);
    }

    return state;
}
```

这段代码的关键逻辑：

1. 计算相邻方块的距离值 + 1
2. 如果结果不是 1（即相邻方块不是原木），**或者**树叶自身的 `distance` 与该值不同，调用 `scheduleBlockTick` 调度延迟为 1 的计划刻
3. 计划刻被调度后，会在延迟到期时执行 `scheduledTick` 方法：

```java
// LeavesBlock.java, lines 58-61
@Override
public void scheduledTick(BlockState state, ServerWorld world, BlockPos pos, Random random) {
    world.setBlockState(pos, updateDistanceFromLogs(state, world, pos), Block.NOTIFY_ALL);
}
```

方块刻调度请求被添加到 `ChunkTickScheduler`：

```java
// ChunkTickScheduler.java, lines 59-71
@Override
public void scheduleTick(OrderedTick<T> orderedTick) {
    if (this.queuedTicks.add(orderedTick)) {
        this.queueTick(orderedTick);
    }
}

private void queueTick(OrderedTick<T> orderedTick) {
    this.tickQueue.add(orderedTick);
    if (this.tickConsumer != null) {
        this.tickConsumer.accept(this, orderedTick);
    }
}
```

关键点在于：`queuedTicks` 是一个使用 `OrderedTick.HASH_STRATEGY` 的 `Set`，它保证了**同一位置、同一方块类型的计划刻不会重复添加**。如果树叶在同一 gt 内接收到多次 PP 更新，调度器会去重，只保留一个计划刻。[^2]

[^2]: `HASH_STRATEGY` 定义在 `OrderedTick.java` 第 22-36 行，哈希值由 `pos.hashCode()` 和 `type.hashCode()` 组合计算。这个去重机制在下降沿传播中非常重要：当多个相邻树叶同时完成 `distance` 更新时，它们会向同一个树叶发出多次 PP 更新，但调度器只会为该树叶创建一个计划刻。

## 距离计算的拓扑逻辑

树叶的 `distance` 计算由 `updateDistanceFromLogs` 方法完成：

```java
// LeavesBlock.java, lines 84-96
private static BlockState updateDistanceFromLogs(BlockState state, WorldAccess world, BlockPos pos) {
    int i = 7;
    BlockPos.Mutable mutable = new BlockPos.Mutable();

    for (Direction direction : Direction.values()) {
        mutable.set(pos, direction);
        i = Math.min(i, getDistanceFromLog(world.getBlockState(mutable)) + 1);
        if (i == 1) {
            break;
        }
    }

    return state.with(DISTANCE, i);
}
```

这个方法会检查六个方向的相邻方块，找到最小的 `distance` 值，然后 +1 作为自己的新 `distance`。如果找到原木（通过 `getDistanceFromLog` 返回 0），则立即停止搜索，返回 1。

但这个"六方向最小值"的计算，在多分支拓扑中会产生非直觉的结果。考虑以下场景（示意性，并非精确 tick 跟踪）：

```
原木 - 叶A - 叶B - 叶C
       |
       叶D - 叶E
```

当原木被移除后，距离值会通过迭代松弛逐步收敛到固定点。每个树叶在计划刻执行时，会读取**当前时刻**相邻方块的 `distance` 值，而这些值可能是旧状态。因此传播过程中存在"陈旧邻居距离"问题：

1. 叶A 接收到 PP 更新，调度计划刻
2. 计划刻执行时，叶A 计算 `distance`：
   - 原木位置现在是空气，`getDistanceFromLog` 返回 7
   - 叶B 仍然是旧状态，`distance=2`
   - 叶D 仍然是旧状态，`distance=2`
   - 最小值是 2，所以叶A 的新 `distance=3`
3. 叶A 状态回写，向叶B 和叶D 发出 PP 更新
4. 叶B 和叶D 调度计划刻
5. 计划刻执行时：
   - 叶B 读取叶A=3，叶C=3（旧状态），最小值 3，新 `distance=4`
   - 叶D 读取叶A=3，叶E=3（旧状态），最小值 3，新 `distance=4`
6. 传播继续，直到所有树叶的 `distance` 收敛到稳定值或达到 7

这个过程类似图算法中的松弛操作：每次计算都基于当前已知的邻居状态，多次迭代后收敛。**实际延迟取决于拓扑结构、计划刻的调度阶段和执行顺序**，不能简单概括为"每层 1 gt"或"分支导致固定延迟"。

## 计划刻的调度顺序

计划刻的执行顺序由 `OrderedTick` 的比较器决定：

```java
// OrderedTick.java, lines 8-17
public record OrderedTick<T>(T type, BlockPos pos, long triggerTick, TickPriority priority, long subTickOrder) {
    public static final Comparator<OrderedTick<?>> TRIGGER_TICK_COMPARATOR = (first, second) -> {
        int i = Long.compare(first.triggerTick, second.triggerTick);
        if (i != 0) {
            return i;
        }

        i = first.priority.compareTo(second.priority);
        return i != 0 ? i : Long.compare(first.subTickOrder, second.subTickOrder);
    };
    // ...
}
```

排序规则：

1. **triggerTick**（触发时刻）：计划刻应该在哪个 tick 执行
2. **priority**（优先级）：树叶使用默认优先级 `TickPriority.NORMAL`
3. **subTickOrder**（子刻顺序）：在同一 tick 内的调度顺序

树叶的计划刻 delay 为 1，因此 `triggerTick` 为当前 tick + 1。计划刻会在 `triggerTick` 对应的 Tick Tick 阶段被优先级队列取出并执行。

## 状态回写与 Block.NOTIFY_ALL

当树叶完成 `distance` 计算后，`scheduledTick` 方法调用 `setBlockState` 更新方块状态：

```java
// LeavesBlock.java, lines 58-61
@Override
public void scheduledTick(BlockState state, ServerWorld world, BlockPos pos, Random random) {
    world.setBlockState(pos, updateDistanceFromLogs(state, world, pos), Block.NOTIFY_ALL);
}
```

`Block.NOTIFY_ALL` 是一个标志常量，定义为 `3`（`NOTIFY_NEIGHBORS | NOTIFY_LISTENERS`），定义在 `Block.java` 第 133 行。[^3]

[^3]: 源码路径 `Block.java` 第 104、108、133 行。`NOTIFY_NEIGHBORS=1`、`NOTIFY_LISTENERS=2`、`NOTIFY_ALL=3`。

在 `World.setBlockState` 中，这个标志控制两个关键更新路径：

```java
// World.java, lines 267-278 (简化)
if ((flags & Block.NOTIFY_NEIGHBORS) != 0) {
    this.updateNeighbors(pos, blockState.getBlock());  // NC 更新
    if (!this.isClient && state.hasComparatorOutput()) {
        this.updateComparators(pos, block);
    }
}

if ((flags & Block.FORCE_STATE) == 0 && maxUpdateDepth > 0) {
    int i = flags & ~(Block.NOTIFY_NEIGHBORS | Block.SKIP_DROPS);
    blockState.prepare(this, pos, i, maxUpdateDepth - 1);
    state.updateNeighbors(this, pos, i, maxUpdateDepth - 1);  // PP 更新
    state.prepare(this, pos, i, maxUpdateDepth - 1);
}
```

因此，树叶在更新自己的 `distance` 后，会触发：

- 通过 `updateNeighbors` 通知相邻 NC 响应方块
- 通过 `state.updateNeighbors` 向六个方向发出 PP 更新，相邻的树叶通过 `getStateForNeighborUpdate` 调度新的计划刻，继续传播

这就是树电能驱动无粉布线的核心：每一层树叶的状态变化都会发出更新，形成可预测的传播链。

## distance=7 的特殊处理

当树叶的 `distance` 增大到 7 时，它不会立即移除，而是被标记为"需要衰变"：

```java
// LeavesBlock.java, lines 42-55
@Override
public boolean hasRandomTicks(BlockState state) {
    return state.get(DISTANCE) == 7 && !state.get(PERSISTENT);
}

@Override
public void randomTick(BlockState state, ServerWorld world, BlockPos pos, Random random) {
    if (this.shouldDecay(state)) {
        dropStacks(state, world, pos);
        world.removeBlock(pos, false);
    }
}

protected boolean shouldDecay(BlockState state) {
    return !state.get(PERSISTENT) && state.get(DISTANCE) == 7;
}
```

`distance=7` 且 `PERSISTENT=false` 的树叶会启用随机刻（`hasRandomTicks` 返回 true）。在 `randomTick` 中，`shouldDecay` 检查通过后，树叶会被移除。随机刻的执行时机由游戏规则 `randomTickSpeed` 控制，无法预测。[^4]

[^4]: 随机刻每 tick 随机选择区块内的若干方块执行。触发频率与 `randomTickSpeed` 成正比，但具体哪个方块何时被选中是随机的。

当树叶最终被移除时，它会向六个方向发出**另一轮状态变化更新**，这可能会触发相邻树叶的再次检查。如果电路仍与这些树叶保持连接，这个移除波可能影响布线行为。如果相邻树叶依然没有找到更近的路径，它们的 `distance` 不会变化，方块状态也不会改变，因此不会发出新的更新，传播链在这里终止。

## 持久树叶的特殊行为

如果树叶的 `PERSISTENT` 属性为 `true`（玩家手动放置的树叶），它**仍然参与 distance 计算、接收 PP 更新、调度计划刻、更新状态并传播**。`PERSISTENT=true` **仅**阻止 `distance=7` 时的随机刻衰变：

```java
// LeavesBlock.java, lines 42-55 (已引用)
public boolean hasRandomTicks(BlockState state) {
    return state.get(DISTANCE) == 7 && !state.get(PERSISTENT);
}
```

持久树叶的 `distance` 计算、计划刻调度和状态更新逻辑与非持久树叶完全相同。唯一区别是当 `distance=7` 时，`hasRandomTicks` 返回 false，不会启用随机刻，因此不会衰变。在树电传播中，持久树叶会正常传播信号。

## 与脚电的对比

脚手架的 `distance` 计算与树叶类似，但有个关键区别：

> **脚手架优先检查下方支撑**，而树叶是六方向平等检查

脚手架的距离计算逻辑：

```java
// ScaffoldingBlock.java, lines 133-154
public static int calculateDistance(BlockView world, BlockPos pos) {
    BlockPos.Mutable mutable = pos.mutableCopy().move(Direction.DOWN);
    BlockState blockState = world.getBlockState(mutable);
    int i = 7;
    if (blockState.isOf(Blocks.SCAFFOLDING)) {
        i = blockState.get(DISTANCE);
    } else if (blockState.isSideSolidFullSquare(world, mutable, Direction.UP)) {
        return 0;
    }

    for (Direction direction : Direction.Type.HORIZONTAL) {
        BlockState blockState2 = world.getBlockState(mutable.set(pos, direction));
        if (blockState2.isOf(Blocks.SCAFFOLDING)) {
            i = Math.min(i, blockState2.get(DISTANCE) + 1);
            if (i == 1) {
                break;
            }
        }
    }

    return i;
}
```

这个逻辑保证了纵向堆叠的脚手架会共享相同的 `distance`，因此脚电可以实现**纵向同步传播**，而树电的纵向传播会受到拓扑路径的影响。

脚手架在 `distance=7` 时的双分支处理：

```java
// ScaffoldingBlock.java, lines 96-108
@Override
public void scheduledTick(BlockState state, ServerWorld world, BlockPos pos, Random random) {
    int i = calculateDistance(world, pos);
    BlockState blockState = state.with(DISTANCE, i).with(BOTTOM, this.shouldBeBottom(world, pos, i));
    if (blockState.get(DISTANCE) == 7) {
        if (state.get(DISTANCE) == 7) {
            FallingBlockEntity.spawnFromBlock(world, pos, blockState);
        } else {
            world.breakBlock(pos, true);
        }
    } else if (state != blockState) {
        world.setBlockState(pos, blockState, Block.NOTIFY_ALL);
    }
}
```

这使得脚电的下降沿传播更加可预测：当支撑被移除后，所有达到 `distance=7` 的脚手架会在**计划刻执行时**处理。如果旧状态已经是 7，变为下落方块实体；如果新到达 7，破坏并掉落物品。

## 总结

树电的下降沿传播是一个复杂的拓扑过程：

1. 原木移除触发相邻树叶的 PP 更新
2. 树叶通过 `getStateForNeighborUpdate` 调度延迟为 1 的计划刻
3. 计划刻执行时，调用 `updateDistanceFromLogs` 计算新的 `distance`
4. 距离计算遵循"六方向最小值 + 1"的规则，多分支路径和陈旧邻居距离导致迭代松弛
5. 调度器通过 `HASH_STRATEGY` 去重，排序依据 `triggerTick → priority → subTickOrder`
6. 状态回写时使用 `Block.NOTIFY_ALL`，触发 `updateNeighbors`（NC 更新）和 `state.updateNeighbors`（PP 更新），驱动下一层传播
7. `distance=7` 且 `PERSISTENT=false` 的树叶启用随机刻，在 `randomTick` 中衰变移除
8. 持久树叶正常参与 `distance` 计算和传播，`PERSISTENT=true` 仅阻止 `distance=7` 时的随机刻衰变

与脚电相比，树电的下降沿传播更依赖拓扑结构，而脚电的纵向继承特性使其在某些场景中更易控制。在实际应用中，理解这些底层机制可以帮助你设计更稳定、更可预测的无粉布线方案。
